# business-analysis — 业务功能讨论框架

当用户想讨论一个业务功能/需求的可行性、方案、工作量时，按以下 7 个 Phase 顺序执行。

每个 Phase 输出结论后再进下一个。如果用户提前给出足够信息，跳过已覆盖的 Phase。

## Trigger

- "分析 XX 功能"
- "XX 怎么样"
- "讨论一下 XX"
- "/business-analysis"

## Phase 1 — 需求理解

**目的**: 搞清楚到底要什么，避免做到一半发现理解偏了

1. 接收用户的一句话需求
2. 反问 2-3 个关键问题来澄清：
   - 范围：这个功能覆盖哪些场景？哪些明确不做？
   - 优先级：急需还是锦上添花？
   - 约束：有没有预算/时间/技术限制？
3. 输出：
   - **一句话需求定义**
   - **核心场景描述**（谁在什么情况下用）
   - **明确排除项**（不做什么）

## Phase 2 — 业务分析

**目的**: 从企业角度判断该不该做、做什么程度

1. **风险分析**：
   - 不做什么风险？（用户投诉、竞品差距、合规风险）
   - 做了什么新风险？（资金安全、隐私、误操作）
2. **影响分析**：影响哪些用户？影响哪些现有功能？
3. **ROI 判断**：收益 vs 成本，值不值得做
4. **行业调研**：竞品/业内怎么做的？有没有标准做法？（需要时可 WebSearch）
5. 输出：
   - **要不要做的结论**
   - **风险清单**（按严重程度排列）

## Phase 3 — 技术差距分析

**目的**: 不写代码，只摸清现有代码差在哪

1. **后端**: 现有 Service/Tool/Graph 节点够不够？缺什么？
2. **数据库**: 现有表够不够？要加字段还是加表？
3. **API/事件**: 现有 Socket 事件/API 够不够？
4. **Flutter**: 现有 Model/Widget/Provider 够不够？
5. 输出：
   - **逐层差距清单**
   - **改动文件列表**（只列文件名，不写代码）

## Phase 4 — 原型 + 状态穷举

**目的**: 在做之前把所有 UI 状态想清楚，避免开发中才发现"这个边界没考虑"

1. **主流程原型**：
   - 用文字描述关键界面
   - 建议用 excalidraw 出图（调用 `excalidraw-diagram` skill）
   - 标注交互细节（点击、滑动、长按、返回）

2. **状态穷举**（对每个界面都要过）：
   - ✅ **正常流程** — 一路畅通的理想路径
   - ⚪ **空状态** — 没数据、首次使用、被清空
   - 🔴 **错误状态** — 网络失败、服务器 500、超时
   - 🟡 **边界状态** — 余额不足、已达上限、重复操作、权限不够
   - 🔵 **加载状态** — Loading skeleton / spinner
   - 🟣 **多模式** — Light/Dark、中文/English、不同角色权限
   - ⚠️ **中断恢复** — 操作到一半退出、重连后恢复、token 过期

3. 输出：
   - **每个界面的状态矩阵**（表格式，行=界面，列=7 种状态）
   - **excalidraw 原型图**

## Phase 5 — 技术方案

**目的**: 逐层说清楚要改什么、怎么改

1. **数据库层**：
   - migration 内容（新表、新字段、索引）
   - 数据迁移策略（如果改现有数据）

2. **后端层**：
   - 新增文件路径 + 职责
   - 修改文件路径 + 改动内容
   - Service 方法签名
   - Socket 事件定义
   - 安全/权限/限流检查

3. **Flutter 层**：
   - 新增 Widget / Model / Provider 路径
   - 修改的现有文件路径
   - 状态管理变更

4. **依赖关系**：哪些可以并行？哪些有先后？
5. 输出：
   - **文件级改动清单**（路径 + 改动说明）
   - **依赖流程图**（建议 excalidraw）

## Phase 6 — 工作量评估

**目的**: 让你能决策"做不做、先做哪个"

1. 按层估算（文件数、代码行数、预估天数）
2. 按风险区分系数：
   - 安全相关（资金、权限）：+1d
   - UI 纯展示：-0.5d
   - 涉及 LLM prompt 调优：+0.5d
3. 分批建议：
   - **P0（必要）**: 不做就不能上线
   - **P1（重要）**: 体验问题可以后补
   - **P2（优化）**: 锦上添花
4. 输出：
   - **工期估算表**
   - **分批路线图**

## Phase 7 — 决策

**目的**: 你拍板，后续开干

给出选项：
- 选项 A：完整方案（一次性做完）
- 选项 B：轻量方案（先上线核心，后续迭代）
- 选项 C：分步走（P0 → P1 → P2）

**你选一个方向**，然后切换到对应的实施模式（code-review / superpowers / 直接编码）。

## Conventions

- 所有分析输出用中文，代码相关术语保留英文
- Phase 4 的原型主动建议用 excalidraw 出图
- Phase 6 的工期用"人天"为单位
- Phase 7 必须有明确的选项，不能只给建议不拍板
