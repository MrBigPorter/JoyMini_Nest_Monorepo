## 2. 诊断：为什么中文召回差

查库发现 **`intent_examples` 里 100% 是英文**（10 个域、395 条，无一条含中文）。
中文查询只能靠跨语言 embedding 硬匹配，`kyc` 库中仅 6 条英文例句，召回 12.5%；
`wallet` 29.4%、`product` 41.2%。

而代码里的 seed 文件本来就有中文（`intent-examples/*.ts`），只是运行时库被历史
`PUT ... mode=replace` 覆盖成了纯英文。修复方式不是改分类器，而是把缺的中文
补回数据层 —— 分类逻辑一行没动。

> 同类问题以后会重复出现：**seed 文件与 DB 是两套事实**。
> 建议后续把「seed 与 DB 的差异」做成部署检查项，而不是依赖人工发现。

**泄题自查**：首轮补入的「早上好」「辛苦了」与题集 g07/g14 同形，已从
seed 与 DB 中删除并重建 general 向量；删除前后分数均为 84.3%，说明提升来自
真实的中文覆盖，不是记住了题。`check_duplicates.py --against-api` 现在返回
「题集未发现泄题」。

### 3.3 二次修正：Meili 同步 + 地址语境

发现两个数据层缺陷：

1. `indexIntentExamples` 用 `filter: domain = ...` 删除旧文档，但 domain 不是
   filterable attribute，删除抛错被静默吞掉 → 已删句子仍被 BM25 命中。
   改为按固定 id ``${domain}_0..199`` 批量删除。
2. `appendToDomain` 只写向量、不更新 Meilisearch（历史遗漏）→ 新补的中文
   永远进不了关键词通道。已补上同步。

同时补了地址语境例句（order：修改订单收货地址；user：收货地址在哪里修改 / 添加 / 删除），
把「订单改址」和「地址簿管理」分开。

| 指标 | 值 |
|---|---|
| Top-1 | **86.9%**（133/153） |
| macro-F1 | **87.1%** |
| 配对变化 | +2.6pp（9 修好 / 5 回退） |
| McNemar | **p=0.42（不显著）** |

结论：方向正确（地址路由不再混），但 +4 题在 153 题样本下不足以证明显著；
报告如实标注，不当作大胜。

### 3.4 仍然错的题（20/153）

| 类型 | 例子 | 说明 |
|---|---|---|
| 规则题被业务域吸走 | `优惠券使用规则`→coupon、`提现手续费怎么收`→wallet | rag 与业务域的边界仍需靠 prompt/路由规则区分 |
| 语义歧义 | `你叫什么名字`→user、`会员等级怎么计算`→user | 期望标签本身可争议，保留为陷阱题 |
| kyc 个别表达 | `人脸识别一直转圈`→general | 可继续补「人脸/活体」类例句 |

## 4. 复现

  tools/eval/reports/<改前>.json tools/eval/reports/<改后>.json \
  --out tools/eval/reports/compare-<日期>.md
