## 3. 配置模拟器

所有配置只走环境变量，不读 `.env`。

```bash
export SIM_API_BASE_URL=http://localhost/api
export SIM_SOCKET_URL=http://localhost/events
export SIM_BUSINESS_ID=official_platform_support_v1
export SIM_TRAFFIC_SOURCE=simulation_support_v1
export SIM_OTP_CODE=123456
export SIM_ACCOUNT_COUNT=15
export SIM_CONCURRENCY=5
```

说明：本地 backend 只 `expose: 3000`，没有映射宿主机端口；`http://localhost:3000` 不可用，必须走 nginx 的 `http://localhost/api` 和 `http://localhost/events`。

渠道说明：

- `official_platform_support_v1` 是本地已有的官方客服渠道
- `trafficSource` 只用于标记来源，后端写入 `Conversation.ai_metadata.trafficSource`
- **实施前确认（当前代码缺口）**：`driver.mjs` 的 `openConversation()` 还没有把 `trafficSource` 透传给 `fetchBusinessConversation()`，`provision.mjs` 的渠道探测也没有带。此时后端会回退为 `businessId`，即 `official_platform_support_v1`，会和真实官方渠道流量混在一起。
- 两种处理方式，实施时二选一：
  1. 建专用渠道 `simulation_support_v1`，让 `SIM_BUSINESS_ID` 指向它（推荐，零代码）
  2. 修 driver/provision，把 `config.trafficSource` 透传下去（一行级改动）
- 在缺口修好前，不要声称 `trafficSource=simulation_support_v1` 已实现隔离。

## 4. 建 15 个真实账号

先干跑，不联网：

```bash
node tools/simulator/provision.mjs --count 15 --dry-run
```

正式建号：

```bash

```

行为：

- 每个账号：`POST /v1/otp/request` → `POST /v1/otp/verify` → `POST /v1/auth/login/otp`
- 手机号：`+63917` + 7 位随机
- 每账号独立 `deviceId`
- 每 5 个账号等待 60 秒，避免 OTP 限流
- token 写入 `tools/simulator/.runtime/accounts.json`，权限 600，已被 `.gitignore` 忽略

注意：

- 本地 OTP 固定码是 `123456`；生产是 `999999`
- 不要打印或提交 `accounts.json`
- 建号失败先看错误里的 HTTP 状态码

常见错误：

| 错误 | 原因 | 处理 |
|---|---|---|
| 403 CSRF | 后端 cookieParser 顺序错误 | 已修复；确认 `main.ts` 中 cookieParser 在 CSRF 前 |
| 429 | OTP 限流 | 等 60 秒或降低批量 |
| 渠道探测失败 404 | 渠道不存在/未启用 | 在 admin `/support-channels` 创建并启用 |
| 401 | token 失效 | `--replace` 重建，或删除 accounts.json |

## 9. 故障演练（仅开发）

### 9.1 Redis 断连演练（已修，可复现）

```bash
docker compose stop redis
node tools/simulator/driver.mjs --once --scenario general_greeting --account-index 13
```

**2026-11-20 修复后实测**：

- Redis 停止期间，`/api/v1/health` 持续返回 200，backend 不再退出
- Socket `send_message` 会 ack 超时；改用真实 HTTP `POST /api/v1/chat/message` 可以写入 Outbox，并停在 `PENDING`
- Redis 恢复后，`RedisService` / `RedisLockService` 自动重连成功，无需重启 backend
- 再次发消息 AI 正常回复

如果要制造 Outbox `FAILED`，需要 relay 连续 8 次入队失败；单纯停 Redis 会先卡在 `PENDING`。BullMQ 死信用 9.2 的占锁法更快、更可控。

恢复：

```bash
docker compose start redis
```

复查：

```bash
docker compose exec -T db sh -c \
  'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -v ON_ERROR_STOP=1' <<'SQL'
SELECT status, count(*) FROM ai_task_outbox GROUP BY status;
SQL
```

### 9.2 制造 BullMQ 死信（占锁法，开发环境）

思路：真实占用会话锁 `ai:conv:<conversationId>`，让 AI worker 等锁超时并抛错，BullMQ 按真实 `attempts=3 + 130s backoff` 重试耗尽后进死信。

```bash
# 1. 占住目标会话锁 15 分钟
docker compose exec -T redis sh -c \
  'REDISCLI_AUTH="$REDIS_PASSWORD" redis-cli SET ai:conv:<conversationId> fault-drill NX EX 900'

# 2. 用真实账号发一条消息（Socket 或 HTTP 均可）
#    这条消息会入 Outbox -> BullMQ，然后卡在会话锁

# 3. 等待约 3 × 130 秒，观察队列
curl -s http://localhost/api/v1/admin/queues \
  -H "Authorization: Bearer <ADMIN_TOKEN>" | jq '.data.queues[] | select(.name=="ai-processing")'

# 4. 死信出现后释放锁
docker compose exec -T redis sh -c \
  'REDISCLI_AUTH="$REDIS_PASSWORD" redis-cli DEL ai:conv:<conversationId>'

# 5. 管理员在 /ai-ops/runtime 点 Replay，或调用
curl -X POST http://localhost/api/v1/admin/queues/ai/<messageId>/replay \
  -H "Authorization: Bearer <ADMIN_TOKEN>"
```

注意：

- 锁 TTL 必须覆盖至少 3 次重试窗口；900 秒足够
- 这是真实 worker 失败，不是插库
- 生产不做

## 12. 失败处理

| 现象 | 优先排查 |
|---|---|
| 所有会话都 `property trafficSource should not exist` | `/chat/business` DTO 白名单未包含 `trafficSource`；暂时去掉该参数，依赖 businessId 回退 |
| 所有会话 `fetch failed` | `SIM_API_BASE_URL` 是否带 `/api`；本机是否能访问 |
| Socket 连不上 | `SIM_SOCKET_URL` 必须是 `http://localhost/events`（nginx 转发到 backend，backend 本身没映射 3000） |
| 全部 noReply | backend AI 日志；Redis / 队列 / LLM key |
| 16/30 网络错误 | 降低并发到 2，重试 |
| 账号全转人工 | 换新账号；转人工后该账号不能再次触发 AI |
| OTP 429 | 等待 60 秒；或减少 `--count` / 增大 `--batch-wait-ms` |
