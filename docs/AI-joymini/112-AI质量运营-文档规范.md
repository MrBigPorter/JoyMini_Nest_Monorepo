# 112 — AI 质量运营文档规范

> 状态：设计稿
> 负责人：AI 质量运营 / 平台
> 更新时间：2026-11-21
> 关联文档：[113 数据模型](./113-AI质量运营-数据模型.md)、[114 Admin 设计](./114-AI质量运营-Admin设计.md)
> 适用范围：AI 质量运营、评测、知识质量、后台产品设计

## 1. 为什么需要这套规范

AI 质量运营同时涉及四类人：

| 角色 | 关心什么 | 不应该被迫理解什么 |
|---|---|---|
| 运营 / 客服主管 | 这条对话有没有问题、该怎么处理 | `implicit`、`PENDING`、JSON、trace |
| 知识库管理员 | 知识有没有缺、检索有没有命中 | 数据库字段、队列实现 |
| 工程师 | 归因、复现、回归、版本 | 运营的工单话术 |
| 产品 / 负责人 | 质量趋势、风险、投入产出 | 单条调试细节 |

同一份文档如果混着写，四类人都看不懂。所以文档必须分层，并且统一格式。

## 2. 文档集分层

| 层 | 文档 | 回答的问题 | 主要读者 |
|---|---|---|---|
| L1 产品意图 | 产品简报 | 为什么做、成功标准是什么 | 负责人、产品 |
| L2 运营流程 | 运营工作流 | 谁在什么情况下做什么 | 运营、客服主管 |
| L3 数据模型 | 数据模型设计 | 数据怎么存、怎么兼容 | 工程师、DBA |
| L4 API 契约 | API 契约 | 前后端怎么交互 | 前后端 |
| L5 迁移 | 迁移与回填 | 老数据怎么办、怎么回滚 | 工程师、运维 |
| L6 UX | 页面状态矩阵 | 正常/空/错/边界怎么显示 | 产品、前端、运营 |
| L7 验收 | 验收脚本 | 怎么证明真的可用 | 产品、测试、运营 |
| L8 运行 | 运行手册 | 出问题怎么处理 | 运维、值班 |
| L9 决策 | ADR | 为什么选这个方案 | 所有技术角色 |

一份需求不要求写满九层。但只要涉及数据结构或运营动作，至少要有 L2、L3、L6、L7。

## 3. 所有文档的固定头部

每份文档开头必须包含：

```markdown
> 状态：草稿 / 评审中 / 已批准 / 已废弃
> 负责人：
> 更新时间：YYYY-MM-DD
> 关联需求：
> 关联数据表：
> 关联页面：
> 关联文档：
```

没有负责人和状态的文档，不进入评审。

## 4. 模板

### 4.1 产品简报模板

```markdown
# 产品简报：<名称>

## 背景
现在发生了什么，为什么不能继续这样。

## 用户
谁用，在什么场景下用。

## 目标
用可观察的结果描述，不写“做一个页面”。

## 非目标
明确这次不做什么。

## 成功标准
- 运营可以在 X 分钟内完成 Y
- 指标从 A 到 B
- 不增加 Z 风险

## 约束
数据、权限、合规、时间、依赖。

## 方案摘要
一段话说明选择，不展开实现。
```

### 4.2 运营工作流模板

```markdown
# 运营工作流：<场景>

## 角色
谁执行。

## 触发
什么事件让这条工作出现。

## 输入
运营看到的上下文：对话、回答、来源、转人工原因。

## 判断
运营需要回答的问题，最多 5 个。
每个问题必须有选项定义。

## 动作
确认 / 排除 / 加入回归 / 标记修复 / 升级。

## 状态
处理前、处理中、处理后分别是什么状态。

## 失败与例外
信息不足、权限不足、系统故障时怎么办。

## 指标
这条工作流产生什么可统计结果。
```

### 4.3 数据模型模板

```markdown
# 数据模型：<领域>

## 目标
解决什么数据问题。

## 兼容原则
只做加法 / 可空字段 / 回填 / 回滚。

## ER 图
Mermaid。

## 实体
每个实体：用途、字段、类型、可空、默认值、索引、关系。

## 枚举
每个枚举的取值和业务含义。

## 与现有表的关系
新增、扩展、保留、不修改。

## 迁移顺序
步骤、锁风险、回填、双读、切换。

## 回滚
怎么停写、怎么恢复旧路径。

## 保留与隐私
TTL、脱敏、访问控制。
```

### 4.4 API 契约模板

```markdown
# API：<资源>

## 用途
## 权限
## 请求
字段、类型、必填、校验。
## 响应
成功、空、失败、分页。
## 幂等
重复请求会怎样。
## 错误码
业务码、HTTP 状态、运营可读文案。
## 示例
只给一个真实请求和一个真实响应。
```

### 4.5 UX 状态矩阵模板

每个页面必须覆盖七种状态：

| 状态 | 必须回答 |
|---|---|
| 正常 | 有数据时怎么显示 |
| 空 | 没有数据时说什么、下一步是什么 |
| 错误 | 接口失败怎么提示、能否重试 |
| 边界 | 超长、超大、重复、权限不足 |
| 加载 | 首屏、翻页、提交中 |
| 权限 | 无权限、只读、功能未开启 |
| 中断恢复 | 刷新、返回、会话切换后状态是否保留 |

### 4.6 验收模板

禁止写“功能完成”。必须写可观察结果：

```markdown
## 场景
运营打开页面，看到一条 ai_error 反馈。

## 操作
选择“服务故障”，点击“排除”。

## 期望
- 该条从待处理队列消失
- 状态变为“已排除”
- 不计入模型错误率
- 审计日志记录操作人和原因

## 证据
截图 / API 响应 / 数据库查询 / 页面计数。
```

### 4.7 决策记录 ADR 模板

```markdown
# ADR-<编号>：<决策>

## 背景
## 选项
A / B / C，各自代价。
## 决策
选哪个。
## 理由
## 影响
## 何时重新评估
```

## 5. 可追溯矩阵

每个需求必须能追到五层：

| 需求 | 数据 | API | UI | 验收 |
|---|---|---|---|---|
| 区分服务故障和模型错误 | `failureKind` | 反馈列表返回 `failureKind` | 归因列/筛选 | 8 条真实反馈分类正确 |

矩阵放在 L1 或 L2 文档末尾。没有矩阵的需求，不进入开发。

## 6. 评审门

### 设计评审

- 运营流程是否能被一线人员复述
- 每个判断是否有定义
- 是否有空/错/权限状态
- 是否有非目标

### 迁移评审

- 是否只做加法
- 是否可空/有默认值
- 是否有回填和回滚
- 是否有旧代码兼容路径
- 是否有锁风险

### 上线评审

- 验收脚本是否用真实数据跑过
- 指标口径是否写清
- 运营是否知道怎么处理异常
- 是否有关闭开关

## 7. 语言规范

### 运营文档禁止裸用内部术语

| 内部术语 | 运营文案 |
|---|---|
| `implicit` | 系统自动发现 |
| `explicit` | 人工标注 |
| `PENDING` | 待处理 |
| `REVIEWED` | 已确认 |
| `IGNORED` | 已排除 |
| `ai_error` | 服务故障 |
| `explicit_request` | 用户明确要求转人工 |
| `repeated_attempts` | 多次未解决 |
| `score` | 评分 / 判断结果 |
| `dataset` | 回归测试集 |
| `run` | 一次回归运行 |

### 每个专业词第一次出现必须解释

例如：

```text
回归测试：把已经确认过的问题和正确答案存成一组固定用例，
每次改 Prompt / 知识库 / 模型后重新跑一遍，确认没有变坏。
```

## 8. 版本与变更

- 文档标题下必须写状态和更新时间
- 重大决策变更追加 ADR，不直接覆盖历史
- 数据模型变更必须同时更新 113 和迁移章节
- 运营流程变更必须同时更新 114 和验收脚本
- 废弃文档保留，状态改为“已废弃”，不删除

## 9. 文件命名与位置

```text
docs/AI-joymini/NNN-主题.md         功能与运营文档
docs/superpowers/specs/YYYY-MM-DD-主题-design.md  设计规格
docs/superpowers/plans/YYYY-MM-DD-主题.md         实施计划
```

编号连续，主题用中文，避免空格和特殊符号。
