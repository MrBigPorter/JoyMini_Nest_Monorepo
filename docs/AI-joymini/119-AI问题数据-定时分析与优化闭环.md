> 状态：设计稿（未实现）
> 负责人：AI 平台 / 运营

> 关联文档：[113 数据模型](./113-AI质量运营-数据模型.md)、[114 质量 Admin 设计](./114-AI质量运营-Admin设计.md)、[115 运营化设计](./115-AI-Operations-运营化设计.md)、[116 页面结构与 UI](./116-AI-Operations-页面结构与UI规范.md)、[118 验收评审与修复计划](./118-AI-Operations-验收评审与修复计划.md)

---

## 0. 执行摘要

现在的 AI Operations 能看单条，不能看规律：

```text
单条：这条为什么错？        → 已有页面，但证据不全（118 §5.4）
批量：哪类问题最多？        → 没有
趋势：这周比上周好还是坏？  → 没有
优化：改完有没有效？        → 没有
```

本设计补的是**批量层**：

```text
原始事件 → 标准化问题事件 → 时间窗指标 → 问题簇 → 修复 → 回归 → 前后对比
```

三个原则：

1. **不扫全量原始数据。** 按时间窗增量处理，窗口可重跑、可幂等。
2. **不把每条都交给人。** 规则先归类、相似问题聚类，人只看代表和异常。
3. **不自动下结论。** 系统给证据和建议，人确认后才进入修复。

## 1. 边界与非目标

### 1.1 目标

| 目标 | 说明 |
|---|---|
| 固定时间分析 | 每小时/每天/每周自动跑，不依赖人点按钮 |
| 大规模 | 按时间窗增量，设计余量 1 万条/天 |
| 可定位 | 每个问题事件带意图、知识域、失败类型、trace、会话 |
| 可统计 | 指标有分子、分母、窗口、维度，可下钻 |
| 可优化 | 问题簇 → 修复 → 回归 → 前后对比 |
| 可运维 | 任务运行可见、失败可重跑、多实例不重复 |

### 1.2 非目标

- 不引入 ClickHouse / Kafka / Flink，不上流计算。
- 不做实时逐条 LLM 分析（成本高、噪声大）。
- 不自动修改 prompt / 知识库 / 路由。
- 不存储原始对话全文到分析表（只存脱敏片段或 ID）。
- 不替代人工判断和回归评测，分析层只负责“找出来、排好序、给证据”。

### 1.3 为什么现在是批量而不是实时

当前体量（每天几十到几百条）下，实时分析没有收益：

- 5 分钟级的健康告警已经能覆盖服务故障；
- 质量问题需要成簇才可行动，单条实时判定噪声大；
- LLM 分类成本按条计，批量可以用便宜模型 + 抽样。

## 2. 什么算“有问题数据”

先定义可计算的事件，不要用一个模糊的“异常”。

| 事件类型 | 来源 | 自动置信度 | 默认处理 |
|---|---|---|---|
| `EXPLICIT_NEGATIVE` | `ai_answer_feedback.verdict=incorrect` | 高 | 进待分诊（118 §4.3） |
| `SERVICE_ERROR` | `transferReason=ai_error` / trace ERROR / 工具失败 | 高 | 进待分诊 |
| `ZERO_HIT` | trace 的 RAG `sourceCount=0`，且该意图需要知识 | 中 | 事件 + 聚类 |
| `UNCITED_RAG` | RAG 有来源，但回答没有引用 | 中 | 事件 + 聚类 |
| `UNEXPECTED_TRANSFER` | 人工确认的误转 | 高 | 进待跟进 |
| `REPEATED_QUESTION` | 隐式信号 | 中 | 信号区 + 聚类 |
| `EVAL_UNSOLVED` | `ai_eval_results.verdict=unsolved` 且期望有效 | 中 | 事件 + 聚类 |
| `SECURITY_HIT` | `ai_security_events` | 低 | 安全页，不进质量待办 |
| `COST_SPIKE` | 单会话/单日 token 超基线 | 高 | 事件 + 告警 |

事件必须带：

```text
occurredAt / type / severity / confidence
conversationId / messageId / traceId
intent / domain / failureKind
source / sourceId（幂等键）
clusterId（聚类后回填）
```

### 2.1 线索不进入待办

沿用 118 §4.3 的产品决策：

- 系统隐式线索（转人工、取消、重复追问）默认只进信号区；
- 只有显式负反馈、服务故障、人工认领才进入待办；
- 分析层可以把线索聚成簇，但不能直接抬高“待处理”。

## 3. 固定时间分层

### 3.1 任务表

| 频率 | 任务 | 处理窗口 | 产出 |
|---|---|---|---|
| 每 5 分钟 | 健康检查 | 当前快照 | 服务故障、队列积压、Outbox 失败、安全命中突增告警 |
| 每小时 | 事件构建 + 指标聚合 | 上一个整点小时 | `ai_problem_events`、`ai_metric_windows` |
| 每天 02:00 UTC | 归因 + 聚类 + 日报 | 过去 24 小时 | 问题簇、日报、评审批次 |
| 每周一 03:00 UTC | 趋势 + 基线 | 过去 7 天 | 周环比、基线更新、回归集补充 |
| 每月 1 日 04:00 UTC | 保留与成本 | 上月 | 清理、成本报告 |

时间统一用 **UTC**，页面按用户时区展示。原因是 `ai_usage_daily` 已经按 UTC 日分桶，避免两套日界。

### 3.2 窗口语义

```text
windowStart = 2026-11-21T00:00:00Z
windowEnd   = 2026-11-22T00:00:00Z   // 左闭右开
windowType  = DAY
```

迟到数据（late arrival）处理：

- 每次运行回看 24 小时，按幂等键 upsert；
- 不做“只追加”，保证重跑结果一致；
- 日报生成后如果补跑，允许覆盖同窗口的聚合行。

### 3.3 幂等与单写者

```text
jobId = analysis:hourly:2026-11-21T10:00:00Z
唯一键 = (jobType, windowStart)
```

- BullMQ repeatable job 用固定 `jobId`；
- 启动时获取 Redis 锁或 Postgres `pg_try_advisory_lock`；
- 拿不到锁直接跳过，不排队；
- 运行记录写 `ai_analysis_runs`，状态 `RUNNING / COMPLETED / FAILED`；
- 启动时把超过 2 小时仍 `RUNNING` 的旧记录标 `FAILED`（孤儿回收）。

## 4. 数据模型

### 4.1 表清单

| 表 | 用途 | 保留 |
|---|---|---|
| `ai_problem_events` | 标准化问题事件 | 180 天 |
| `ai_problem_clusters` | 滚动问题簇 | 长期 |
| `ai_problem_cluster_days` | 簇按天计数 | 365 天 |
| `ai_metric_windows` | 指标窗口 | 长期 |
| `ai_analysis_runs` | 任务运行记录 | 90 天 |

### 4.2 `ai_problem_events`

```text
id                String   @id @default(cuid())
occurredAt        DateTime
windowStart       DateTime
windowType        String   // HOUR / DAY
type              String   // 见 §2
severity          Int      // 1 低 / 2 中 / 3 高

source            String   // feedback / trace / security / eval / usage
sourceId          String   // 幂等键：feedback.id / trace.id / event.id
conversationId    String?
messageId         String?
traceId           String?
intent            String?
domain            String?
failureKind       String?
clusterId         String?
status            String   // NEW / CLUSTERED / TRIAGED / IGNORED / RESOLVED
metadata          Json?    // 脱敏摘要，不放原文
createdAt         DateTime @default(now())

unique(type, sourceId)
index(windowStart, type)
index(conversationId)
index(traceId)
index(clusterId)
```

### 4.3 `ai_problem_clusters`

```text
id                    String   @id @default(cuid())
signature             String   // 规范化问题的 hash
representativeText    String   // 脱敏代表问题

unique(signature)

```

### 4.4 `ai_problem_cluster_days`


```text

```

## 5. 事件构建规则

### 5.1 从现有表映射

| 来源 | 条件 | 事件类型 | 置信度 |
|---|---|---|---|
| `ai_answer_feedback` | `verdict=incorrect` | `EXPLICIT_NEGATIVE` | 0.9 |
| `ai_answer_feedback` | `signal=repeated_question` | `REPEATED_QUESTION` | 0.6 |
| `Conversation` | `transferReason=ai_error` | `SERVICE_ERROR` | 0.95 |
| `ai_traces` | `status=ERROR` | `SERVICE_ERROR` | 0.95 |
| `ai_traces` + `ai_spans` | RAG span `sourceCount=0` 且 intent 属于知识型 | `ZERO_HIT` | 0.7 |
| `ai_traces` + `ai_spans` | RAG `sourceCount>0` 且回答无引用 | `UNCITED_RAG` | 0.6 |
| `ai_eval_results` | `verdict=unsolved` 且用例 `expect` 非空 | `EVAL_UNSOLVED` | 0.7 |
| `ai_security_events` | 状态 `NEW` | `SECURITY_HIT` | 0.4 |
| `ai_usage_daily` | 单日 token > 基线 2σ | `COST_SPIKE` | 0.8 |

### 5.2 去重

同一来源事件只建一次：

```text
unique(type, sourceId)
```

同一会话、同一类型的重复信号（如多次转人工）在事件层保留，但聚类层合并计数。

### 5.3 脱敏

- 事件表**不存原文**；
- 聚类代表问题可以用脱敏片段（手机号、邮箱、地址、订单号打码）；
- 需要原文时，靠 `conversationId` / `traceId` 回原表，按角色控制；
- 分析表保留 180 天，原始 trace 按 113 的 30 天策略。

## 6. 定位方法

### 6.1 维度

```text
意图       coupon_query / order_query / wallet_query ...
知识域     coupon / order / wallet / kyc ...
失败类型   MODEL_ERROR / SERVICE_ERROR / ZERO_HIT ...
模型       deepseek-chat / 其他
Prompt 版本（补齐后）
渠道       用户会话 / 评测 / 后台
时间       小时 / 天 / 周
```

### 6.2 归因判断树

```text
意图置信度低，且人工判为答非所问？
  → ROUTING（路由/关键词/示例）

意图对，RAG 0 命中？
  → KNOWLEDGE_GAP（补文档）

RAG 有命中，回答没引用？
  → PROMPT_OR_RANKING（改 prompt / 排序 / 截断）

工具 span 报错或超时？
  → TOOL_FAILURE（工具/下游）

以上都正常，人工仍判错？
  → MODEL_CAPABILITY（换模型/加约束/加 few-shot）

全部正常，但用户重复追问？
  → UX_OR_CLARITY（追问引导/澄清）
```

### 6.3 聚类

目标：把 1000 条相似问题变成 1 个簇，人只看代表。

```text
1. 规范化：去标点、去问候、统一大小写
2. 生成 signature：规范化文本 hash（精确去重）
3. 向量聚类：embedding 余弦相似度 >= 0.85 归入已有簇
4. 新簇：创建 centroid
5. 代表问题：取簇内最高频 + 最高严重度的脱敏文本
```

实现细节：

- 复用现有 embedding 提供方（bge-m3 / Jina），不新增模型；
- pgvector 建 HNSW/IVFFlat 索引；
- 每次只对窗口内新事件做增量归类，不全量重算；
- 簇跨天滚动，`ai_problem_cluster_days` 记录每天计数，便于看趋势。

### 6.4 影响分

```text
impact = count × severity × confidence
priority = impact / effort
```

- `count`：窗口内事件数
- `severity`：1/2/3
- `confidence`：事件置信度
- `effort`：KNOWLEDGE=1 / PROMPT=2 / ROUTING=2 / TOOL=3 / MODEL=4 / INFRA=3

排序只用于“先看哪个”，不自动决定修什么。

## 7. 统计口径

### 7.1 核心指标

| 指标 | 分子 | 分母 | 窗口 |
|---|---|---|---|
| `problem_rate` | 问题事件数 | AI 回复数 | 小时/天 |
| `solve_rate` | solved | solved + partial + unsolved | 每次评测/周 |
| `zero_hit_rate` | ZERO_HIT 事件 | 需要知识的请求 | 天 |
| `citation_rate` | 有引用的回答 | 有 RAG 命中的回答 | 天 |
| `mis_transfer_rate` | 确认误转 | 确认转人工 | 天 |
| `service_error_rate` | SERVICE_ERROR | AI 回复数 | 小时/天 |
| `repeat_rate` | 重复追问事件 | 会话数 | 天 |
| `cost_per_solved` | 总成本 | solved | 周 |
| `p95_latency` | — | — | 小时/天 |

每个指标必须能回答：

```text
分子是什么？分母是什么？哪个时间窗？按什么维度切？样本量多少？
```

### 7.2 异常检测

不要用固定阈值：

```text
baseline = 过去 7 天同星期几的中位数
偏离 = (today - baseline) / MAD
告警条件：偏离 >= 2 且 sampleSize >= 30
```

- 样本不足只记录，不告警；
- 低量时用 7 天滚动均值，不用单日；
- 告警必须带“同比/环比”和“样本量”，避免“1 条 = 100%”。

### 7.3 分段

```text
按意图：coupon_query 的问题率
按知识域：wallet 的零命中率
按模型/prompt：版本切换前后
按渠道：用户会话 vs 评测
```

分段的目的是找“哪一段显著高于整体”，不是给每个维度都画图。

## 8. 优化闭环

### 8.1 簇的状态机

```text
NEW
  → ASSIGNED（指定负责人）
  → FIXING（确定修复类型）
  → VERIFYING（回归验证中）
  → CLOSED（连续 7 天低于阈值）
  ↘ IGNORED（确认不是问题）
```

### 8.2 修复类型

| 类型 | 动作 | 验证 |
|---|---|---|
| `KNOWLEDGE_GAP` | 补文档 / 改切片 | 检索测试 + 同问题 LIVE 回归 |
| `PROMPT_OR_RANKING` | 改 prompt / rerank / 截断 | 回归集对比 |
| `ROUTING` | 改意图关键词/示例/阈值 | 意图重跑 + 回归 |
| `TOOL_FAILURE` | 修工具/兜底/重试 | 单测 + trace 复跑 |
| `MODEL_CAPABILITY` | 换模型/加 few-shot/加约束 | 回归集 + 抽检 |
| `INFRA` | 修服务/扩容 | 错误率监控 |

### 8.3 从簇到回归

```text
1. 取簇代表问题 + 脱敏上下文
2. 写期望：mustMention / mustNot / expectedAction / language
3. 创建回归用例，关联 clusterId 和来源
4. LIVE 跑一次，记录基线
5. 修复后重跑，比较 verdict 和簇计数
```

没有期望答案的簇**不能进入 VERIFYING**，否则又回到“空期望假通过”。

### 8.4 前后对比

```text
修复前：簇 count = 180/天，zero_hit_rate = 18%
修复后：簇 count = 12/天，zero_hit_rate = 3%
结论：有效，关闭
```

如果计数没降：

- 修错了地方（回到 §6.2 重新归因）；
- 或者问题被别的簇吸收（看总问题率）；
- 或者样本不足（延长观察窗口）。

## 9. 规模化与可靠性

| 关注点 | 做法 |
|---|---|
| 不扫全量 | 按窗口增量；`ai_analysis_runs` 记录水位 |
| 不重复计算 | `(jobType, windowStart)` 唯一键 + upsert |
| 不重复跑 | Redis 锁 / `pg_try_advisory_lock`，只允许一个实例 |
| 不阻塞聊天 | 分析任务独立 BullMQ 队列，失败不影响主链路 |
| 不全部用大模型 | 规则先分类；只有模糊样本走便宜模型；抽样校准 |
| 不无界增长 | 事件 180 天、运行记录 90 天、聚合长期；按天分区 |
| 不静默失败 | 每次 run 落状态；超过 2 小时未完成告警 |
| 可重跑 | 任意窗口可手动重跑，结果覆盖 |
| 可回填 | 新规则上线后，按窗口回放历史事件 |

### 9.1 批量与采样

```text
规则可判的：全部处理（无 LLM 成本）
需要 LLM 的：每天最多 N 条，按严重度优先
人工评审：每簇 1 条代表，不逐条看
```

### 9.2 失败表现

- 任务失败 → `ai_analysis_runs.status=FAILED`，页面显示原因；
- 数据为空 → 显示“窗口内无事件”，不是 0 指标；
- 锁被占用 → 跳过并记录，不报错；
- 下游表缺失 → 该指标标记 `unavailable`，不显示 0。

## 11. 分期实施

### Phase 1：日级指标 MVP（3–5 天）

范围：

- 建 4 张表；
- 每小时跑 EVENT_BUILD（只用规则，不聚类、不 LLM）；
- 每天跑 METRICS + 日报；
- 页面只做“分析任务 + 指标趋势”。

验收：

- 连续 7 天有数据；
- 任意指标可下钻到事件；
- 同一窗口重跑两次，计数一致；
- 抽 10 条事件与源表对得上；
- 任务失败可见，不显示 0。

### Phase 2：问题事件 + 聚类（1 周）

范围：

- 事件构建接入 trace/feedback/eval/security；
- embedding 聚类 + 代表问题；
- 问题簇页面 + 认领 + 建议归因。

验收：

- Top 20 簇覆盖 ≥60% 的问题事件；
- 重复问题合并，人工只评审代表；
- 簇可按天看趋势；
- 簇能一键创建回归用例（带期望）。

### Phase 3：小时级告警（3–5 天）

范围：

- 服务故障、零命中、成本突增、SLA 超时；
- 基线与显著性判断；
- 告警去重、静默窗口。

验收：

- 模拟 `ai_error` 突增，10 分钟内告警；
- 正常波动不告警；
- 告警带样本量和对比。

### Phase 4：优化闭环（1–2 周）

范围：

- 簇状态机、负责人、修复类型；
- 回归集成、前后对比；
- 周报：Top 变化、已修复、仍失败。

验收：

- 至少 1 个簇完成“发现 → 修复 → 回归 → 计数下降 → 关闭”；
- 报告能说清“改了什么、指标从多少到多少”。

### Phase 5：规模化与治理

范围：

- 表分区、保留策略、回填工具；
- LLM 分类预算与抽样；
- 多实例锁与故障演练。

## 12. 与 118 的依赖关系

分析层依赖以下修复，否则事件不完整：

| 118 项 | 依赖原因 |
|---|---|
| P0-4 统一时间窗 | 没有“今日”口径，指标无法对齐 |
| P1-2 血缘（traceId / aiMessageId / conversationId） | 事件无法回链到会话和消息 |
| P1-3 分类在摄入时派生 | 事件类型依赖 `failureKind` |
| P0-2 回归期望答案 | 簇无法进入 VERIFYING |
| P1-10 trace 字段 | 零命中/引用/工具事件依赖 span |
| P1-11 单写者 | 多实例定时任务会重复写 |

**建议顺序**：118 本周第 1–8 项完成后，再启动 Phase 1；否则事件层会继承同样的空值与假数字。
