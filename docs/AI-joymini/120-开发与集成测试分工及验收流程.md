# 120 — 开发与集成测试分工及验收流程

> 状态：流程稿
> 负责人：AI 平台
> 更新时间：2026-11-21
> 适用范围：[118 修复计划](./118-AI-Operations-验收评审与修复计划.md)、[119 定时分析](./119-AI问题数据-定时分析与优化闭环.md)
> 角色：Lead（主线）/ Dev（开发）/ QA（集成测试）
> 一句话：开发对实现负责，QA 对验收标准负责，Lead 对合并负责。

---

## 0. 为什么这样分

不是“一个人写、一个人点一遍”，而是让两条线不共享假设：

```text
Dev 知道自己怎么写的 → 容易只测自己想到的路径
QA 只看验收标准   → 能测出 Dev 没想到的边界
Lead 只看证据     → 决定能不能合并
```

如果 QA 照着实现写断言，测试就变成“把代码翻译一遍”，永远测不出“实现本身理解错了”。

---

## 1. 角色与边界

### 1.1 RACI

| 事项 | Lead | Dev | QA | 产品/运营 |
|---|---|---|---|---|
| 拆任务、定验收标准 | **A/R** | C | C | C |
| 产品规则（语言、资金操作） | C | I | I | **A/R** |
| 写产品代码 | I | **R** | I | I |
| 写单元测试 | I | **R** | I | I |
| 写集成/E2E 测试 | I | C | **R** | I |
| 测试环境与 fixtures | I | C | **R** | I |
| 代码评审 | **R** | C | I | I |
| 合并与发布 | **R** | I | C | I |
| 验收签字 | A | I | **R** | C |
| 缺陷分级与延期 | **A** | C | R | C |

A=最终负责，R=执行，C=被咨询，I=知会。

### 1.2 边界

**Dev 不做：**

- 自己宣布“验收通过”；
- 修改 QA 的测试来让测试通过；
- 决定产品口径（如“回答正确算什么状态”）。

**QA 不做：**

- 修改产品代码；
- 按实现反推断言；
- 用 mock 代替真实后端做验收；
- 直接改开发/生产数据库。

**Lead 不做：**

- 替 QA 做验收；
- 在 QA 未签字时合并；
- 让 Dev 和 QA 私下协商降低标准。

---

## 2. 验收标准从哪里来

每条任务必须能指向一个文档条目：

```text
118 §8.1 第 4 项：回答正确 → NO_ISSUE；连续审 A/B/C 不漏
119 §11 Phase 1：同一窗口重跑结果一致
```

验收标准必须写成**可观察的行为**，不写“优化一下”“体验更好”。

产品规则未确认的，任务不能进入开发：

- 中文提问是否必须中文回答；
- 充值/提现是否只引导、不执行。

## 3. 交接契约

### 3.1 开发交接

每次交付必须给一个**冻结提交**和一份 handoff 文件：

```text
handoff/batch-N.md
```

模板：

```markdown
# Handoff — Batch N

## 任务
- 118-4 分诊语义
- 118-5 今日口径

## 分支与提交
- branch: feat/batch-N
- commit: <sha>
- base: <sha>

## 改动文件
- apps/api/...
- apps/admin-next/...

## 验收标准对照
| 标准 | 实现位置 | 自测结果 |
|---|---|---|

## 自测证据
- `yarn workspace @lucky/api tsc --noEmit` → 通过
- `yarn workspace @lucky/api test ...` → X passed
- 手工步骤：...

## 开关与环境
- AI_FEEDBACK_UI_ENABLED=...
- 迁移：...

## 已知限制
- 未做的：
- 未测的：
- QA 需要特别注意的：

## 回滚
- 关闭开关 / 回滚提交 / 回滚迁移
```

没有 handoff 的提交，QA 不接。

### 3.2 QA 报告

```text
qa/reports/batch-N.md
```

模板：

```markdown
# QA Report — Batch N

## 测试对象
- commit: <sha>
- 环境: qa compose / DB joy_mini_qa / Redis DB 15
- 迁移: 已执行 / 未执行
- 数据集: fixtures vN

## 结果
| 用例 | 预期 | 实际 | 结论 |
|---|---|---|---|

## 数据对账
| 指标 | 页面值 | SQL 值 | 一致 |
|---|---|---|---|

## 缺陷
| ID | 严重度 | 复现 | 期望 | 实际 |
|---|---|---|---|---|

## 结论
- PASS / FAIL
- 未覆盖项与原因
- 是否允许合并
```

### 3.3 缺陷单

```text
qa/defects.md
```

每条包含：ID、批次、严重度、复现步骤、期望、实际、证据（日志/截图/SQL）、状态。

## 4. 批次节奏

### 4.1 冻结提交，不测移动代码

```text
Dev 实现 Batch N
  → 自测
  → 提交并冻结（记录 commit sha）
  → 写 handoff
        ↓
QA 在独立 worktree 检出该 commit
  → 跑集成/E2E
  → 写报告
        ↓
Dev 同时开始 Batch N+1（独立分支）
        ↓
QA PASS → Lead 合并 Batch N
QA FAIL → Dev 回到 Batch N 修 → QA 复测
```

QA 永远测一个固定 commit，不追开发的最新代码。

### 4.2 批次大小

- 每批 1–2 个任务；
- 单批改动超过 15 个文件或跨 3 个模块，拆批；
- 每批必须有独立可演示的结果。

### 4.3 修复轮次

- 同一缺陷最多 3 轮修复；
- 3 轮不过，Lead 裁定：降级、拆任务或回滚；
- 不允许“再试一次”无限循环。

---

## 5. 环境隔离

QA 不能复用开发库，否则数据污染、断言不稳、清库误删。

| 资源 | 开发 | QA |
|---|---|---|
| 数据库 | `joy_mini` | `joy_mini_qa`（独立 volume） |
| Redis | DB 0 | DB 15 |
| 队列前缀 | `bull:` | `qa-bull:` |
| API 端口 | 4000 | 4100 |
| Admin 端口 | 4001 | 4101 |
| 账号 | 开发测试号 | `qa_*` 专用账号 |
| 数据 | 联调数据 | 每次重置 + fixtures |
| 开关 | 开发取值 | QA 显式固定 |

规则：

- QA 迁移只从被测 commit 执行；
- QA 种子只进 QA 库，禁止往开发/生产库 INSERT；
- 每批开始前重置，结束后保留失败现场；
- 失败现场包含：DB 快照、日志、队列状态、截图。

### 5.1 难测场景的 harness

| 场景 | 做法 |
|---|---|
| 固定时间 | 注入 Clock 或 fake timers，手动触发窗口任务 |
| 迟到数据 | 窗口关闭后补一条，重跑窗口 |
| 多实例 | 起两个 API 进程/容器，共享 DB/Redis，断言只跑一次 |
| Redis 故障 | 停 Redis 容器或指向错误地址，断言页面显示错误而非 0 |
| DB 故障 | 停 DB，断言任务 FAILED、页面不显示 0 |
| 模型超时 | 用本地 stub/代理返回超时，断言降级 |
| 权限矩阵 | 4 个角色 × 页面/接口，断言 403 且不泄漏字段 |

## 6. 测试分层与归属

| 类型 | 归属 | 是否作为合并门禁 |
|---|---|---|
| 单元测试 | Dev | 是（CI） |
| 类型检查 / lint | Dev | 是（CI） |
| API 契约测试（真实 DB） | QA | 是 |
| UI E2E（真实后端） | QA | 是（关键流程） |
| UI 冒烟（mock） | Dev | 否（只做渲染） |
| 权限矩阵 | QA | 是 |
| 失败注入 | QA | 是（P0/P1 场景） |
| 幂等 / 重跑 | QA | 是（119） |
| 多实例 | QA | 是（扩容前必须） |
| 数据对账 | QA | 是（119） |
| 保留 / 清理 | QA | 是（上线前） |

**明确一点**：现有 `ai-ops` E2E 是全 mock 的，只能证明页面能渲染，不能证明后端接线。验收必须有一套打真实 API 的集成套件。

## 7. Batch 1–5 任务与验收

### Batch 1：权限 + 下钻（1 天）

**Dev**

- 118 #1：VIEWER 去原文；judge 去 VIEWER；Sidebar 按角色隐藏工程页。
- 118 #2：质量页读 URL 参数；KPI 卡可点；Insights 链接带参。

**QA**

- 4 角色调 traces / feedback / support / context，断言返回字段与 403。
- 首页每张异常卡 → 列表数量与卡片一致；刷新保留筛选。
- 切角色登录，断言导航与页面一致。

**验收**

- VIEWER 看不到原始 `input/output/answer`；
- VIEWER 看不到 Memory/Context/Traces；
- 点「服务故障 3」→ 列表恰好 3 条且都是 SERVICE_ERROR。

### Batch 2：分诊语义 + 今日口径（1.5 天）

**Dev**

- 118 #4：待办/信号分轨；`updateTriage` 原子派生；正确 → `NO_ISSUE`；修跳条。
- 118 #5：feedback summary/list 加时间窗；首页与质量页统一；待处理按 §4.3 口径。

**QA**

- 造 10 条已知反馈（显式负反馈、服务故障、转人工、取消、重复追问、正确回答）。
- 断言：只有显式负反馈/服务故障/已认领进待办；信号区计数正确。
- 连续审 A/B/C，断言不跳过。
- 跨 UTC 日边界：昨天数据不进今日；新一天归零。
- 只改备注，断言不新增 `AiScore`。

**验收**

- “待处理”数字与 SQL 按新口径统计一致；
- 回答正确显示“无问题”，不再计入确认问题；
- 信号区不抬高待处理。

### Batch 3：开关 + 血缘（1.5 天）

**Dev**

- 118 #7：统一前后端反馈开关；质量页禁用态；eval 写接口受 `AI_EVAL_ENABLED` 与角色约束。
- 118 #8：feedback 写 `traceId`；trace 写 `aiMessageId`；安全事件写 `conversationId`；testChat 写 trace 或停止伪造 traceId。

**QA**

- 关闭开关 → 页面显示“未启用”、接口 403、无按钮。
- 分诊一条 → trace 详情出现 HUMAN 评分。
- LIVE 评测一条 → 结果的 traceId 能在 `ai_traces` 找到。
- 安全事件 → 会话列有值，能跳到 Context。

**验收**

- 开关两端一致；
- trace / feedback / eval 三方互跳至少一条链路走通。

### Batch 4：回归期望 + eval 生命周期（2 天）

**Dev**

- 118 #3：DTO 增 `expected/sourceFeedbackId`；加入回归必须填期望；空期望拒绝启动；STORED 标注；用例编辑/删除。
- 118 #6：同 dataset 并发锁；孤儿 RUNNING 回收；终态停轮询；渲染 `summary.error`。

**QA**

- 空期望启动 → 400；有期望 → 正常。
- 跑一半杀进程 → 5 分钟内变 FAILED 且有原因。
- 结果页显示模式（LIVE/STORED）；终态不再轮询。
- 修改用例期望后重跑，结果变化可解释。

**验收**

- 3 条历史用例补全期望后，通过率变化能逐条解释；
- 不再出现“坏答案 pass”。

### Batch 5：119 Phase 1（3 天）

**Dev**

- 4 张表；事件构建（规则）；小时/日指标；分析任务页。

**QA**

- 造 100 条已知事件 → 跑任务 → 断言事件数/类型/置信度。
- 页面指标 vs SQL 聚合逐项对账。
- 同一窗口跑两次 → 行数/数值不变。
- 窗口关闭后补数据 → 重跑后计入。
- 两进程同时触发 → 只有一个 run。
- 停 DB/Redis → FAILED，页面显示原因不显示 0。
- 保留任务 → 超期事件被清理，聚合保留。

**验收**

- 连续 7 天有数；
- 10 条抽样事件与源表一致；
- 任务失败可见、可重跑。

## 8. 缺陷流转与门禁

```text
QA 发现 → 缺陷单 → Dev 修 → QA 复测 → 关闭
                         ↓ 3 轮不过
                     Lead 裁定
```

| 严重度 | 例子 | 门禁 |
|---|---|---|
| P0 | 数据泄漏、假拦截、数据写坏、任务重复写 | 阻断合并 |
| P1 | 指标口径错、状态机错、权限错、血缘断 | 阻断合并 |
| P2 | 文案、排序、空态、非关键筛选 | 可延期，记录 |
| P3 | 细节 | 记录 |

合并条件（全部满足）：

1. Dev 自测通过 + handoff 完整；
2. QA 报告 PASS，无 P0/P1；
3. Lead 代码评审通过；
4. CI 硬门禁通过（typecheck + 单测 + 集成套件）；
5. 文档已更新（118/119 状态、开关说明）；
6. 回滚方式明确。

## 9. 反模式

| 反模式 | 后果 | 纠正 |
|---|---|---|
| Dev 自己写“集成测试”并宣布通过 | 测的是实现，不是需求 | QA 独立写 |
| QA 照着实现写断言 | 实现错，测试也错 | 从 118/119 验收标准写 |
| QA 顺手修产品代码 | 独立性丢失，责任不清 | 只报不修 |
| 用 mock 代替真实后端验收 | 测试全绿、功能是假的 | 关键流程打真实 API |
| 共用开发库 | 数据污染、清库误删 | 独立 QA 环境 |
| QA 追最新代码 | 测的不是冻结提交 | 固定 commit |
| 无限修复轮次 | 批次失控 | 3 轮升级 |
| 没有 handoff | QA 靠猜 | 无 handoff 不接 |

## 10. 落到 Agent Teams

| 角色 | 工作区 | 权限 | 产出 |
|---|---|---|---|
| `lead` | 主 worktree | 拆任务、评审、合并、发布 | 任务单、评审结论、合并 |
| `dev-agent` | `worktree/dev` | 写产品代码 + 单测；不碰权限配置 | 冻结 commit + handoff |
| `qa-agent` | `worktree/qa` | 只写测试/fixtures/脚本；产品代码只读 | QA 报告 + 缺陷单 |

规则：

- 交接用文件，不靠聊天记忆：`handoff/batch-N.md`、`qa/reports/batch-N.md`、`qa/defects.md`；
- Dev 和 QA 不直接互相“说服”，有争议交 Lead；
- QA 不改产品代码，不改权限配置；
- Lead 只收摘要 + 证据，不让两个 agent 共享上下文；
- 每批结束由 Lead 决定合并或打回。

- [ ] 代码 + 单测 + 类型检查
- [ ] handoff 完整
- [ ] QA 集成/E2E 通过
- [ ] 无 P0/P1 缺陷
- [ ] 数据对账通过（涉及指标时）
- [ ] 文档更新
- [ ] 回滚验证过

## 12. 风险与应对

| 风险 | 应对 |
|---|---|
| QA 环境与生产差异大 | 用同一 compose 配置，只改端口/库名/队列前缀 |
| 测试数据污染 | 独立库 + 每批重置 + 禁止跨库写入 |
| harness 维护成本高 | 先覆盖 P0/P1 场景，不追求全量 |
| 多实例难本地复现 | 两个进程 + 共享 DB/Redis，纳入 Batch 5 |
| QA 成为橡皮图章 | 验收标准先行；QA 报告必须有无覆盖项 |
| 开发等测试 | 批次并行，Dev 做下一批 |
| 时间被测试拖长 | 每批 1–2 个任务；P2 延期 |
