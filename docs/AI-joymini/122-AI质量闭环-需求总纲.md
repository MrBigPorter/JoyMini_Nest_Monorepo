# 122 — AI 质量闭环需求总纲

> 状态：现行（2026-11-25）
> 依据：[`2026-11-25-ai-quality-console-audit.md`](../system-review/2026-11-25-ai-quality-console-audit.md)、三轴一致性核查（契约↔代码、端到端流程、页面承诺↔后端事实）、`openspec/specs/admin-ai/quality-loop`、`openspec/specs/ai-customer/quality-loop`
> 定位：**本文是这条链路的产品叙事唯一来源**——回答「要什么、为什么、到什么水平」。可测条目以 OpenSpec 为准；实现细节进各 change 的 `design.md`。

---

## 1 定位与边界

**一句话**：把线上 AI 回答的「出问题 → 判定 → 修复 → 验证 → 发布」变成一条每一步都能追溯到证据的闭环。

**做什么**

- 采集线上对话的链路证据，接收显式标注与隐式信号。
- 分诊：判定回答对错、归因到失败步骤、认领与关闭。
- 把问题转成评测用例，维护数据集与判分条件。
- 运行评测，区分「模型答错」「判官坏了」「执行失败」。
- 维护基线与回归，出可解释的差异。
- 产出发布证据，供质量负责人决策。
- 校准判官（人工标注只做校准）。
- 检查知识库文档的解析质量与版本状态。

**不做什么**

- 不做多租户；不做在线实时干预（不拦截、不改写线上回答）；不做模型训练或微调。
- 不替代人的发布决策：给证据与门槛结果，判断仍由人做。

## 2 四种决策与角色视图

四类使用者都要支撑，**运营是主场景**。复用现有角色（SUPER_ADMIN / ADMIN / VIEWER），不新增账号类型；同一页面按角色给默认视图。

| 角色 | 打开系统要回答的问题 | 默认视图 | 失败/数据不足时看到什么 |
|---|---|---|---|
| 运营（主场景） | 今天哪些反馈要处理？哪条是模型答错、哪条是判官坏了？ | 队列（未认领 / 已认领 / 已处理） | 失败条目留在队列并标原因；不因加载失败清空成「暂无」 |
| 质量负责人 | 这次能不能发？依据是什么？ | 运行 / 基线 / 发布证据 | 缺哪项证据就列哪项，不给绿灯 |
| 研发 | 这条为什么错？坏在 intent / rag / tool / llm / guardrail 哪一步？ | 链路与检索调试 | 无 trace 标「证据已过期」，不猜 |
| 管理者 | 趋势如何、成本多少？ | 趋势与成本 | 样本不足显示样本量，不画趋势线 |

**视图与决策对应**：运营看到操作按钮与队列；质量负责人看到指标、版本、门禁；研发看到 span 与检索各层计数；管理者看到时间序列与用量。同一事实只有一个来源（后端），前端推断必须标注「推断」。

## 3 主链路十步

每步必须有唯一产出与明确消费方；没有消费方的字段不得写入（除非登记为 `pendingConsumer`）。

| # | 步骤 | 输入 | 产出 | 负责角色 | 失败语义 | 证据 | 今天断在哪 |
|---|---|---|---|---|---|---|---|
| 1 | 采集 | 线上对话、检索与工具调用 | `AiTrace`/`AiSpan`（prompt 名+版本、各层检索计数、工具记录） | 系统 | 链路写入失败：回答仍返回，但该条标「无证据」 | traceId + span 树 | trace 30 天清理后反馈引用悬空；无外键 |
| 2 | 反馈 | 显式标注、隐式信号（转人工/重复追问/放弃） | `AiAnswerFeedback`（source、signal、messageId） | 系统 + 用户 | 无法定位消息 → 进「未归属」池，不猜 | 消息与信号原值 | 隐式信号靠前端推断，后端无字段 |
| 3 | 分诊 | 反馈 | verdict、failureKind、resolution、reviewStatus、owner、version | 运营 | 并发提交冲突 → 409 并提示重读；不静默覆盖 | 操作者与时间 | 认领不改队列；五种 resolution 共用「已确认」 |
| 4 | 归因 | trace span | 失败步骤 + 错误摘要 + 建议归因 | 运营确认、研发复核 | 无 trace → 标「证据已过期」，不得伪造归因 | 失败 span 的错误码与耗时 | 页面只判「有无链路」布尔，无步骤定位 |
| 5 | 转用例 | 已确认反馈 | `AiEvalCase(sourceFeedbackId)` + 反馈回链 | 运营 | 重复转 → 幂等返回已有用例 | 反馈 id ↔ 用例 id | 两列只写不读；建用例与回链非事务 |
| 6 | 数据集维护 | 新用例 | `expect` 判分条件、标签、来源类型、查重结果、**判据溯源（`sourceDocIds/sourceDocVersions`）与复核状态** | 运营 / 质量 | 超限或重复 → 400/409 并指明字段；知识变更命中溯源 → 用例进「待复核」，不得当作模型退步 | 数据集快照 hash + 溯源文档版本 | 期望双字段（`expect`/`expected`）；编辑丢条件；无查重；**判据无溯源，标准过期与模型退步不可分** |
| 7 | 运行 | 数据集、判官标准、快照 | run（互斥、心跳、采样数、判官版本）+ result（judge_error / execution_error 分账） | 质量 / 研发 | 单条失败留痕继续；连续失败达阈值熔断整单 | run id + 版本字段 | 内部 run 永不 promote；单条失败整单红 |
| 8 | 汇总 | result | summary（指标族、分子、分母、排除项、有效样本、版本） | 系统 | 缺版本 → 拒绝跨运行比较 | 可复算的全套标识 | 两套词汇表同名不同义（`delta/newFailures/fixed`） |
| 9 | 基线 / 回归 | summary + 数据集 | `isBaseline`（按数据集，仅 EXTERNAL）、回归状态机 | 质量 | 待验超期 → 标「未验证」，不默认通过 | 基线 run id 与快照 | 基线三义；`FIXED_PENDING_VERIFY` 无自动闭环 |
| 10 | 发布证据 | EXTERNAL 全量 run | `/evidence` 的 `checks[]` | 质量负责人 | 缺任一证据 → 红项列明，不给 `ok` | 每项检查的实测值与门槛 | 内部 run 按构造不合格，页面不说 |
| A | 知识侧 | 文档与切块 | `parseQuality`、`effectiveness`、`activeVersion` | 运营 / 研发 | 解析失败单独计，不混入有效性；有效性未采集显示「未采集」 | 四项解析检查明细、版本号 | 解析分冒充「知识检索质量」；「当前版本」两种含义 |
| B | 标注校准 | 判官结论 + 人工标注 | 一致率、样本量、分歧明细、标注 provenance | 质量负责人 | `n<20` → 「样本不足」，不下结论 | 标注者、guide 版本、置信度 | 标注不入库、不进报表；文档自相矛盾 |

## 4 状态机

每个状态必须有产出方与至少一条转移；不允许只能人工点击推进或永不产出的状态。

### 4.1 反馈分诊

- `reviewStatus`：`PENDING`（待处理）→ `REVIEWED`（已处理）｜`IGNORED`（已排除，必须有排除理由）。
- `IGNORED` → `PENDING`：撤销排除，需记录操作者与原因。
- **认领是正交属性**（`claimedBy/claimedAt`），不改变 `reviewStatus`；展示上把待处理分成「未认领 / 已认领」两段，认领 ≠ 处理完成。
- 产出方：运营提交分诊；系统派生 `reviewedBy/reviewedAt` 于「判定类」提交，不于「仅认领」「仅备注」。

### 4.2 评测运行

`RUNNING` → `COMPLETED` ｜ `FAILED`（`failureCategory`：入队、预算、未捕获异常、心跳超时、判官整体不可用）｜ `CANCELLED`（仅从 RUNNING，记录发起人）。

单条判官/执行失败不改变 run 状态；连续失败达阈值（默认 5）才整单 `FAILED`，且 summary 保留已判分计数。

### 4.3 回归用例

`OPEN` → `FIXED_PENDING_VERIFY`（某次运行判定通过）→ `CLOSED`（下一轮仍通过）｜ 打回 `OPEN`/`REGRESSED`（下一轮失败，记 `regressedAt`）。

推进由运行结果自动完成，不靠人工口头确认。

## 6 权威层级

同一事实只有一个权威来源，冲突按序裁决：

1. **质量结论**：judge verdict（多数聚合）为准。人工标注只用于校准一致率，不进入任何通过率/准确率的分母或分子；`unsafe/abstain` 既不算通过也不算失败。
2. **分诊路由**：`failureKind` 只用于决定进哪个队列、给谁看，不参与质量分。
3. **辅助分**：`AiScore`（分诊打分）不参与质量分，必须显式标量纲。
4. **知识分**：`parseQuality` 只描述文档解析质量，不代表回答正确；`effectiveness` 未采集时显式显示未采集，不得用解析分代替。
5. **数据来源**：run 记录 > 页面缓存 > 前端推断；前端推断必须标注「推断」。
6. **术语唯一**：「基线」只能指按数据集登记的 EXTERNAL 基线 run；对比用的任意 run 叫「对比运行」；知识库回归的「上次全量」叫「上次全量运行」，不叫基线。「待处理」只能是 `PENDING`。「当前版本」只能是 `activeVersion`，最新写入叫「最新写入版本」。

## 7 非功能约束

- **多实例**：禁止本地文件与进程内状态承载共享数据。标注落库（JSONL 仅作导出）；清扫用 `@Cron` + 分布式锁；启动互斥用 DB 约束；转用例用事务 + advisory lock。
- **保留期与悬空引用**：trace 30 天清理后，反馈保留、证据标「已过期」，不删除反馈；引用失效必须在页面可见。
- **分页上限**：反馈列表 `pageSize ≤ 100`；run 结果默认 50、上限 200；数据集用例同形状；切块不前端分页，走服务端 diff。
- **权限**：VIEWER 只读且字段脱敏；写接口仅 ADMIN/SUPER_ADMIN；只读数据集（`e2e:` 前缀）拒绝一切写请求。
- **时区**：筛选 URL 保持 `YYYY-MM-DD`，调用 API 前转本地日界；后端 date-only 语义不变。
- **成本**：run 可见用量；内部单次采样必须显式声明采样数。
- **依赖失败**：判官、检索、向量库失败必须可见（逐条分账或降级标记），不得静默折算成业务失败。

## 8 验收机制

### 8.1 四不变量（任何改动都要回答）

1. **指标可复算**：族、分子、分母、排除项、spec 版本、数据集快照、判官模型/供应商、run id。
2. **标注可归属**：标注者（人/模型）、guide 版本、置信度、原始信号。
3. **失败可定位**：坏在 intent/rag/tool/llm/guardrail 哪一步 + span 错误。
4. **回归可解释**：用例从哪条反馈/哪次文档变更产生、每次运行判定、两次运行差异。

### 8.2 三道门禁

1. **字段/枚举注册表 + 测试**：summary key、枚举值、指标族必须已登记；未登记即测试红。
2. **Requirement ↔ 代码/测试映射表**：每条 Requirement 在 spec 内标注实现文件与验证用例，未映射视为未交付。
3. **coding-standards 审阅项**：提交前声明所改链路步骤、四不变量影响，并跑一致性核查。

### 8.3 做完能达到的水平

| 维度 | 今天 | 做完 |
|---|---|---|
| 数字 | 判官坏掉时通过率莫名下跌；基线下拉显示「-」 | 每个百分比可复算到族、分母、版本、run、快照 |
| 操作 | 403 吞成 `undefined`，提示成功但没写进去 | 禁用/失败/未知三态可区分，无假成功 |
| 失败 | 只知道「有没有链路」 | 指到具体步骤 + span 错误 |
| 回归 | 只有「新建规则 + run 列表」 | 时间线 + 四分类 diff（新增/修复/回退/仍失败） |
| 发布 | 内部 run 假装能当证据 | 只认 EXTERNAL 全量，内部 run 老实标「诊断」 |
| 运维 | 标注在本地 JSONL，多实例互相覆盖 | 落库 + 锁，多实例成立 |

**四条验收话术**（能说出来才算达标）：

1. 「发布前 EXTERNAL 全量：准确率 X%，判官一致率 Y%，证据在这。」
2. 「这次知识更新：8 条修复、2 条回退，回退的两条坏在 rag 第 3 层。」
3. 「今天 12 条待处理，其中 3 条是判官失败，不是回答错误。」
4. 「运营 30 分钟清完当日队列。」

**两个已知天花板**（做完也不会消失）：

- **评测集覆盖**：指标只覆盖数据集内用例；未入集的场景质量未知。本次不建覆盖率看板（需要长期运营积累），在本文登记为已知限制。
- **判官质量**：所有分数以判官为准。本次补校准入口（一致率 + 样本量 + 分歧明细，`n<20` 不下结论），但校准入口必须真的被使用，否则体系会「精确地错」。

## 9 明确不做与不承诺

**不做**：多租户；在线实时干预；模型训练；分布式锁之外的新基础设施；为内部 run 补发布证据资格；评测集覆盖率看板（本次）。

**不承诺**：不让模型更聪明；不承诺准确率提升具体百分比；不替人做发布决策——给证据与门槛结果，判断仍是人。
