## 三、详细对标分析

### 3.1 规划能力（挑战 01, 02, 06）

#### 挑战 01: 复杂目标的自主拆解 ⚠️

**当前实现**: Supervisor Node 使用 LLM 将用户意图分解为多个 Agent 任务。

```typescript
// supervisor.node.ts — 当前实现（将被方案 B 移除）
const systemPrompt = `...你是一个任务分解专家...
根据用户查询，分解为以下 Agent 中的一个或多个：${AGENT_LIST}...`;
```

**问题**: Bug 5 已验证 — LLM 会编造不存在的 Agent（如"购买商品订单和优惠券"分解为 `[walletAgent, orderAgent, generalChat]` 而非 `[orderAgent, couponAgent]`）。

**方案 B 变更**: 移除 LLM 分解，由 intentRouter 做单意图分类（Single Agent Per Round）。不再需要自主拆解。

**学习资料关联**: [`01-autonomous-decomposition.md`](../../study/LLM/general-agent/01-autonomous-decomposition.md) 提供了完整的 Plan-and-Execute 架构参考（规划节点 + 校验节点 + 重拆逻辑），但不适用于当前客服场景（客服场景每个用户请求是独立任务，无需跨步规划）。

---

#### 挑战 02: 规划的动态调整（重规划）❌

**当前实现**: 无重规划机制。intentRouter 一次性分类完成后不可修改。

**适用性分析**: 在 JoyMini 客服场景中，用户每次发一条消息，意图路由是"单次分类"而非"多步规划"。因此**重规划需求较低**。但以下场景可能需要：
- Agent 执行过程中发现需要额外信息（如查询订单后发现需要优惠券信息）
- 当前无机制让 Agent 在执行中"重新路由"到另一个 Agent

**方案 B 影响**: 方案 B 后意图路由固定，更不需要重规划。

**优先级**: P3（低，当前场景不适用）

---

#### 挑战 06: 目标偏离 / 任务漂移 ❌

**根因分析**: Bug 5 就是**目标偏离**的典型案例。Supervisor LLM 收到"查优惠券"的请求，却分配了 `orderAgent` + `walletAgent`。

**偏离原因**:
1. **语义近似性混淆**: "优惠券"和"订单"在电商场景中语义接近
2. **无排斥规则**: Prompt 没有说"如果用户仅提及优惠券，不要分配其他 Agent"
3. **助人偏差**: LLM 倾向于"多做事"而不是精确做事
4. **无 Chain-of-Thought**: 直接让 LLM 输出 Agent 列表，没有推理过程

**方案 B 修复**: 由 intentRouter 做确定性路由（单意图分类），Supervisor 仅做 round 计数器，完全消除 LLM 在编排层的决策。

**学习资料关联**: [`06-goal-drift.md`](../../study/LLM/general-agent/06-goal-drift.md) 讨论了目标漂移的检测和修正策略。

---

### 3.2 执行能力（挑战 03-05）

#### 挑战 03: ReAct 推理-行动循环稳定性 ✅

**当前实现**: `orderAgentNode` 和 `walletAgentNode` 均使用 LangGraph 的 `createReactAgent` 构建。

```typescript
// order-agent.node.ts:29
export const createOrderAgentNode = (
  llmConfig: LlmProviderConfig,
  orderTools: TaggedTool[],
): AgentNodeFactory => {
  return async (state: typeof AgentState.State): Promise<AgentNodeOutput> => {
    const reactAgent = createReactAgent({
      llm: llmFactory(llmConfig),
      tools: orderTools.map(t => t.tool),
    });
    // ...
  };
};
```

**稳定性保障**:
- LangGraph `createReactAgent` 内部实现了 ReAct 循环的标准控制流
- 工具调用结果通过 `tool` role 返回到 messages
- Agent 在工具调用完成后自动返回最终回答

**未覆盖场景**:
- 极端长的 ReAct 循环（超过正常步数）无保护
- 工具返回格式异常时 LLM 可能解析失败

---

#### 挑战 04: 死循环 / 原地打转 ⚠️

**当前保护**:
- `supervisorRouter` 在 [`customer.graph.ts:55`](../../apps/api/src/client/ai-customer/graph/customer.graph.ts:55) 有 `maxRounds = 5`（实际生效 3 轮后 supervisorRound >= 3 走 end）
- `agentDoneRouter` 在 [`customer.graph.ts:44`](../../apps/api/src/client/ai-customer/graph/customer.graph.ts:44) 确保 Agent 完成后不再重复调用

**缺失保护**:
- 单 Agent 内部的 ReAct 循环无限步
- 工具调用结果反复触发 LLM 重新思考但没有进展
- 无"连续相同输出"检测（如果 Agent 连续 3 次返回相同内容）

**学习资料关联**: [`04-loop-cycle-detection.md`](../../study/LLM/general-agent/04-loop-cycle-detection.md) 提供了循环检测策略：
- 相同状态检测（hash consecutive states）
- 连续相同 tool_call 检测
- 最大步数限制

---

#### 挑战 05: 失控的资源消耗 ❌

**当前状态**: 完全无保护。

| 资源维度 | 当前状态 | 风险 |
|---------|---------|------|
| 单 Agent 最大 Token 消耗 | 无限制 | LLM 可能在长上下文中消耗大量 Token |
| 单步超时 | 无 | 工具调用可能永远挂起 |
| 总体超时 | 无 | 整个 Graph 执行无时间限制 |
| 最大工具调用次数 | 无 | ReAct 可能无限循环 |

**学习资料关联**: [`05-resource-consumption-control.md`](../../study/LLM/general-agent/05-resource-consumption-control.md) 提供了：
- Token 预算（per-step + total）
- 超时机制（Runnable.withFallbacks）
- 步数计数器

### 3.3 记忆管理（挑战 08-10）

#### 挑战 08: 短期工作记忆管理 ✅

**当前实现**: `state.ts` 中 `currentMessages` 字段管理当前会话的对话历史。

```typescript
// state.ts
currentMessages: Annotation<BaseMessage[]>({
  reducer: (a, b) => {
    // AgentNode 返回所有消息，直接用 b
    if (b.length > a.length) return b;
    return a;
  },
  default: () => [],
}),
```

**工作原理**:
- 每轮对话追加新消息
- AnswerSynthesizer 在最终回复前截取 `slice(-6)` 窗口避免超长上下文
- MemorySaver 持久化到下次对话

---

#### 挑战 09: 长期记忆存取 ✅

**当前实现**: [`MemorySaver Checkpointer`](18-PostgreSQLCheckpointer.md) 已实现。

**关键代码**:
```typescript
// ai-customer.service.ts
const checkpointer = new MemorySaver();
const graph = builder.compile({ checkpointer });
```

**能力**:
- 跨会话持久化状态
- 通过 `configurable.thread_id` 区分不同用户/会话
- 恢复时自动加载上一次会话的最后状态

**待优化**:
- 生产环境需迁移到 PostgreSQL Checkpointer
- 长期记忆无"衰减"或"摘要"机制

---

#### 挑战 10: 记忆的取舍与遗忘 ⚠️

**当前状态**: Bug 4 已暴露此问题 — `taskResults` 使用 merge reducer:

```typescript
// state.ts — Bug 4 根因
taskResults: Annotation<Record<string, any>>({
  reducer: (a, b) => ({ ...a, ...b }),
  // merge 不会删除旧 key，跨轮污染
});
```

**已应用修复**: 双重置策略
1. `intentRouter` 入口重置 `taskResults = {}`
2. `answerSynthesizer` 入口重置 `taskResults = {}`

**但这仍是 workaround**，而非完整的记忆管理方案。需要：
- 显式的记忆淘汰策略（保留最近 N 轮，丢弃旧数据）
- 记忆摘要（将多轮对话压缩为摘要）

**学习资料关联**: [`10-memory-selection-forgetting.md`](../../study/LLM/general-agent/10-memory-selection-forgetting.md) 讨论了记忆的取舍策略。

### 3.5 多智能体编排（挑战 13-15）

#### 挑战 13: 多智能体的角色分工与编排 ⚠️

**当前架构**: Supervisor Pattern（Orchestrator-Worker 模式）。

```
User → IntentRouter → [Gateway: FLOW_INTENTS 缓存检查]
  → Supervisor Router (按 round 分流)
    → Round 0: Supervisor Node (LLM 拆解)
    → Round > 0: Supervisor Node (计数器+1)
  → Agent Executor → AgentDone Router → End/Supervisor
```

**问题**: Bug 5 — Supervisor LLM 在 Round 0 的拆解可能错误。

**方案 B 变更**: 移除 Supervisor 的 LLM 拆解，变为纯计数器。

```
User → IntentRouter（确定性分类，单意图）
  → Supervisor（仅 round++，无 LLM 调用）
  → Agent Executor → AgentDone → End
```

**编排模式变更**: 从 Orcherstrator-Worker 变为 Sequential Router 模式。每个 round 执行一个 Agent，不交叉。

---

#### 挑战 14: 智能体间的通信与冲突 ⚠️

**当前通信机制**: 通过共享的 `AgentState` 实现。

| 通信渠道 | 用途 | 污染风险 |
|---------|------|---------|
| `currentMessages` | 对话消息历史 | 低（纯追加） |
| `taskResults` | 各 Agent 的执行结果 | 高（Bug 4 已验证） |
| `intentResult` | 最新意图分类 | 中（每轮覆盖） |
| `supervisorResult` | Supervisor 输出 | 中（每轮覆盖） |

**方案 B 后**: `taskResults` 每轮只存一个 Agent 的结果，相互覆盖不再有合并冲突问题。

---

#### 挑战 15: 多智能体协作的成本与收敛 ❌

**当前状态**: 无成本追踪和收敛优化。

**基础保护**:
- `supervisorRound` 上限 3 轮
- 每个 Agent 完成即走 `agentDoneRouter` 回到 Supervisor

**缺失**:
- 每轮 Token 消耗统计
- 模型切换的成本优化（如简单问题用便宜模型）

### 3.8 结果质量（挑战 16）

#### 挑战 16: 结果质量不稳定 / 不可复现 ⚠️

**根因**: LLM 输出是**非确定性**的。即使是相同的 Prompt + 相同输入，不同次调用可能得到不同结果。

**项目中的表现**:
| 场景 | 不稳定表现 | 影响 |
|------|-----------|------|
| Intent Router 分类 | 相同查询可能被分到不同意图 | 用户体验不一致 |
| Supervisor 分解 | 相同查询可能分配到不同 Agent | Bug 5 的变种 |
| ReAct Agent 回答 | 相同查询可能给出不同回答 | 用户体验不一致 |
| AnswerSynthesizer 总结 | 相同结果可能重新组织不同措辞 | 可接受 |

**缓解措施**:
- **方案 B** 移除 Supervisor LLM 调用 → 消除编排层的不确定性
- LLM Temperature = 0 → 降低生成层的不确定性
- 确定性路由优先 → LLM 只做"无法确定"的兜底

**学习资料关联**: [`16-quality-instability-non-reproducibility.md`](../../study/LLM/general-agent/16-quality-instability-non-reproducibility.md)

## 七、面试话术

### Q1: 你们项目有没有遇到 Agent 目标偏离的问题？

**回答要点**：
- 是的，Bug 5 就是典型案例。Supervisor LLM 在收到"查优惠券"请求时，错误地分配了 orderAgent 和 walletAgent。
- 根因是 LLM 的语义近似性混淆 + 助人偏差。模型看到一个电商请求就倾向于"多做事"。
- 我们的解决方案是方案 B：放弃 LLM 分解，改为由 intentRouter 做确定性单意图分类。Supervisor 不再调用 LLM，只做 round 计数器。
- 这样从根本上消除了编排层的 LLM 决策，目标偏离问题不再出现。

### Q2: 大量工具时 LLM 选错工具怎么处理？

**回答要点**：
- 当前每个 Agent 只有 3-7 个工具，选错概率较低。
- 我们的设计是按 Agent 分组工具，而不是把所有工具放在一个 Agent 里。这样 LLM 只需要从一个较小的工具集里选择。
- 如果未来工具扩展到 15+，我们会考虑工具分类描述、分层选择策略、以及工具调用的前置验证步骤。

### Q3: 你们的 Agent 执行过程可观测吗？

**回答要点**：
- 当前通过 testChat API 返回完整的 allAgentSteps 日志，包含每个节点的执行结果。
- 生产环境缺可视化仪表盘，这是我们下一步要完善的。
- 另外实时展示 Agent 思考过程（通过 SSE 流式）也还在 TODO 列表中。

### Q4: ReAct Agent 会有死循环问题吗？

**回答要点**：
- LangGraph 的 createReactAgent 内部有基本的循环控制。
- 我们在编排层有 supervisorRound 上限 3 轮的保护。
- 但单个 Agent 内部的 ReAct 循环没有最大步数限制，这是我们知道的风险点。后续会添加最大工具调用次数保护。
