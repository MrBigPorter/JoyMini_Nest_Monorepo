# 60. 企业级文档解析质量保障体系

> **架构分析**: 企业如何保证 PDF 解析和切片的内容一致性与完整性  
> **日期**: 2026-07-09  
> **状态**: 架构设计完成 — 见 [61-Enterprise-Parse-QA-Implementation-Plan.md](61-Enterprise-Parse-QA-Implementation-Plan.md) 实施

---

## 一、问题域

文档解析的质量保障有两个层面:

```
层面 A: 完整性 (Completeness)    层面 B: 正确性 (Accuracy)
文档内容有没有丢？                提取的数据对不对？

"看起来像一篇文章"               "数据和原文一模一样"
    盲审 (No-Reference)              有参照对比 (Reference-Based)
    只看文本本身                     需要对比原文
```

当前盲审方案（LLM 只看提取文本）只能回答**完整性**问题，无法回答**正确性**问题。

## 二、三种企业级验证方案

### 方案一: 多模态比对 (最精准)

**原理**: 将 PDF 每页转为图片，多模态 LLM 同时看图片和提取文本，逐页比对。

```
PDF 文件
    ├─ 转图片 (page1.png, page2.png, ...)
    └─ Unstructured 解析 → 提取文本

多模态 LLM (GPT-4o/Gemini):
  输入: page1.png + 提取文本第1段
  判断: 文本与图片内容是否一致？表格是否串行？
  输出: accuracy_score, discrepancies[]
```

| 优势 | 劣势 |
|:-----|:------|
| 最准确，能发现表格串行/漏字 | 需要多模态 LLM，成本高 |
| 可定位到具体页码 | PDF 转图片 + API 调用成本高 |
| **行业标准做法 — 作为定期审计** | 不适合每天大量文档实时处理 |

### 方案二: 双引擎交叉验证 (日常主力)

**原理**: 用两个不同内核的解析引擎分别解析同一 PDF，LLM 对比两个结果的差异。

```
PDF 文件
    ├─ 引擎 A: Unstructured (OCR/表格/多栏)
    └─ 引擎 B: pdf-parse (文本流)

LLM (DeepSeek):
  输入: 引擎A输出 vs 引擎B输出
  判断: 哪些地方不一致？哪个更合理？
  输出: best_result, discrepancies[], quality_score
```

| 优势 | 劣势 |
|:-----|:------|
| 纯文本处理，DeepSeek 可用 | 两个引擎同时翻车时无法发现 |
| 已有双引擎架构，改造成本低 | 额外 50% 解析时间 |
| 成本低，适合每日大量文档 | |

### 方案三: 启发式规则检查 (前置过滤器)

**原理**: 不依赖 LLM，通过统计规则自动检测明显问题。

```typescript
interface HeuristicChecks {
  // 截断检测: 末尾是否是完整句子
  truncation: boolean;
  
  // 字符比: 提取文本 / 文件大小
  retentionRate: number;
  
  // 乱码检测: 非标准字符比例
  encodingIssues: boolean;
  
  // 实体孤岛: 孤立数字/符号
  orphanEntities: boolean;
}
```

| 优势 | 劣势 |
|:-----|:------|
| 零 API 成本 | 只能发现明显问题 |
| 毫秒级完成 | 无法发现语义错误 |
| 可作为前置过滤器 | |

## 三、企业级分层架构

> **核心原则**: 不是三选一，而是三层叠加。

企业实际做法是 **分层验证**，不同层次解决不同问题：

```
上传 PDF
    │
    ▼
┌─────────────────────────────────────┐
│ Layer 1: 启发式规则 (Heuristic)      │ ← 毫秒级，零成本
│  检查: 截断/字符比/乱码/空内容       │
│  结果: PASS → 继续  |  FAIL → 标记   │
└─────────────────────────────────────┘
    │ PASS
    ▼
┌─────────────────────────────────────┐
│ Layer 2: 双引擎并行 + LLM Diff      │ ← 秒级，DeepSeek
│  引擎A: Unstructured                │
│  引擎B: pdf-parse                   │
│  LLM对比 → 选最优 + quality_score   │
└─────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────┐
│ Layer 3: 入库 → 切片 → 向量化       │
│  同时: quality_score 存入数据库      │
└─────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────┐
│ Layer 4: 按需多模态深度检查          │ ← 仅在 L2 评分 < 4 时触发
│  触发条件: LLM Diff score < 4       │
│  将 PDF 转图片 → GPT-4o 逐页比对     │
│  确认具体问题位置 → 标记待审查        │
└─────────────────────────────────────┘
```

### 每层职责

| 层次 | 检测能力 | 成本 | 触发条件 | 适用场景 |
|:-----|:---------|:-----|:---------|:---------|
| L1 启发式 | 截断、乱码、空内容 | $0 | 每次上传 | 快速过滤明显问题 |
| L2 双引擎+LLM | 文本一致性、结构保留 | DeepSeek tokens | 每次上传 | 日常主力质量门禁 |
| L3 入库存储 | quality_score 持久化 | $0 | 每次上传 | 追踪趋势、标记异常 |
| L4 多模态检查 | 表格串行、漏字、排版 | GPT-4o $ | L2 评分 < 4 时触发 | 深度验证可疑文档 |

### 为什么需要全部四层？

| 只做… | 能发现… | 不能发现… |
|:------|:---------|:-----------|
| L1 启发式 | 文件损坏、编码错误 | 语义错误、表格串行 |
| L2 双引擎+LLM | 大部分语义差异 | 两个引擎同时翻车 |
| L1+L2+L3 | 日常 95% 问题 | 偶尔的解析盲区 |
| **+L4 多模态** | **可疑文档的深度验证** | — |

## 四、LLM Diff 审计 Prompt

```typescript
const prompt = `
你是一个文档解析质量审计专家。
同一个 PDF 文件经过两个不同引擎解析，产生了以下两段文本。

请对比分析:

1. 内容完整性: 哪个引擎提取的内容更完整？
2. 数据准确性: 数字、日期、金额是否一致？
3. 结构保留: 表格/列表结构是否合理？

${engineAResult}

引擎 B 输出:
${engineBResult}

返回 JSON:

  "selected": "A" | "B",
  "score": 1-5,
  "reasoning": "选择引擎A的原因...",
  "issues": ["引擎B表格数据有串行"],

`
```

## 五、关于方案一的正确认知

**之前说"多模态不适合我们"是不准确的。**

1. **不适合作为日常每文档检查** — 因为成本高、速度慢
2. **必须作为深度验证手段** — 因为只有多模态能真正验证解析正确性，尤其是表格/多栏排版
3. **触发时机** — 不是每周定时跑，而是在上传流程中按需触发：
   - L2 (双引擎+LLM) 评分 >= 4 → 直接通过，不调多模态
   - L2 评分 < 4 → 自动触发多模态深度检查
   - 这样可以做到"好东西不浪费，有疑问才深查"
