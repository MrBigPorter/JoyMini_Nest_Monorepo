# 统一客服后端架构重设计 — Spec Coding

## 背景：为什么现有架构不对

当前有**两套完全独立**的客服系统：

```
                    AI 客服                             人工客服
  ───────────────────────────────────────────────────────────────
  协议     SSE 流（/ai/customer/chat）             Socket（/events）
  对话类型 ConversationType.AI                    ConversationType.SUPPORT
  对话ID   硬编码 ai_chat:{userId}                 动态创建，businessId 匹配
  入口     POST /ai/customer/chat                 GET /chat/business?businessId=xxx
  消息存储 AiMemoryService → ChatMessage          ChatService → ChatMessage
  UI       ChatPage 简化版（无语音/图片/呼叫）    ChatPage 完整版
```

两个系统不互通：AI 处理不了时只能让 LLM 在回复中写 "请联系人工客服"，没有实际的转接机制。

## 目标：一个客服

用户从任何入口（订单详情、个人中心、充值页、消息列表）点"客服/帮助" → 进入同一个客服对话 → 后端先走 AI 处理 → AI 搞不定无缝转人工。用户全程无感知"现在是 AI 在回"还是"人工在回"。

```
  入口（订单/个人中心/充值页/消息列表）
          │
          ▼
  CustomerServiceHelper.startChat()
          │
          ▼
  GET /chat/business?businessId=xxx
          │
          ▼
  创建/复用 ConversationType.SUPPORT 对话
          │
     ┌────┴────┐
     │  AI 处理  │ ← SSE 流式回复（逐字出现）
     │         │
     └────┬────┘
          │
     ┌────┴────┐
     │ 转人工   │ ← AI 判断搞不定，同一对话切 Socket
     │         │
     └────┬────┘
          │
     人工客服回复（Socket）
```

## 改动方案

### 1. Conversation 类型说明

不要删除 `ConversationType` 的类型区分。`Conversation` 模型已经有 `type` 字段：

```prisma
enum ConversationType {
  GROUP     // 用户创建的群聊
  DIRECT    // 私聊
  SUPPORT   // 客服对话（人工客服）
  BUSINESS  // 自动业务群（拼团等）
  AI        // AI 客服对话
}
```

核心原则：
- **所有客服对话统一用 `ConversationType.SUPPORT`** — 不管是 AI 在处理还是人工在处理，类型不变
- **Flutter UI 统一渲染** — SUPPORT 类型对话使用完整聊天界面，不区分 AI/人工
- **通过 `senderId` 区分消息来源** — AI 消息的 senderId 是机器人用户，人工消息的 senderId 是管理员用户
- **转人工不切换类型** — 同一对话、同一类型，只是数据源从 SSE 切到 Socket

```typescript
async createOrGetAiConversation(
  userId: string,
  conversationId?: string,  // ← 新增
): Promise<{ conversationId: string; threadId: string }> {
  if (conversationId) {
    // 校验该对话存在且类型为 SUPPORT
    const conv = await this.prisma.conversation.findUnique({
      where: { id: conversationId },
      select: { id: true, threadId: true, type: true },
    });
    if (!conv || conv.type !== 'SUPPORT') {
      throw new BizException('Conversation not found or not a support chat');
    }
    // 确保 threadId 存在
    if (!conv.threadId) {
      const threadId = crypto.randomUUID();
      await this.prisma.conversation.update({
        where: { id: conversationId },
        data: { threadId },
      });
      return { conversationId, threadId };
    }
    return { conversationId, threadId: conv.threadId };
  }
  // 无 conversationId → 创建新 SUPPORT 对话（兼容旧逻辑）
  // ...
}
```

### 3. AI → 人工转接机制

#### 3.1 整体流程

```
  User: CustomerServiceHelper.startChat()
          │
          ▼
  GET /chat/business?businessId=official_platform_support_v1
          │
          ▼
  创建/复用 ConversationType.SUPPORT 对话（conversationId = "cuid_xxx"）
  两个成员：userId（用户）+ botUserId（SupportChannel 关联的机器人）
          │
          ▼
  后端检测到新 SUPPORT 对话 → 自动触发 AI 处理
  → SSE 流逐字回复用户（senderId = botUserId 的机器人）
          │
     ┌────┴────┐
     │  正常结束  │ → SSE done，对话完成
     └────┬────┘
          │  转人工
     ┌────┴────┐
     │  AI 判定  │ → SSE 发 transfer 信号
     └────┬────┘
          │
          ▼
  后端：事件触发通知管理员
  CHAT_EVENTS.SUPPORT_CONVERSATION_STARTED
  → 管理员在后台看到该对话
  → 管理员开始回复（Socket，senderId = 管理员 ID）
          │
          ▼
  Flutter：收到 transfer → 断开 SSE
  → 加入 Socket 房间
  → 同一 conversationId，后续消息来自 Socket
  → 渲染管理员回复的消息
```

#### 3.2 消息来源区分

不依赖 `ConversationType` 判断 AI/人工，而是通过 `ChatMessage.senderId`：

| 消息来源 | senderId | 传输协议 | 消息存储方式 |
|---------|----------|---------|------------|
| AI 回复 | SupportChannel.botUserId | SSE（逐字流） | SSE done 后一次写入 ChatMessage |
| 人工回复 | 管理员的 userId | Socket | 实时写入 ChatMessage |
| 用户消息 | 用户的 userId | HTTP POST / Socket | POST 时写入 / Socket 写入 |

Flutter 渲染时判断 `senderId === currentUserId` 来决定"我的消息"还是"对方消息"，不区分 AI 还是人工。

**历史记录展示**：AI 阶段和人工阶段的消息都写在同一张 `ChatMessage` 表、同一 `conversationId` 下。Flutter 拉历史时 `GET /chat/messages?conversationId=xxx` 一次返回全部消息，按 `createdAt` 排序。用户看到的是一条完整的客服对话记录，连续、统一，无法区分哪段是 AI 回的、哪段是人工回的。

#### 3.3 AI 判定转人工的触发条件

AI 在以下情况启动转人工：

1. **LLM 主动判断** — 在 agent prompt 中加入规则：用户情绪激动、要求找人工、涉及敏感操作时返回 `transfer_to_human: true`
2. **工具调用失败** — orchestrator 检测到多次 tool call 失败（如查余额服务不可用）
3. **用户手动触发** — 聊天界面有一个"转人工"按钮

#### 3.5 后端通知管理员


#### 3.6 管理员回复 → Flutter 收到

已有完整链路，无需修改：

1. 管理员在后台发消息 → `AdminChatService.sendMessage()`
2. → 写入 ChatMessage（`senderId = adminUserId`）
3. → Socket dispatch `chat_message` 事件到 conversation 房间
4. → Flutter 收到 Socket 事件 → 追加到消息列表

### 6. Flutter ChatPage 融合

**核心逻辑：默认 AI，按需转人工。**

```
  ChatPage 打开
      │
      ▼
  默认连接 SSE（AI 处理）
      │
  ┌───┴──────────────┐
  │  done → AI 结束   │
  │  transfer → 切 Socket  │
  └──────────────────┘
```

**ChatPage** (`chat_page.dart`)

不再区分 `isAiChat` 模式。`ConversationType.SUPPORT` 对话统一使用同一套完整聊天界面：

- 相同的 app bar（头像 + 名称来自 SupportChannel，无"AI"标签）
- 相同的输入栏（支持文字 + 图片 + 语音）
- 相同的消息气泡渲染（通过 `senderId` 区分"我"和"对方"）
- AI 回复时打字机效果保留（逐字出现），但渲染为普通消息气泡样式
- 后台处理时不显示"正在查询..."状态文字

**ChatViewModel SSE ↔ Socket 切换** (`chat_view_model.dart`)

```typescript
enum ChatDataSource { ai, human }

class ChatViewModel extends StateNotifier<ChatState> {
  ChatDataSource _source = ChatDataSource.ai;
  SseClientV2? _sseClient;         // AI 阶段
  StreamSubscription? _socketSub;   // 人工阶段

  Future<void> connect(String conversationId) async {
    // 默认先走 AI（SSE）
    await _startSse(conversationId);
  }

  void _onSseEvent(SseEvent event) {
    switch (event.type) {
      case SseEventType.token:
        _appendAiMessage(event.data['content']);
        break;
      case SseEventType.transfer:   // ← 新增
        _switchToSocket(event.data['conversationId']);
        break;
      case SseEventType.done:
        // AI 回复完成，仍保持 Socket 监听（人工可能后续加入）
        _listenSocket(conversationId);
        break;
    }
  }

  void _switchToSocket(String conversationId) {
    _source = ChatDataSource.human;
    _sseClient?.dispose();
    _socket.emit('join_chat', { conversationId });
  }

  /// 发送消息 — 根据当前数据源选择通道
  Future<void> sendMessage(String text) async {
    if (_source == ChatDataSource.ai) {
      await _sendViaSse(text);      // POST /chat → SSE
    } else {
      await _sendViaSocket(text);   // Socket send_message
    }
  }
}
```

### 8. LLM Prompt 转人工规则

在 agent prompt 中加入转人工的判断规则：

```typescript
// orchestrator.config.ts 或 agent prompt
const TRANSFER_RULES = `
## 转人工规则
在以下情况，你必须在回复中标记 require_human: true：
1. 用户明确要求"找人工"、"我要投诉"、"转人工"
2. 用户情绪激动或使用威胁性语言
3. 涉及账号封禁、大额退款、安全验证等需要人工审核的操作
4. 连续 3 次工具调用均失败
5. 用户提出的需求不在你的业务范围内且无法转给其他 Agent

当 require_human = true 时，AI 停止执行后续 agent，
回复用户"已为您转接人工客服，请稍等..."，
系统会自动发送 transfer 信号。
`;
```

## 迁移步骤

### Phase 1：后端打通（AI 接入 SUPPORT 对话）
1. `ChatStreamDto` 加 `conversationId` + `entryPoint` + `metadata` 字段
2. `AiMemoryService` 支持传 `conversationId`（不再硬编码 `ai_chat:{userId}`）
3. `AiCustomerService` / `AiCustomerController` 透传 `conversationId`
4. Graph State 加 `entryPoint` / `entryMetadata` / `transferToHuman` 字段
5. 意图路由利用 `entryPoint` 提权

### Phase 2：转接机制
6. SSE 新增 `transfer` 事件类型
7. Orchestrator + prompts 加入转人工判断规则
8. AiCustomerService 触发 `CHAT_EVENTS.SUPPORT_CONVERSATION_STARTED`

### Phase 3：入口改造
9. `CustomerServiceHelper.startChat()` 支持 entryPoint + metadata
10. 各页面调用处传入上下文

### Phase 4：Flutter UI 融合
11. `SseEventType` 加 `transfer`
12. ChatPage 去掉 `isAiChat` 分支 + 去掉 AI 简化版 UI
13. ChatViewModel 支持 SSE → Socket 切换（收 + 发双通道）
14. `conversation_provider.dart` 去掉强制注入的 AI 条目
