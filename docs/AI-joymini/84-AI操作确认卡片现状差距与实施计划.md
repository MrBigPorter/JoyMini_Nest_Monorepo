## 1. 背景

#83 是 AI 操作确认卡片的**设计稿**，描述了理想流程：`LLM 提取参数 → 不调 tool → 前端卡片展示 → 用户点确认 → 后端执行`。

本文档记录 **2026-08-03 实测验证** 后发现的"设计与实现差距"，以及在此基础上的实施计划。
83 里的设计目标是正确的（结构化卡片 = 用户"对不对"的核对入口，符合 FinTech 提现行业标准），
但**当前实现没有闭环**，且有资金风险。

## 3. 现状差距分析（实测验证）

### 3.1 当前真实链路

```
用户给全信息 → wallet agent 调 applyWithdraw
  → ❌① runAgentLoop 已真实执行提现（agent-runner.ts 直接 await tool.invoke()）
  → orchestrator 拦截 → pendingConfirm → AI_CONFIRM 事件
  → Flutter 渲染卡片（AiConfirmCard 已存在 ✅）
  → 用户点确认 → Flutter 直接调业务 API（不走 confirmToken）
  → ❌② 但 summary 缺 channelId/account/accountName → 提现确认会崩/失败
```

### 3.2 差距清单（按严重程度）

| # | 严重度 | 差距 | 证据 |
|---|--------|------|------|
| 1 | 🔴 资金 | **拦截在写操作执行之后**：`runAgentLoop` 循环里 `await tool.invoke()` 已真实执行 `applyWithdraw`，orchestrator 才检查 `lastToolCallInfo` 拦截。卡片出现时提现已提交 → 用户再点卡片确认 = **双执行** | `graph/agents/agent-runner.ts`（`await (foundTool as any).invoke(...)`）；`orchestrator.node.ts` 拦截段 |
| 2 | 🔴 资金 | **summary 字段缺失/不匹配**：`buildConfirmSummary` 提现只生成 `{amount, channel}`，缺 `channelId`、`account`、`accountName`；且 key 用 `channel`，Flutter 读 `channelId` | `orchestrator-utils/confirm-utils.ts` |
| 3 | 🔴 前端 | **Flutter `confirmAction` 提现会崩/失败**：读 `params['channelId']` 是 null → `(null as num).toInt()`；account/accountName 为空串 | Flutter `lib/core/api/lucky_api.dart` `confirmAction()` |
| 4 | 🟡 时序 | **wallet DB workflow 让 agent 先文字问** "Shall I proceed?"，用户确认后才调 `applyWithdraw` → 卡片永远晚一步（实测"帮我取款"只弹文字、不弹卡片） | DB `knowledge_prompt_versions` wallet-agent v1 `domainRules` |
| 5 | 🟡 安全 | **confirmToken 是死代码**：`AiActionConfirmService.generate()` 发 token，但无任何 controller 消费；Flutter 也完全忽略它，直接调业务 API | `ai-action-confirm.service.ts`；Flutter `chat_view_model.dart` `confirmAction()` |
| 6 | 🟡 合规 | **OTP 被跳过**：#83 §6.3 决定"本轮先跳过 OTP"，但本轮新决策要求**卡片 + OTP 双保险** | #83 §6.3 |
| 7 | 🟢 UX | **卡片展示不全**：提现卡片只显示金额+渠道，账号/手续费/到账金额都没有，用户无法完整核对 | Flutter `ai_confirm_card.dart` `_paramEntries` |

### 3.3 已存在且可复用的资产

- ✅ Flutter 卡片 UI 完整：`AiConfirmCard` widget + `ConfirmCardStatus` 状态机（pending/loading/success/failed/expired/cancelled）+ `AiActionModel`
- ✅ 后端拦截骨架：`CONFIRM_REQUIRED_TOOLS` + `pendingConfirm` state + `routeConfirm` 发 `AI_CONFIRM` 事件
- ✅ 写操作工具本身有安全兜底（`applyWithdraw` 内置 KYC/余额/30s 幂等检查）

## 5. 目标流程（正常企业模式）

```
用户: "取款 100 到 GCash 0917xxxx"
  │
  ▼
wallet agent 收集信息（聊天）→ 信息齐 → 触发 applyWithdraw 意图
  │
  ▼
orchestrator 拦截【执行前】→ 用完整参数生成卡片（金额/渠道/账号/手续费/到账）
  │
  ▼
AI_CONFIRM 事件 → Flutter 渲染提现确认卡片
  │
  ├── 用户点 [确认] → 后端校验 token → requestWithdrawOtp 发验证码
  │     → 用户输 OTP → verifyWithdrawOtp → applyWithdraw 执行
  │     → AI_ACTION_RESULT 返回结果
  │
  └── 用户点 [取消] / 60s 过期 → 不执行，记录日志
```

关键不变式：**写操作只有一次执行点（用户确认之后），服务端绝不先执行。**

## 8. 决策选项

- **选项 A · 完整方案**（6 天）：P0+P1+P2 全做，一次到位。
- **选项 B · 轻量上线**（2 天）：只做 P0 —— 拦截前置 + summary 补全 + Flutter 对齐，让卡片确认能**安全执行**；OTP/token/展示后续迭代。

**建议**：先 **B** —— 当前双执行隐患比"没卡片"更危险，优先止血；再补 OTP 达到双保险。
