## 0. 一页结论

功能完成度已经不低，但**生产工程化程度不足**。按真实企业上线标准，当前状态：

| 维度 | 评估 | 说明 |
|---|:--:|---|
| 功能 / 产品闭环 | ~80% | 9 意图、8 Agent、35 工具、转人工、确认卡片、Flutter 全链路 |
| 生产工程化 | ~45% | 鉴权、资金一致性、可观测性、评测、部署形态均有缺口 |
| 运维 / SRE | ~20% | 单实例、无 SLO、告警只写日志、无故障演练 |
| 治理 / 合规 | ~15% | 无审计日志、无 AI 披露、无数据留存策略 |

**结论：**
- ✅ 可以做**内部员工试点、只读灰度**
- ⚠️ 可以做**外部用户只读 + 非资金写操作灰度**（需先修 P0-1/2/4/5）
- ❌ **不能开放资金写操作、不能宣称生产可用**（P0-3 已修，P0-4 部分修复——代码路径已收口、真实短信供应商待接入，P0-1 / P0-5 未修）

## 3. P0 详细分析

### P0-1 Socket.IO 会话越权

**现状**
- `handleConnection` 仅在存在 token 时解析身份，**无 token 不断开**（`events.gateway.ts:83-141`）。
- `handleJoinChat` 不查 `chatMember`，拿到任意 `conversationId` 即 `client.join(room)`；`userId` 为 null 也继续 join（`:249`、`:258`）。
- `handleSendMessage` 只校验 socket 上有 userId，不校验是否为该会话成员（`:314-366`），并会触发 FCM 与 AI。
- REST 拉历史是校验了成员的（`chat.service.ts:594+`），说明是 Socket 通道单独遗漏。

**影响**
- 任意登录用户可订阅任意会话，实时读取他人聊天内容。
- 未认证连接同样可进房窃听。
- 可向他人会话写消息、触发 AI、刷新 `lastMsgSeqId`。
- `AI_CONFIRM` 事件携带 `confirmToken` 并广播到会话房间（`ai-customer.service.ts:362-370`），进房即可获取。

**修复方案**
1. `handleConnection`：无有效 token 直接 `client.disconnect()`；连接时统一注入 `userId`、`role`。
2. 新增 `ChatService.assertMember(conversationId, userId)`，`join_chat` / `send_message` 必须先过。
3. `join_chat` 校验会话存在且成员有效；失败返回 error，不 join。
4. `send_message` 增加内容长度、type 白名单、会话状态校验。
5. 敏感事件（`AI_CONFIRM`）改为仅推送到 `user_${userId}` 私有房间，不广播到会话房间。

**验收**
- e2e：用户 A join 用户 B 的会话 → 拒绝；未认证连接 → 被断开。
- e2e：A 向 B 会话发消息 → 拒绝，且无消息落库、无 AI 触发。
- 房间成员数与 `chatMember` 一致。

### P0-2 AI 会话 IDOR

**现状**
`createOrGetAiConversation(userId, conversationId)` 仅校验 `conv.type === 'SUPPORT'`，**未校验 `userId` 是否成员**（`ai-memory.service.ts:68-90`）。随后复用该会话的 `threadId`，并允许 `finalizeAfterStream → publishAiReply` 写入该会话。

**影响**
- 攻击者传入受害者 `conversationId`，可让 LangGraph 载入受害者历史上下文（可被诱导复述）。
- AI 回复会写进受害者会话，形成消息注入与骚扰。

**修复方案**
1. 在 `createOrGetAiConversation` 中增加 `chatMember` 查询：`where: { conversationId, userId }`。
2. 校验失败抛 `ForbiddenException`，不返回 threadId。
3. 增加单测覆盖：非成员 / 不存在 / 非 SUPPORT / 正常成员四种路径。

**验收**
- 非成员请求被拒绝；成员请求正常；threadId 不可跨用户复用。

### P0-3 提现冻结余额不释放（资金）

**现状**
1. 申请提现时 `freezeCash`：`realBalance -= amount`、`frozenBalance += amount`，并写一条 `walletTransaction`（`wallet.service.ts:353-416`）。
2. 管理员审核通过：先把订单置 `PROCESSING`，调用 Xendit，成功后**直接把订单置 `SUCCESS`**（`finance.service.ts:321-379`，`:374`），**不处理钱包**。
3. Xendit 回调到达：`handlePayoutWebhook` 开头幂等判断，见 `SUCCESS` 直接 return（`client-wallet.service.ts:277-285`）→ **后续解冻 + `totalWithdraw` 累加的代码永不执行**（`:295-320`）。
4. 审核时 Xendit 调用失败：直接置 `FAILED`，**不解冻**（`finance.service.ts:350-368`）。
5. 定时任务把幽灵单置 `FAILED`：**不解冻**，注释写明“让财务手动处理”（`finance.task.ts:140-150`）。

**影响**
- 每笔成功提现都会在 `frozenBalance` 留下永久冻结金额，用户可用余额被吞。
- 失败单同样不解冻，需人工修数据。
- 审计时 `frozenBalance` 与提现单无法对齐，资金无法对平。
- 即使回调先到并正确解冻，审核的最终 `update` 仍会把状态覆盖为 `SUCCESS`，语义也不严谨。

**修复方案（状态机重写）**
1. 审核通过**只置 `PROCESSING`**，不置 `SUCCESS`；`SUCCESS` / `FAILED` 只能由回调或对账任务落定。
2. 统一一个 `settleWithdrawal(order, outcome)` 服务：
   - `SUCCESS`：`frozenBalance -= actualAmount`、`totalWithdraw += actualAmount`、流水置成功、订单置成功（同一事务）。
   - `FAILED`：解冻回 `realBalance`、写退款流水、订单置失败。
3. 幂等键从“订单状态”改为“结算流水是否已存在”，避免状态提前置位导致跳过。
4. 对账任务：按 Xendit 最终状态补偿，并输出差异报表。
5. 兼容检查：Xendit 返回 `PENDING` 时不得置 `SUCCESS`。

**验收**
- 单测：成功 / 失败 / 回调重复 / 回调先到 / 审核后到 五种路径，冻结余额最终为 0、`totalWithdraw` 正确。
- 对账脚本：任意时间点 `sum(冻结流水) == frozenBalance`。
- 手工回归：一笔提现从申请到回调全链路，钱包四个字段守恒。

**修复结果（2026-11-12，见 [#95](./95-提现冻结状态机-SDD.md)）**

- 审核通过只置 `PROCESSING`；`SUCCESS` / `FAILED` 只由 `WithdrawSettlementService.settleWithdrawal()` 写。
- 成功：`frozen − 毛额`、`totalWithdraw + 净额`；失败：`frozen − 毛额`、`real + 毛额` + 退款流水。
- 幂等靠"订单状态原子抢占"（`updateMany` + `notIn` 终态），重复回调/cron 重扫只结算一次。
- 补单任务区分「查无此单」与「查询异常」：后者跳过本轮，避免钱已打出却误退款。
- 单测 8 例覆盖：成功 / 终态幂等 / 并发抢占失败 / 失败解冻 / 冻结不足强扣 / 订单不存在 / 抢占条件 / 复用外部事务。
- **未做**：对账脚本与 `sum(冻结流水) == frozenBalance` 的定时校验，列入后续（#95 §8）。

### P0-4 生产 OTP 不可用且日志泄露

**现状**
- `OTP_PEPPER = process.env.OTP_PEPPER || ''`（`otp.service.ts:13`），未配置时哈希退化为 `sha256(phone:code:)`。
- `console.log('[OTP]==> ... code=...')` 在所有环境执行（`:75`），生产日志明文含验证码。
- 生产分支 `// TODO: 生产环境在这里调用供应商 SDK`（`:81`），实际不发短信。
- `isProd` 仅由 `NODE_ENV === 'production'` 决定（`:20`）；配置错误时会走 dev 固定码。
- `requestIp: null`，无法做 IP 维度风控。

**影响**
- 生产用户收不到验证码，提现确认流程不可用。
- 能看日志的人可直接登录 / 提现。
- pepper 为空时 6 位码可离线枚举。

**修复方案**
1. 接入短信供应商，生产分支发真实短信；失败必须抛错并记录供应商返回码。
2. 删除/降级 OTP 明文日志：生产只记录 `phone` 掩码 + 请求 ID。
3. 启动时校验：`NODE_ENV=production` 时 `OTP_PEPPER` 必填且长度 ≥ 16，否则拒绝启动。
4. 写入 `requestIp`、设备号，增加手机号 + IP 双维度限流。
5. 生产禁止返回 `devCode`。

**验收**
- 生产环境无 `[OTP]==>` 明文；未配 pepper 启动失败。
- 发送失败有明确错误码与告警；同一手机号 60s 内二次请求被拒。

**修复结果（2026-11-12，详见 [#96](./96-OTP生产化-SDD.md)）**

| 方案项 | 状态 | 落地 |
|:--:|:--:|---|
| 1. 接入短信供应商 | 🟡 | 抽出 `SmsProvider` 接口 + 工厂注册；生产用 `UnconfiguredSmsProvider` **显式抛错**，接入时只换实现 |
| 2. 删除/降级明文日志 | ✅ | 删除 `console.log`；开发环境由 `ConsoleSmsProvider` 打印（仅 `NODE_ENV=development`） |
| 3. 启动校验 pepper | ✅ | `main.ts`：生产环境 `OTP_PEPPER` 缺失或 < 16 字符直接拒绝启动 |
| 4. 写入 `requestIp` | 🟡 | 已写入数据库；**尚未用于限流** |
| 5. 生产禁止返回 `devCode` | ✅ | `isDev` 判据 fail-closed，只有 `development` 才返回 |

顺带修掉两处未登记的逻辑缺陷：`verifyTimes` 每次尝试被 +2（5 次实为 3 次）、`verify` 查询用未 trim 的 `phone` 导致带空格时查不到单。
发送状态改为 `PENDING → send → SENT / FAILED`，不再抢在实际发送之前写「已发送」。

**验证**：`tsc --noEmit` 0 error；全量 308 passed（3 例失败为 `auth` / `flash-sale` 已知过期 suite）。

**仍缺**：真实供应商账号 → 生产调用会抛 `NotImplementedException`；pepper 两个读取时机的隐患（#87 N-19）。

### P0-5 领券并发超卖

**现状**
`claimCoupon` 注释写“悲观锁”，实际是 `findUnique`（无锁）→ 判断 `issuedQuantity >= totalQuantity` → 判断个人领取数 → 无条件 `increment`（`coupon.service.ts:71-150`）。`UserCoupon` 无 `@@unique([userId, couponId])`（`schema.prisma:843-868`）。

**影响**
- 并发下可突破总库存与个人限领；兑换码可枚举（`:151-168` 无尝试限制）。

**修复方案**
1. 扣减改为原子条件更新：
   `updateMany({ where: { id, issuedQuantity: { lt: totalQuantity } }, data: { issuedQuantity: { increment: 1 } } })`，`count === 0` 即售罄。
2. 个人限领在事务内用 `SELECT ... FOR UPDATE` 或 Redis 分布式锁；或加唯一约束 + 计数表。
3. 兑换码增加失败次数限制（Redis 计数 + 冷却）。
4. 补并发测试：100 并发抢 10 张，最终 `issuedQuantity === 10`。

**验收**
- 并发测试无超卖；同一用户并发领取不超过 `perUserLimit`。
