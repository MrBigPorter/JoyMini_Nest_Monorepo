## 1. 岗位解构

### 1.1 职责 → 权重

| 职责簇 | 具体条目 | 权重 | 说明 |
|---|---|:--:|---|
| **业务与状态机** | SOP 流程引擎、状态流转、业务决策规则、话术表达 | 30% | 岗位的骨架 |
| **LLM 应用** | 意图理解、提示词、结构化输出、RAG、知识库、话术库 | 25% | 不是模型研究，是工程化 |
| **生产可靠性** | 幂等、重试、死信、Outbox、并发竞态、崩溃恢复、PG 行锁 | 20% | 和业务强耦合 |
| **可观测与验证** | ELK 定位、单元/集成测试、离线回放、正确率评估、成本控制 | 15% | **区分"写过 demo"和"能上线"的地方** |
| **工程协作** | Git、代码审查、Python 分析脚本、Claude Code 并审产出 | 10% | 已明确写进要求 |

### 1.2 这不是什么岗位

- 不是从零搭系统（他们要接手一个已经在跑的系统）
- 不是调模型（唯一涉及模型的词是"温度"和"成本"）
- 不是前端/全栈（没有任何前端要求）
- 不是研究岗（"离线回放""正确率评估"指的是工程指标，不是论文）

| Claude Code / Codex 并审产出 | 正在使用 | ✅ **强项** | 写进简历自我评价 |
| 20–25K 远程 | 低于上一个 30–50K 岗 | — | 定位不同，可作备选 |

### 2.1 关于 C# 的诚实判断

JD 把 C# 放在第一条，但**其余全部要求都是通用的**（PG、MQ、LLM、Python）。两种可能：

- **悲观**：现有系统是 .NET，要人接着维护 → HR 硬筛
- **乐观**：技术栈声明，不是能力测试 → 技术面认"同等复杂度后端"

**投递前必须问清**：「AI 客服服务的代码库是什么语言？.NET 占比多少？入职后主要写 C# 还是 AI 服务？」

这个答案决定：
- 若 .NET 为主 → 你要评估是否愿意长期改 C#（可能 50% 时间不在做 AI）
- 若 AI 服务独立 → C# 只是老系统，不影响主线

## 7. 面试素材（做完即用）

### 7.1 三个必讲的故事

每个按 **问题 → 判断 → 改动 → 验证** 四段讲，第四段是关键（JD 要"可复现的验证证据"）。

**故事 1 — 提现冻结余额永远不释放**
- 问题：审核通过直接置 SUCCESS，回调幂等提前 return，解冻代码永不执行
- 判断：状态机把"业务终态"和"资金结算"混在一起，幂等键选错（选了订单状态）
- 改动：审核只置 PROCESSING；统一 `settleWithdrawal`；幂等键改为"结算流水是否存在"
- 验证：五种路径单测（成功/失败/重复回调/回调先到/审核后到），冻结余额恒为 0

**故事 2 — "麻烦"被判成人身攻击，AI 永久失联**
- 问题：关键词表含 `'烦'`，用 `includes` 子串匹配；转人工后 `handlerId='awaiting_human'` 且每轮刷新时间戳，AI 永不恢复
- 判断：关键词匹配没有词边界概念；状态机的"超时"被实现成"刷新计时"
- 改动：词边界匹配 + 情绪强度分级；转人工改为可超时回收的状态
- 验证：回放集里该类 case 转人工率从 X% 降到 Y%

**故事 3 — 中文问题打进 RAG，关键词层全废**
- 问题：`replace(/[^\w\s]/g, ' ')` 把中文全部清空；Layer 2 SQL 占位符从 `$2` 起但只推 n 个参数，必然报错被 catch 吞掉
- 判断：英文 tokenizer 直接套中文场景；错误被 catch 静默吞掉，导致"降级"看起来正常
- 改动：中文分词 + 占位符对齐 + catch 里计数告警（降级必须可观测）
- 验证：中文 query 的 Layer 2 命中数从 0 到 N
