## 1. 为什么需要它

已有的 jest 用例（13 个 suite / 187 条）覆盖的是**函数逻辑**：
`detectTransferRequest('我要转人工')` 返回什么、`dispatchToConversation()` 发几个房间。

但它们覆盖不了一整条链路：

```
POST /chat/message
  → ChatService.sendMessage
  → EventEmitter: AI_MESSAGE_REQUESTED
  → AiMessageListener（在这里才生成 traceId）
  → LangGraph: intent → orchestrator → agent → 回复
  → publishAiReply（写 ChatMessage）
  → EventsGateway.dispatchToConversation（会话房间 + 私有房间）
  → Socket → Flutter 端
```

N-9 就是这么漏掉的：`publishAiReply` 只发会话房间，单测里 `dispatch()` 被 mock 掉，
测试全绿，但用户断线重连后一条 AI 回复都收不到。**只有真的发一条消息、真的看日志才会暴露。**

这个脚本把「手动发一条消息 → 翻日志 → 肉眼核对」固化成一条命令。

## 2. 它做了什么

1. **签 token**：在 `lucky-backend-dev` 容器里用 `JWT_SECRET` 临时签发一个 client JWT。
   不碰密码、不发 OTP、不打印密钥。
2. **准备会话**：复用或新建一条专用 SUPPORT 会话（名字 `【AI自测】`），
   成员 = 最近活跃的真人用户（`users.is_robot = false`）+ AI 占位账号（`is_robot = true`）。
3. **逐条重置**：每个场景发送前执行

   ```sql
   UPDATE "Conversation"
   SET handler_id = NULL,             -- 转人工后 AI 会被跳过，必须清掉
       handler_assigned_at = NULL,
       thread_id = gen_random_uuid()  -- MemorySaver 换 thread，历史 / repeatCount 归零
   WHERE id = '<自测会话>';
   ```

   这样场景之间互不污染，且每个场景都是"干净记忆"。
4. **发消息 → 认领 traceId**：发送后从后端日志里找 `stage=chat.start` 且
   `conversationId` 匹配、`ts >= 发送时间`、且没被前面用例用过的 `traceId`。
5. **等收尾**：轮询同一 `traceId` 的 `stage=chat.done`，超时（默认 150s）算失败。
6. **断言四项**：
   - `chat.done.transferred` 是否符合预期
   - `intent` 事件的意图（转人工场景应为 `transfer`）
   - `transfer` 事件的 `reason`（`explicit_request` / `negative_sentiment` / `repeated_attempts`）
   - `[DispatchFallback] Room: <会话>, private rooms: N` 是否出现且 `N >= 2`（N-9 双通道）

   故障注入场景（§4.1）走的是**失败路径**：没有 `chat.done`，改等 `chat.error`，
   断言换成「兜底话术落库 / `handler_id=awaiting_human` / `transfer{source:fallback}`」。

## 3. 怎么跑

```bash
# 前置：make up-db / make up-backend（或 docker ps 能看到 lucky-db、lucky-backend-dev）
bash scripts/ai-e2e-smoke.sh                  # 全部默认场景（约 5~10 分钟，逐条串行）
bash scripts/ai-e2e-smoke.sh 转人工           # 只跑名字里含"转人工"的场景
WAIT_SECONDS=180 bash scripts/ai-e2e-smoke.sh # LLM 慢的时候放宽
WITH_REPEAT=1 bash scripts/ai-e2e-smoke.sh    # 追加"连续重复 4 次才转人工"（很慢）
WITH_FAILURE=1 bash scripts/ai-e2e-smoke.sh   # 追加"模型故障降级"（写 Redis 故障开关，见 §4.1）
```

可选环境变量：

| 变量 | 默认 | 说明 |
|---|---|---|
| `TEST_USER_ID` | 最近加入会话的真人用户 | 指定测试用户 |
| `TEST_BOT_ID` | `is_robot = true` 的账号 | AI 占位账号 |
| `TEST_CONVERSATION_ID` | 无（自动建 `【AI自测】`） | 指定已有会话，不再新建 |
| `TAIL_LINES` | 4000 | 每次取多少行日志（见下方"坑"） |
| `WAIT_SECONDS` | 150 | 单条 chat.done 等待上限 |
| `REDIS` | `lucky-redis` | Redis 容器名（故障注入用；密码从容器内 `REDIS_PASSWORD` 读取） |

退出码：全部通过返回 `0`，任一场景失败返回 `1`，可直接接 CI。

## 4. 场景矩阵

| 场景 | 输入 | 期望意图 | 期望转人工 | 原因 | 覆盖的问题 |
|---|---|---|---|---|---|
| 闲聊问候 | 你好 | `general` | ❌ | — | 基线：正常链路能跑通 |
| 知识问答 | 退款怎么弄 | `rag` | ❌ | — | RAG 检索链路 |
| 明确转人工 | 我要转人工 | `transfer` | ✅ | `explicit_request` | N-7（检测被分数门槛短路） |
| 强负面词 | 我要投诉你们 | `transfer` | ✅ | `negative_sentiment` | 强词单次命中 |
| 弱负面单个 | 太慢了 | 任意 | ❌ | — | N-10（弱词只安抚不转） |
| 弱负面两个 | 好烦啊，快递太慢了 | `transfer` | ✅ | `negative_sentiment` | N-10（弱词累计 ≥2 才转） |
| 子串误判-麻烦 | 麻烦帮我查一下订单 | 任意 | ❌ | — | N-10（`麻烦` 不能命中转人工） |
| 子串误判-没用过 | 这个券我没用过 | 任意 | ❌ | — | N-10（`没用` 不能命中转人工） |
| 连续重复 4 次 | 我的订单到哪了 ×4 | `order` | ✅（第 4 条） | `repeated_attempts` | 重复意图兜底（`WITH_REPEAT=1`） |
| 模型故障降级 | `__CHAOS__ 你好` | — | ✅ | `ai_error` | N-15（provider 挂掉 → 兜底话术 + 转人工）（`WITH_FAILURE=1`） |

> 为什么是 4 次而不是 3 次：`repeatCount` 在**下一轮**才生效——
> 第 1 条 `previousIntent` 为空不计数，第 2/3/4 条分别累计到 1/2/3，
> 检测发生在本轮回答**之前**，所以第 4 条才满足 `repeatCount >= 3`。

## 4.1 故障注入（模型故障降级场景）

真实模型不会配合你"按时挂掉"，所以后端留了一个**测试专用**钩子
（`ai-customer.service.ts#maybeInjectChaos`）：

| 条件 | 作用 |
|---|---|
| 消息以 `__CHAOS__` 开头 | 普通消息第一行就 `return`，零开销 |
| `NODE_ENV !== 'production'` | 生产环境物理上不可能触发 |
| Redis 存在 `ai:chaos:fail` | 脚本临时 `SET … EX 120`，跑完 `DEL`，不会残留 |

三个条件同时满足才抛错，错误走的是**和真实超时完全相同的路径**：
`chatStream` 的 `catch` → `chat.error` → `handleStreamError` → `degradeToHuman`。

脚本断言四件事：

| # | 断言 | 对应降级动作 |
|:--:|---|---|
| ① | 本轮恰好落 1 条 AI 消息，`role=assistant` / `source=ai`，内容含"转接人工" | 兜底话术落库 + 双通道 |
| ② | `Conversation.handler_id = 'awaiting_human'` | 阻断下一轮，故障不被重放 |
| ③ | 日志有 `transfer{source:'fallback', reason:'ai_error'}` | 统计口径不出现黑洞 |
| ④ | 日志有同 traceId 的 `chat.error` | 证明走的是异常路径，不是正常完成 |

> 时序注意：日志先出现、写库在其后，所以脚本用 `wait_sql_eq` 轮询（≤10s），
> 而不是看到 `chat.error` 立刻读库。

**限制**：注入点在 `chatStream` 开头，验证的是"图执行前就失败"这一种；
`runEventStream` 执行到一半才断的流式中断仍由 `chat.error` 覆盖，但没有单独断言。

## 6. 已知限制 / 坑

1. **`docker logs --since` 在 Colima 上会卡死**（本机实测，json-file 驱动）。
   脚本因此改成 `docker logs --tail N` + 按结构化日志自带的 `ts` 过滤。
   如果你换了 Docker 环境并且 `--since` 正常，可以把 `TAIL_LINES` 调小。
2. **LLM 非确定性**：意图分数依赖 embedding（BGE 是确定性的），但 RAG 召回的
   文档可能随索引变化，`tokenTotal`、耗时每次不同——脚本只断言布尔/枚举，不断言数值。
3. **依赖 Meilisearch / Infinity（或 Jina）**：RAG 场景如果检索服务没启动，
   意图可能仍然正常但回答质量会下降；脚本不断言回答内容。
4. **会在你的聊天列表里留一条 `【AI自测】` 会话**，并写入测试消息。
   想换一条新的：删掉旧会话（连带 `ChatMember` / `ChatMessage`）后重跑即可。
5. **串行执行**：靠"发送时间 → traceId"认领，所以不能并发跑两个实例。
