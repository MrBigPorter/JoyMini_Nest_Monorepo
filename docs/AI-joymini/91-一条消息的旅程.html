一条消息的旅程

从用户按下发送，到 AI 那句回复出现在屏幕上。七个框，全部来自真实代码，不是示意图。

01主干

只有主线。所有异常、限流、超时分支都先砍掉 —— 它们都挂在某个框的旁边，看懂主干就能挂上去。

  1. 01

    用户发消息 —— 两个入口，同一个事件

    HTTP 走 ChatService.sendMessage，socket 走 EventsGateway。两边都做同一件事：先把用户消息写库、广播给会话成员，然后判断要不要叫 AI。

    chat.service.ts:236 events.gateway.ts:493 type ∈ {SUPPORT, AI} handlerId == null

  2. 02

    事件总线 → 监听器

    发出去的是 AI_MESSAGE_REQUESTED。监听器自己生成一个 traceId 并挂在异步上下文上，然后调 chatStream。

    ai-message.listener.ts:37 为什么自己生成 traceId

  3. 03

    chatStream 的前四步：准备、快照、思考中、跑图

    找到一个 thread（对话线程），把成员列表查一次（后面每个 token 都要用，不能每条查库），记下当前消息数当"之前的长度"，推一条 thinking，然后进 LangGraph。

    ai-customer.service.ts:128 ai-stream.handler.ts:39 streamEvents

  4. 04

    LangGraph 图里：分类 → 路由 → 干活

    先给用户这句话打意图标签（向量检索），再进 orchestrator。orchestrator 的第一件事就是判转人工，然后才轮到"分数够不够、要不要调 agent"。这一步的顺序，就是 N-7 那个 bug 的现场。

    orchestrator.node.ts:237 transfer-detector.ts:94 顺序 = 语义

  5. 05

    图跑完，取"新增了什么"

    读最终 state，用第 3 步记下的长度切出本轮新增的消息，先存进 Redis 热缓存（saveContext），然后按 state 里的两个布尔值决定走哪条路。

    ai-customer.service.ts:347 transferToHuman pendingConfirm

  6. 06

    三路分发（互斥）

    转人工 / 确认卡片 / 正常完成。三选一，各自有各自的副作用 —— 这张图就是下面那张 fork。

    ai-customer.service.ts:364 if / else if / else

  7. 07

    广播：一条消息，两个通道

    AI 的话写进 ChatMessage（带上 role=assistant / source=ai），然后推给"会话房间"和"每个成员的私有房间"，用 .except() 把重复的那一份挡掉。

    ai-reply-publisher.ts:42 events.gateway.ts:225 .except(conversationId)

06三条读法

  • 先找出口，再读入口。任何一段流程，先看它有几条 return / 几个结局，再倒着读进去。正向读一定会被中间的分支绊住。
  • 每一行先问一句：这是承诺，还是装饰？更新 handlerId 是承诺（失败必须报错）；写一条消息记录、查成员列表是装饰（失败 warn 一下就过）。分不清这两类，就会觉得代码"有时严谨有时随便"，其实一直很一致。
  • 状态只在两个地方。图里是 AgentState（一个所有人共用的抽屉），图外是 Conversation 表 + Redis 热缓存。看到一个字段不知道谁写的，去这两处找，不要在图里瞎找。

07面试就讲这 60 秒

「用户发一条消息，我们先落库广播，然后判断这个会话是不是 AI 在处理 —— 条件是 SUPPORT 类型且没有人工接手。是的话发一个领域事件，监听器包一层 traceId 再进 LangGraph。

图里先打意图标签，然后进 orchestrator。orchestrator 第一件事是判转人工，在分数门槛之前 —— 因为"我要转人工"这种短句意图分天然很低，放后面就永远转不出去。

图跑完，我们比对前后消息数切出本轮新增的，按 state 上的两个布尔值三路分发：转人工、确认卡片、正常完成。正常完成就把消息落库，同时推会话房间和成员私有房间，再用 except 去重 —— 只推会话房间会漏掉还没 join 的客户端。

整个过程每个决策点发一条结构化日志，共享一个 traceId，所以能按对话聚合出意图、耗时、token 和转人工原因。」

这段话里没有一个 API 名字，全是取舍和它们的原因。面试官追问的方向，会从这里往回收依赖、限流、幂等 —— 那也是同样的读法：先找出口。
