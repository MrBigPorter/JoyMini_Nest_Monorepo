## 一、这份文档是什么

一句话：把「一次 AI 回答，从事实定义到事故复盘」的完整链路画出来，并标出每个节点此刻的真实状态。

它**不描述任何单点行为**。单点行为归 OpenSpec 契约（`openspec/specs/`），改行为要有 change。这份文档只管三件跨阶段的事：

1. **顺序**——节点之间的依赖，谁能先做、谁必须先做。
2. **主轴**——贯穿所有节点的那条版本线，回答「这条回答出自哪一套东西」。
3. **闸门**——在哪五个位置拦人，拦什么，证据是什么。

判断标准只有一条：**文档里的每个论断都能指向一个真实文件或一次可执行的验证。**

第七节并列一份外部参考实现，只作对照，不构成约束。

## 三、版本主轴

### 3.1 定义

```
release = codeSha + indexVer + promptVer + kbVer
```

任一回答、任一次评测、任一次部署，都必须能反查到这四个值。**没有这条主轴，"证据通过"和"部署上去了"就是两件不相干的事。**

### 3.2 四个分量现在在哪

| 分量 | 当前载体 | 状态 |
|---|---|---|
| `codeSha` | `AiEvalRun.codeVersion`（schema.prisma:2532）；部署镜像 SHA | 已有 |
| `kbVer` | `AiEvalRun.knowledgeFingerprint` + `knowledgeSnapshot`；运行时 `KB_EPOCH_KEY`（kb-version-notice.ts:19） | 已有 |
| `promptVer` | `PromptResolverService` 合并后的 DB 版本号；对话级记录在 `ai-customer.service.ts:1526` | 已有，未进 release |
| `indexVer` | 无独立标识，隐式附着在 KB 版本上（chunk + Meilisearch 版本切换由 `KbVersionService` 保证） | 缺 |

### 3.3 一次回答的反查路径（目标态）

```
回答 → traceId → 对话记录（promptVersion / kbEpoch）
                      │
                      └─► release manifest
                            ├─ codeSha
                            ├─ indexVer
                            ├─ promptVer
                            └─ kbVer
```

现状断在「release manifest」这一环：四个分量各自可查，但没有一个对象把它们绑在一起。

## 四、术语

| 术语 | 含义 |
|---|---|
| **真值源** | 某类事实的唯一定义处（如渠道费率以 `payment_channels` 为准）。文档只能引用，不能自证 |
| **release** | 一次可部署的组合：代码 + 索引 + Prompt + 知识库四个版本号 |
| **证据** | 一次评测运行给出的、可判定通过与否的结构化结果（`/evidence` 的 `checks`） |
| **闸门** | 在链路上强制检查的位置；不通过则阻断，不是告警 |
| **坏例** | 线上真实失败样本，入池后转成回归用例 |
| **忠实（faithfulness）** | 答案是否被检索到的内容支撑——证明「没编」 |
| **正确（correctness）** | 答案是否与真值源一致——证明「没错」。二者不等价 |

## 五、五闸门

| 闸门 | 位置 | 拦什么 | 证据是什么 | 现状 |
|---|---|---|---|---|
| **G1 一致性** | ③ 一致性校验 | 文档宣称 ≠ 线上事实 | 比对报告（doc 声明 vs 业务表） | ✗ 无 |
| **G2 版本绑定** | ④ → ⑨ | 评测跑的和部署的不是同一套 | release manifest | ◐ 分量齐、绑定缺 |
| **G3 质量** | ⑥ → ⑧ | 指标退化 | `/evidence` 的 checks | ◐ 有，advisory |
| **G4 运行时** | 生成后 | 无依据 / 低置信 / 高风险动作 / 状态冲突 | 转人工事件 + 拦截日志 | ◐ 只有 no_evidence |
| **G5 回滚** | 事故后 | 四个版本不同步 | 回滚 runbook + 回滚后证据 | ◐ 只有代码镜像 |

G1 与 G2 是当前最大的两个洞：它们不补，G3 的评测结果就无法回答「测得对不对」和「测的是不是同一套东西」。

### 6.1 一条已知的错判

`no_identical_repeat`（`tools/eval/e2e/judge.mjs:593`）把「同一问题两次回答相似度 ≥80%」判为失败。方向与事实相反——同一问题答案不一致才是缺陷。该用例在不同运行里出现 4% ✅ / 96% ❌ 的波动，判定随模型温度翻转。

## 七、参考实现对照（OmniSupport Copilot）

同课程的准生产仓库（本机路径 `/Volumes/MySSD/work/study/omnisupport-copilot`，591 个文件，Python + FastAPI + Dagster + pgvector）。技术栈不同，**不能照搬代码，但可以照搬结构和判定顺序**。以下路径均相对该仓库根目录。

| 位置 | 参考文件 | 它做了什么 | 对我们的用法 |
|---|---|---|---|
| ① ③ · G1 | — | 全仓没有「事实 → 来源」的登记，也没有文档与配置的比对；`contracts/data/*.json` 只约束数据形状 | 证明 G1 是两边共同的空白，不是我们漏看 |
| ④ · G2 | `contracts/release/release_manifest_v2.schema.json`、`release/registry.py`、`release/integrity.py` | manifest 分 `metadata / spec.components / quality / business_slo / rollout / governance / integrity`；注册时校验 `previous_release_id + previous_manifest_digest` 祖先链；`promote` / `rollback` 用 `expected_current_release_id` 乐观锁切环境指针，rollback 必须直接祖先且写明原因 | P2 直接沿用这套分区，把 `indexVer / promptVer / kbVer` 放进 `spec.components` |
| ⑦ | `release/compliance/generator.py` | 发布证据打包成可签字产物 | P4 除了 `/evidence` 接口，再产一份人可读的证据包 |
| ⑥ ⑧ · G3 | `evals/week11/regression.py`、`evals/week11/business_slo.py`、`evals/baselines/` | 指标 vs 基线、业务 SLO 目标，两段都进发布判定 | P4 的阈值照它分两段：质量指标、业务 SLO |
| ⑧ ⑨ · G5 | `rollout/canary.py`、`rollout/rollback.py` | 判定顺序：红线 → 样本量/观察窗口 → stage gates → baseline guards；任一红线破了直接 rollback，不看质量有没有变好 | P4 照这个顺序，不要先看总分 |
| 运行期 | `agent/copilot.py` | 固定顺序：契约校验 → 角色鉴权 → HITL 判定 → 幂等 → 执行 → 血缘落库 | P5 的承诺分支照这个控制面搭，不另起一套 |
| G4 | `agent/hitl.py` | HITL 条件是一门小语言（`field op literal`，支持 AND），多条命中取最高优先级：reject > require_approval > pause_and_notify | 我们缺的两个信号（低置信、状态冲突）可以直接写成条件，不用改结构 |
| 动作分级 | `contracts/tools/tools/create_ticket.json` | 一个契约同时写清 `allowed_roles / idempotent / idempotency_key_fields / hitl_conditions / failure_codes / rate_limit / audit_fields` | 比 `action-catalog.ts` 的 `needsOtp` 二元强一个量级 |
| 观测 | `observability/runtime/privacy.py` | trace 只存 sha256、长度、计数；要看内容必须显式 preview，且过 5 条正则 | P5 的拦截日志照此，别把用户原话写进 trace |
| 闭环 | `observability/week12/badcase.py`、`tools/badcase_to_eval.py` | incident → `EvalSample` → 回归资产，一步落地 | 2.3 的 learn 段已有现成范式 |

**三条结论**

1. **契约 ≠ 真值**。它的 34 个 schema 管的是形状（字段、类型、必填），不是数值（费率是 0.015 还是 0.008）。两者并存，不能互相替代——P1 的登记是后者。
2. **它的评测与我们同盲区**。`evals/week11/metrics.py` 的 faithfulness 是答案 token 与检索上下文的重叠率（乘 1.8 系数，abstain 固定给 0.5 分）。文档错了照样满分——这是第四节「忠实 ≠ 正确」的第二份证据。
3. **文档放在仓库还是 DB，决定闸门的形状**。它的文档在仓库里，契约测试能在 PR 阶段拦住；我们的文档在 `knowledge_documents`，只能次日定时体检（见 `ai-truth-layer` design D5）。这也是那份 change 把「文档是否迁入仓库」留成 Open Question 的原因。

## 八、阶段索引

按依赖序，**一次只开一个 change，做完 archive 再开下一个**。

| 顺序 | change | 覆盖节点 | 核心行为变化 | 验收 |
|:--:|---|---|---|---|
| P1 | `ai-truth-layer` | ①②③⑤ | 文档宣称与业务表不一致时构建失败 | 故意改一个费率，CI 红 |
| P2 | `ai-release-versioning` | ④⑨ | 每次 run/部署记录四版本号 | 任一回答可反查四个版本 |
| P3 | `ai-eval-correctness` | ⑤⑥ | 评测能发现「忠于错误文档」；修 `no_identical_repeat` | 文档数字写错，评测红 |
| P4 | `ai-gate-enforce` | ⑦⑧ | 证据不通过则阻断部署 | 用不通过 run 部署，失败 |
| P5 | `ai-runtime-boundary` | 运行期 + 闭环 | 承诺类问题不再由模型自由回答 | 问费率，命中工具或转人工 |

**依赖理由**

- P1 → P2：版本绑定要记录「真值是哪一版」。
- P2 → P4：否则门禁通过的和部署的不是同一套东西。
- P1 → P3：引用型用例从真值登记生成。
- P3 → P4：门禁通电前必须先修掉已知误判，否则会被误报卡住。

**开工前先看参考实现（第七节）**

- P2 的 manifest 字段分区照 `contracts/release/release_manifest_v2.schema.json`，不自己发明。
- P4 的判定顺序照 `rollout/canary.py`：红线 → 样本与窗口 → 质量 gate → 基线护栏。
- P5 的工具契约字段集照 `contracts/tools/tools/create_ticket.json`。
