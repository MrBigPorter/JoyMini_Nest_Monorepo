## 0. 一句话

没有数字的改动，在面试里等于没做。这个工具产出一个数：**当前系统在 60 条人工标注问题上，意图判断对了多少条**；以及改完代码后，这个数变了多少。

---

## 1. 它测量什么 / 不测量什么

| 测量 | 不测量（交给别的工具） |
|---|---|
| ✅ 意图分类 top-1 准确率（按域） | ❌ 回答质量（RAG 召回是否对、话术是否好） |
| ✅ 每个意图域的精确率 / 召回率 | ❌ 转人工判定（`scripts/ai-e2e-smoke.sh` 的 8 个场景） |
| ✅ 分类方法分布（embedding vs llm_fallback） | ❌ 端到端耗时（含 LLM 生成，E2E 的 `chat.done.totalMs`） |
| ✅ 单次分类 p50 / p95 延迟 | ❌ 成本（token 在 `llm.usage` 里） |

> **为什么只测分类**：分类是整条链路的岔路口——走错岔路，后面无论答多好都是错的。
> 而且它是唯一能被**低成本、确定性**重放的环节（embedding 比对，不生成回答），
> 所以适合每次改动都跑一遍。

## 2. 为什么用现成接口，不写新代码

`POST /admin/intent-examples/test`（`intent-examples.controller.ts:110`）已经返回：

```json
{ "intent": "order", "labels": [{"domain":"order","score":0.87}, ...],
  "method": "embedding", "rawTop5": [...] }
```

它内部 `new IntentClassifier(aiService, prisma, meilisearch, llmConfig)`（`intent-examples.service.ts:400`），
**与生产 `intent-router.node.ts:167` 是同一个类、同一份构造函数参数**。

> 为什么强调这点：#87 记录过一个反模式——`scripts/verify-intent-router.js` 把 prompt 复制了一份，
> 测的是副本而不是生产代码（「自证测试」）。本工具必须打在生产路径上。

## 3. Golden set 设计

**文件**：`tools/eval/golden/intent.jsonl`，一行一条，JSON：

```json
{"id":"o01","input":"我的订单到哪了","expect":"order","tags":["order","查询"],"note":"典型查询"}
```

| 字段 | 说明 |
|---|---|
| `id` | 稳定 ID（域首字母 + 序号），改动后能对比同一题是否变好 |
| `input` | 用户原话（中文为主，混少量英文，贴近真实流量） |
| `expect` | 期望域（9 个之一） |
| `tags` | 便于分组统计（如 `negative`、`trap`、`short`） |
| `note` | 人话说明，为什么标这个域 |

**规模与分布**：63 条（60 条域覆盖 + 3 条专门陷阱），每域 5~8 条，另加"陷阱题"：
- 子串陷阱：`麻烦帮我查一下订单`（不能被"麻烦"带偏）、`这个券我没用过`（"没用"≠ 负面）
- 跨域歧义：`退款怎么弄`（order 还是 rag？约定：**流程操作 → order；政策规则 → rag**）
- 极短输入：`嗯`、`?`、`在吗`（应归 `general`，不能乱猜业务域）

**标注原则（先定后标，避免"结果倒推标签"）**：

| 情况 | 归哪个域 |
|---|---|
| 查**我自己的**订单、退款进度、地址 | `order` |
| 问政策、规则、流程"是什么 / 怎么弄" | `rag` |
| 余额、充值、提现 | `wallet` |
| 领券、用券、券过期 | `coupon` |
| 账号、等级、资料 | `user` |
| 商品详情、价格、库存 | `product` |
| 抽奖、中奖、奖品 | `lucky-draw` |
| 实名认证、身份证、KYC | `kyc` |
| 打招呼、闲聊、无法归类 | `general` |

> **边界口径（一句话）**：**我自己的记录 → 业务域；通用规则 / 流程 → `rag`。**
> 所以「退款进度怎么样了」是 `order`，「退款怎么弄」是 `rag`。

**防污染**：例句不能用后台 `intent_examples` 里已有的句子——那等于用训练集考试。
写完 golden set 后跑一次 `--check-overlap`（脚本内实现），与 Meilisearch 里的例句做字符串相似度比对，输出疑似重复项。

## 4. 回放脚本

**文件**：`tools/eval/replay.py`（Python 3，只用标准库：`urllib` / `json` / `statistics`）

```
读 golden/intent.jsonl
  ↓ 逐条 POST /admin/intent-examples/test
记录 {id, expect, predicted, topScore, method, latencyMs, rawTop5}
  ↓ 汇总
accuracy / 每域 precision·recall / 混淆矩阵 / method 分布 / p50·p95
  ↓ 落盘
tools/eval/reports/<YYYYMMDD-HHMMSS>.json + .md
  ↓ 与 baseline.json 对比
报告 delta，超出阈值则退出码 1
```

**Token 从哪来**：不在脚本里存密钥。由 `run-replay.sh` 在 `lucky-backend-dev` 容器内用
`JWT_SECRET` 临时签发一个 admin token（与 `ai-e2e-smoke.sh:138` 同一做法），通过环境变量
`EVAL_TOKEN` 传给 Python。脚本不落盘、不打印。

**参数**：

| 参数 | 默认 | 说明 |
|---|---|---|
| `--base-url` | `http://localhost/api/v1` | 也可指向预发 |
| `--limit N` | 全部 | 只跑前 N 条，调试用 |
| `--tag X` | 全部 | 只跑带某 tag 的（如 `trap`） |
| `--fail-under` | 基线 − 2pp | 低于就退出码 1 |
| `--update-baseline` | 关 | 把本次结果写回 `baseline.json`（**只有人工确认后才用**） |

## 5. 指标定义（写清楚，避免自欺）

| 指标 | 公式 | 为什么要 |
|---|---|---|
| **Top-1 准确率** | 预测域 == 期望域 的条数 / 总条数 | 主指标，就是"准确率 80%"里的那个数 |
| **每域 recall** | 该域标对了多少 / 该域总条数 | 哪个域最弱，决定下一步改哪里 |
| **每域 precision** | 预测为该域且对了多少 / 预测为该域总条数 | 防止"什么都猜 order"刷高 recall |
| **macro-F1** | 9 个域 F1 的算术平均 | 小域不被大域淹没 |
| **method 分布** | embedding / llm_fallback 各占多少 | llm_fallback 多代表检索层不健康（贵且慢） |
| **p50 / p95 延迟** | 单条分类耗时分位 | 分类慢了，整轮对话就慢 |

> 只看 accuracy 会被"多数类"骗：如果 60 条里 20 条是 `order`，全猜 order 也有 33%。
> 所以报告必须同时给 macro-F1 和混淆矩阵。

## 6. 判定门槛

| 场景 | 门槛 |
|---|---|
| 首次 | 记录基线，不设门槛。**先有数，再谈好坏** |
| 后续改动 | 准确率下降 > 2pp → CI 红；持平或提升 → 绿 |
| 发布前 | 陷阱题（`tag=trap`）必须 100%——它们是已知的回归用例 |

## 6.1 首次基线结果（2026-11-12）

`tools/eval/run-replay.sh --update-baseline`，63 题、0 请求失败：

| 指标 | 数值 |
|---|---|
| Top-1 准确率 | **68.2%**（43 / 63） |
| macro-F1 | 68.6% |
| 分类方式 | embedding 59 条 / llm_fallback 4 条 |
| 延迟 p50 / p95 | 415 / 499 ms |

**最弱的是 `rag`：精确率 38.9%、召回 87.5%** —— 它把大量本该属于 `kyc` / `wallet` / `user` / `order` 的问题吸了过来
（混淆矩阵里 `kyc→rag` 3 条、`wallet→rag` 2 条、`order→rag` 3 条、`user→rag` 2 条）。
典型错例：`我要提现` → `rag`、`上传身份证一直失败` → `rag`、`我的交易记录在哪看` → `rag`。

各域召回：`general 100%` / `coupon 87.5%` / `rag 85.7%` / `user 71.4%` / `lucky-draw 66.7%` /
`product 57.1%` / `order 62.5%` / `wallet 42.9%` / `kyc 33.3%`。

> 这个数就是"准确率多少"的答案。改 T2-3（RAG 中文分词 + 相关性门槛）或补各域例句后，
> 重跑同一条命令，能直接说出「提高了几 pp」。

**标签修正 1 条（记录在案，不是调分）**：`t03 退款怎么弄` 首跑时按"操作流程"标成 `order`，
但 §3 的口径是「我自己的记录 → 业务域；通用规则/流程 → `rag`」。这题问的是流程，应标 `rag`。
修正后重跑：**68.2%（43/63）、macro-F1 68.6%**，陷阱题 **6/6 全对**。

**踩到的坑（已修）**：第一次跑 63 条撞上全局限流（60 次 / 60 秒），后 6 条被记成失败。
工具已改为「429 → 按 `Retry-After` 退避重试 + 每条间隔 0.5s」，并且**有失败就拒绝更新基线**。
这条同样值得讲：度量工具必须先能区分「系统错了」和「测量被拦了」。

## 8. 不做的事

- **不测回答质量**：那需要人工评分或 LLM-as-judge，是第二个迭代（见 §9）。
- **不改生产代码**：只调用已有管理端接口。
- **不跑在 CI 的每次 commit**：一次 60 条约 1~2 分钟（要看 embedding 服务）。先手动跑，稳定后再接 CI。
- **不用 LLM 生成 golden set**：标注必须人工，否则测的是模型和模型自己的一致性。
