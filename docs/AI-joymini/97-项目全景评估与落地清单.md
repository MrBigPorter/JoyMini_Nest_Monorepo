**重要更正：项目不是按这个顺序建起来的。**
它是「接手一个已跑到 V10 的系统，回头补 V6 / V10 的欠账」。这比从零建更难——每个改动都要兼容历史数据、历史前端、历史用户。证据是 108 个迁移最早到 `20260709`。

**该路线图的两处偏差：**
1. **11 版里没有一版是「安全」** —— 没有权限、越权、注入、幂等、限流、资金一致。按它走完得到的是「能跑的系统」，不是「不会出事的系统」。
2. **Redis 排在第 8 版太晚** —— 限流第一天就要；HITL 的一次性令牌、SSE 预留（120s TTL）、seq 发号全依赖 Redis，都在 V7 之前。

## 4. 整体判断

### 4.1 强在哪（五条）

1. **资金链路的工程正确性**。单一结算出口 + 状态 CAS + 毛额/净额区分 + 事务原子性（#95）。这是很多人做不到的。
2. **写操作的防护深度**。模型只填表、令牌一次性、只发私有房间、TTL 拆分。不是抄来的，是打出来的（T1-2 / T1-4）。
3. **可观测性**。traceId 串起 5–7 条事件、8 类埋点、生产不记 payload（#89）。
4. **检索工程**。4 层混合 + 候选放大 ×4 + 统一 rerank；且**知道为什么不用 RRF**（各层量级差太大，RRF 会被弱层拖累）。
5. **交付能力**。14 条流水线、108 个迁移、Playwright E2E、Lighthouse 门禁——「本地能跑」和「推一次就上线」是两件事。

### 4.2 弱在哪（五条）

1. **没有评测尺子**。意图有 63 题基线，RAG 一个指标都没有 → 任何检索改动都无法判断好坏。
2. **单实例假设**。无 Socket.IO Redis adapter（#85 P1-5），一旦部署两个实例，WebSocket 广播直接失效。
3. **状态不持久**。MemorySaver 重启即失忆；转人工等 10 分钟期间发一次版，上下文就断了。
4. **成本无上限**。没有按天聚合的 token 预算；一条长对话可以无限烧。
5. **AI 行为未披露**。AI 回复没有 `isAi` 标记（#85 P1-1），用户分不清是机器人还是真人。

### 4.3 一句话诊断

> **骨架完整、肌肉有劲，缺的是「多实例 + 可验证 + 合规」这三根筋。**

## 5. 什么叫「落地」

落地不是一个状态，是三档：

| 档 | 定义 | 现在离它多远 |
|:--:|---|---|
| **L1 能演示** | 我用一台机器跑起来，给你看完整流程 | ✅ **已达到** |
| **L2 能给真实用户用** | 随便谁来用都不会出事、不会亏钱、不会被越权 | ❌ 差 **7 个硬阻断** |
| **L3 能规模化运营** | 多实例、有告警、能对账、有客服 SLA | ❌ 差 **一整套运维** |

**当前在 L1，目标是 L2。L3 现在不做。**

## 7. 难度与顺序

### 7.1 剩余 14 项的难度账

| # | 事项 | 工作量 | 真正的难点 | 风险 |

| — | SSE 断连中止 | 0.5d | AbortSignal 贯通 LangGraph | 🟠 |

**全部约 12–16 人日。**

### 7.2 难度不均匀的真实原因

- **6 项是在现有模式上换张表**（T1-5、大额阈值、成本限额、工具超时、Word 解析、RRF）
- **3 项是纯写代码但无法验证**（RRF、Query Rewrite、Faithfulness）
- **1 项真的会碰架构**（PG Checkpointer——其余 13 项都是加法，它是替换）
- **2 项卡在代码之外**（短信资质、支付通道）

### 7.3 顺序的唯一原则

```
先做「能被证明的」→ 再做「需要证明的」
```

`检索质量指标` 是分水岭。有了它，RRF / Query Rewrite / Context Builder 才有判断依据；没有它，这三个都是「我觉得应该会更好」。

## 9. 不做的事（边界）

| 项 | 理由 |
|---|---|
| MCP | 单进程单消费者，引入只增加故障点 |
| 多 Agent | 业务路径确定，普通工作流更稳 |
| RRF | 各层量级差大，rerank 统一打分更可靠 |
| Query Rewrite（现在） | 多一次 LLM 调用，成本 +30~50%、延迟 +200~400ms；应先有评测基线 |
| 模型微调 | 当前问题在检索与工程，不在模型 |
| **Python / FastAPI 重写** | 现有 NestJS 能力等价；**仅在以「转 AI 岗」为目标时再补**，预估 2 周可迁 70%（缺的是语法不是工程判断）。国内 JD 写 Python 的比例高于 Node，属「优先级靠后」而非「不需要」 |

## 10. 一句话总结

> **难不难：不难。14 项里 10 项是顺着现有模式换张表、换个包装。**
>
> **难的是「做完之后你知道它变好了吗」——而这一项现在完全没有。**
>
> 所以落地顺序是：**先关 P0（越权/超卖）→ 再补多实例（否则只能跑一台）→ 再建评测尺子 → 最后才谈优化。**
