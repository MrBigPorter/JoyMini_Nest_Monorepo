# Lucky Nest Monorepo - AI Constitution (Detailed Reference)

> 当需要查具体规则或代码示例时引用此文件。

## 🔴 绝对禁令（一票否决）

1. **禁止使用`any`类型**：未知类型使用`unknown`，必须为所有API响应和组件Props定义完整interface
2. **禁止在代码注释中使用Emoji图标**：所有//注释只能使用纯文本，文档和Markdown文件除外
3. **禁止代码中出现非ASCII字符注释**：注释优先使用英文，中文仅允许在Markdown文档中使用
4. **禁止假设导入存在**：使用任何导入前必须检查目标文件是否确实导出了该标识符
5. **禁止在验证之前提交修改**：任何代码修改必须先通过类型和lint检查
6. **禁止产生水合错误**：涉及浏览器API（window, localStorage, Canvas等）的逻辑，必须封装在`useIsClient` Hook中
7. **禁止硬编码样式**：优先使用Tailwind CSS，避免基于客户端状态计算的动态class
8. **禁止重复定义类型**：优先复用`packages/shared`和`src/types`中的全局类型
9. **禁止线性思维**：每次修改必须从系统角度思考，分析影响范围和水合风险
10. **禁止单层语言处理**：语言切换必须在HTTP请求、React Query缓存、路由参数三个层面统一处理
11. **禁止乱改包名**：package.json中的`name`字段必须遵循项目命名规范，禁止随意更改工作区名称
12. **禁止消防员思维**：禁止只修复出错的那一行代码，必须消除根本原因，完成闭环改进
13. **禁止不必要的 dev 重启**：禁止在代码修改后自动运行全局 `yarn dev` 命令；开发服务器应持续运行，除非修改了配置文件、环境变量或包依赖；优先使用工作区特定的 dev 命令（如 `yarn workspace @lucky/admin-next dev`）；必须利用 Next.js 热重载特性，90%的代码修改无需重启服务

## 🟡 架构规则（按模块）

### Next.js前端

- **页面跳转动画**：必须使用动态导入（`next/dynamic`）禁用SSR，或封装在`useIsClient` Hook中
- **国际化路由**：必须考虑`/[locale]/path`格式，优先使用系统配置的可用语言列表
- **状态管理**：优先使用Zustand，复杂状态必须定义完整interface和initialState
- **API调用**：必须使用项目HTTP客户端，包含完整错误处理和loading状态
- **可选依赖**：动态导入的可选模块必须有类型声明文件（如`capacitor.d.ts`）
- **React Query缓存**：所有数据获取Hook的queryKey必须包含`locale`参数，确保语言切换时缓存正确失效

### NestJS后端

- **数据验证**：必须使用DTO + 全局拦截器/管道处理数据验证和XSS消毒
- **权限系统**：必须复用现有AdminJwtAuthGuard + RolesGuard三级权限体系
- **数据库操作**：金额计算使用Decimal.js，敏感数据加密存储
- **事务处理**：相关操作必须使用Prisma事务确保数据一致性
- **错误处理**：统一错误响应格式，包含错误码和友好消息

### 全局开发规范

- **文件位置**：
  - 公共工具函数 → `src/lib/utils/`
  - 自定义Hooks → `src/lib/hooks/`
  - TypeScript类型定义 → `src/types/` 或 `packages/shared/src/types/`
  - 组件分类 → `src/components/` + 子目录按功能分类
- **组件使用**：必须使用`@repo/ui`组件库，禁止使用原生HTML元素
- **代码质量**：函数长度 ≤ 50行；组件Props必须严格声明；复杂逻辑必须有注释说明
- **文档要求**：重大修改必须遵循七层黄金文档结构

## 🟢 思考过程要求（每次任务前必须执行）

### 1. 系统影响分析

- 这个改动会影响哪些相关部分？是否需要同步修改其他文件？是否符合项目现有模式？

### 2. 水合风险评估

- SSR环境下是否存在水合风险？是否依赖浏览器API（window, localStorage等）？如何防范？

### 3. 类型安全分析

- 所有类型是否已有定义？是否需要新增interface？是否存在可选依赖需要类型声明？

### 4. 重复代码检查

- 这个逻辑在其他地方存在吗？能否抽取公共函数？是否符合DRY原则？

### 5. 时序预判

- 如果有两个请求同时到达会发生什么？异步操作是否有竞态条件风险？是否需要添加防护机制？

### 6. 闭环改进分析

- 这个问题为什么会发生？为什么之前没有被发现？如何保证永远不会再出现？是否需要更新文档或规则？

## 📋 验证流程（AI必须执行）

1. **全局搜索**：先搜索全文，查看是否有可复用结构和现有解决方案
2. **导入验证**：使用任何导入前必须检查目标文件是否确实存在该导出
3. **质量检查**：运行`yarn type-check` → `yarn lint` → `yarn prettier --check`
4. **架构一致性**：检查是否符合项目架构模式和设计系统
5. **知识归档**：如果是新的问题模式，必须更新架构文档或添加到已知问题列表
