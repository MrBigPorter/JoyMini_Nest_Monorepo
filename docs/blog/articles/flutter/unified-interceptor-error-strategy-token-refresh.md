## Overview

[`UnifiedInterceptor`](JoyMini_Flutter_App/lib/core/network/unified_interceptor.dart) is a Dio interceptor that serves as the central nervous system for all HTTP communication in a Flutter application. It extends `QueuedInterceptor` (ensuring request ordering) and handles three lifecycle hooks: request injection, response dispatch, and error strategy resolution.

This interceptor addresses four critical concerns:

| Concern | Mechanism |
|---------|-----------|
| **Device Fingerprinting** | Injects `x-device-id`, `x-device-model`, `x-platform` headers on every request |
| **Error Strategy Dispatch** | Maps HTTP status codes and business error codes to 5+ actionable strategies |
| **Single-Flight Token Refresh** | Only one refresh at a time — concurrent 401 requests share a single Completer |
| **Server Time Sync** | Calibrates local clock from `x-server-time` response headers |

## 1. Request Interception: Device Fingerprint Injection

Every outgoing request automatically injects device identification headers:

```dart
@override
void onRequest(RequestOptions options, RequestInterceptorHandler handler) {
  final fingerprint = DeviceUtils.getFingerprint();
  
  options.headers.addAll({
    'x-device-id': fingerprint.deviceId,
    'x-device-model': fingerprint.deviceModel,
    'x-platform': fingerprint.platform,
  });
  
  handler.next(options);
}
```

This enables the backend to:
- Track device-level activity patterns
- Detect device blacklisting (`deviceBanned` event)
- Enforce device trust levels (`deviceNotTrusted`)
- Identify anomalous access patterns

The fingerprint is generated by [`DeviceUtils`](JoyMini_Flutter_App/lib/utils/device_utils.dart) with platform-specific implementations:

| Platform | Device ID Source | Model Source |
|----------|-----------------|--------------|
| iOS | `FlutterUdid.consistentUdid` | `IosDeviceInfo.utsname.machine` |
| Android | `FlutterUdid.consistentUdid` | `AndroidDeviceInfo.brand/model` |
| Web | SharedPreferences persisted UUID | `webBrowserInfo` |

## 2. Error Strategy Dispatch

The core of `UnifiedInterceptor` is its `onError` handler, which maps HTTP status codes to strategy-specific handlers:

```dart
@override
void onError(DioException err, ErrorInterceptorHandler handler) {
  // Server time calibration (every response)
  ServerTimeHelper.updateOffset(err.response?.headers.value('x-server-time'));
  
  switch (err.response?.statusCode) {
    case 401:
      return _handleUnauthorized(err, handler);   // Single-flight token refresh
    case 403:
      return _handleForbidden(err, handler);       // Permission denied
    case 429:
      return _handleRateLimited(err, handler);     // Rate limit wait
    case >= 500:
      return _handleServerError(err, handler);     // Server error
    default:
      return _handleNetworkError(err, handler);    // Network error
  }
}
```

### Response Interception: Parsing Error Strategy from Business Codes

In addition to HTTP status codes, the interceptor inspects the response body for business error codes, selecting from 5 strategies:

```dart
@override
void onResponse(Response response, ResponseInterceptorHandler handler) {
  ServerTimeHelper.updateOffset(response.headers.value('x-server-time'));
  
  final body = response.data;
  final code = body['code'];  // Business error code
  
  if (code == 10000) {
    // Strategy: success — unwrap data payload
    response.data = body['data'];
    handler.next(response);
    return;
  }
  
  // Parse strategy from error config table
  final strategy = ErrorStrategy.getStrategy(code);
  
  switch (strategy) {
    case ErrorStrategy.success:
      response.data = body['data'];
      handler.next(response);
    case ErrorStrategy.refresh:
      _handleTokenRefresh(response, handler);
    case ErrorStrategy.security:
      EventBus().emit(GlobalEventType.deviceBanned);
      handler.reject(DioException(...));
    case ErrorStrategy.redirect:
      _handleRedirect(code, response, handler);
    case ErrorStrategy.toast:
      RadixToast.show(body['message'] ?? 'Unknown error');
      handler.reject(DioException(...));
  }
}
```

### Error Strategy Decision Table

Strategies are resolved from a static configuration table in [`error_config.dart`](JoyMini_Flutter_App/lib/core/network/error_config.dart):

| Business Code | Strategy | Action |
|-------------|----------|--------|
| `10000` | `success` | Unwrap `response.data` |
| Any token error | `refresh` | Single-flight token refresh + retry |
| `92001` | `redirect` | Navigate to settings page |
| `93001` | `redirect` | Navigate to KYC verification |
| `18023` | `redirect` | Navigate to phone binding |
| `deviceBlacklisted` | `security` | Lock app, emit deviceBanned |
| `deviceNotTrusted` | `security` | Lock app, emit deviceBanned |
| No match | `toast` | Show error toast |

Resolution priority is:
1. `successCodes` (code 10000) → unwrap
2. `tokenErrorCodes` → refresh
3. Lookup in `_strategyMap` → redirect or security
4. No match → toast

## 3. Single-Flight Token Refresh

The most architecturally significant feature is the single-flight token refresh pattern. When multiple requests return 401 simultaneously, only one refresh request is initiated — all others wait for the same result:

```dart
Future<void> _handleUnauthorized(
  DioException err,
  ErrorInterceptorHandler handler,
) async {
  // Guard: prevent infinite retry recursion
  if (err.requestOptions.extra['__retryAfterRefresh__'] == true) {
    // Already retried after refresh — no more loops
    handler.reject(err);
    return;
  }
  
  try {
    // Check if refresh is already in progress
    if (Http.refreshingFuture != null) {
      // Wait for ongoing refresh to complete
      await Http.refreshingFuture;
    } else {
      // Start new refresh — create Completer
      final completer = Completer<void>();
      Http.refreshingFuture = completer.future;
      
      try {
        final newToken = await Http.tryRefreshToken();
        Http.tokenCache = newToken;
        
        // Compare with latest token — if changed, another refresh occurred
        if (Http.latestToken != newToken) {
          // Token already updated by another refresh — skip
          return;
        }
        Http.latestToken = newToken;
      } finally {
        Http.refreshingFuture = null;
        if (!completer.isCompleted) completer.complete();
      }
    }
    
    // Retry original request with new token
    err.requestOptions.headers['Authorization'] = 'Bearer ${Http.tokenCache}';
    err.requestOptions.extra['__retryAfterRefresh__'] = true;
    
    final retryResponse = await Http.dio.fetch(err.requestOptions);
    handler.resolve(retryResponse);
  } catch (e) {
    // Refresh failed — redirect to login
    Http.performLogout();
    handler.reject(err);
  }
}
```

### Race Condition Protections

| Protection | Implementation |
|------------|---------------|
| **Completer Single-Flight** | `Http.refreshingFuture` — concurrent callers await the same Completer |
| **`__retryAfterRefresh__` Flag** | Prevents infinite retry loop if retry also returns 401 |
| **`latestToken` Comparison** | Detects if another refresh already completed and updated the token |
| **`navigatingToLogin` Guard** | Prevents multiple simultaneous navigations to login |

### Token Refresh Flow

```
Multiple 401s arrive concurrently
         │
         ▼
┌─────────────────────────────────────┐
│  Request A arrives first             │
│  → Check refreshingFuture (null)    │
│  → Create Completer                  │
│  → Set Http.refreshingFuture         │
│  → Call tryRefreshToken()            │
└─────────────────────────────────────┘
         │
         ▼ (Refresh in progress)
┌─────────────────────────────────────┐
│  Requests B, C, D arrive            │
│  → Check refreshingFuture (exists)  │
│  → Await the same Completer         │
│  → Wait for refresh to finish       │
└─────────────────────────────────────┘
         │
         ▼ (Refresh complete)
┌─────────────────────────────────────┐
│  All 4 requests retry in parallel   │
│  with new token                     │
│  → __retryAfterRefresh__ = true     │
│  → If still 401, no further retries │
└─────────────────────────────────────┘
```

## 4. Server Time Calibration

Every response (success or error) triggers server time calibration via the `x-server-time` header:

```dart
ServerTimeHelper.updateOffset(err.response?.headers.value('x-server-time'));
ServerTimeHelper.updateOffset(response.headers.value('x-server-time'));
```

This updates the local clock offset used by [`ServerTimeHelper`](JoyMini_Flutter_App/lib/utils/time/server_time_helper.dart), which is critical for:

- **Countdown Timers** — synced with server absolute time
- **KYC Session Expiry** — consistent timeout regardless of device clock drift
- **Event Timing** — accurate display of server-side timestamps

## 5. Zombie Callback Protection

A critical concern for long-lived interceptors is callbacks firing after a widget/page has been disposed:

```dart
// In GlobalHandler or consuming widget
UnifiedInterceptor.onTokenInvalid = () {
  if (!mounted) return;  // Zombie guard
  // Handle token invalidation
};

UnifiedInterceptor.onTokenRefresh = (newToken) {
  if (!mounted) return;  // Zombie guard
  // Update UI with new token
};
```

The interceptor itself does not hold widget references — instead, it exposes static callback slots (`onTokenInvalid`, `onTokenRefresh`) that widgets can register against. These slots are set up during bootstrap in [`AppBootstrap.setupInterceptors()`](JoyMini_Flutter_App/lib/app/bootstrap.dart).

## 6. Integration with the Rest of the System

```
Http (Static Class)
  ├─ _dio (Main Dio) ←── UnifiedInterceptor
  │   ├─ Header injection (device fingerprint)
  │   ├─ Error strategy dispatch
  │   └─ Single-flight refresh
  │
  ├─ _rawDio (Refresh-Only) ←── No interceptor
  │   └─ Used exclusively for token refresh itself
  │      (Prevents infinite interceptor loop)
  │
  ├─ tokenCache / refreshingFuture / navigatingToLogin
  │   └─ Shared static state with interceptor
  │
  └─ tryRefreshToken() / performLogout()
      └─ Bridge methods invoked by the interceptor
```

The dual Dio architecture (see [Http Static Class + Dual Dio + Native Adapter](http-static-class-dual-dio-native-adapter.md)) ensures that the refresh request itself does not trigger the interceptor's 401 handler, preventing infinite recursion.

## Key Takeaways

1. **`QueuedInterceptor`** ensures request ordering — critical for the single-flight refresh pattern to work correctly.
2. **5 Error Strategies** (`success` / `refresh` / `redirect` / `security` / `toast`) cover the full spectrum of API responses from success unwrapping to security lockdown.
3. **Single-Flight Token Refresh** uses the `Completer` pattern — concurrent 401 requests share one refresh request, then all retry in parallel with the new token.
4. **Triple Race Protection** (`__retryAfterRefresh__` flag, `latestToken` comparison, `navigatingToLogin` guard) prevents infinite loops and duplicate navigation.
5. **Per-Request Device Fingerprint Injection** enables backend risk control without modifying individual API endpoints.
6. **Per-Response Server Time Calibration** via `x-server-time` header keeps local time synchronized for countdowns and expiry.
7. **Zombie Callback Protection via `mounted` Checks** prevents crashes from callbacks firing after page disposal.
