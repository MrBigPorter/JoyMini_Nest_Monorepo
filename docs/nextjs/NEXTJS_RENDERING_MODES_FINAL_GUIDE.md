## 🔑 核心原理详解

### 1. 构建时生成 (`yarn build`)

**发生在 CI/CD 服务器上，部署之前**

```
开发者 git push → 构建机运行 yarn build → 所有 force-static 和 revalidate 页面全部预先生成好 HTML → 部署到生产服务器
```

用户永远不会看到这个过程
这个过程花多久都没关系
部署完成后所有页面已经存在硬盘上了

### 2. 正常访问 (`99.9% 的请求`)

**不会运行任何 JavaScript**

```
用户点击链接 → Nginx 看到这个 HTML 文件已经存在 → 直接把 .html 文件发回给浏览器
```

Node.js 进程甚至都不会被唤醒
响应时间 = 硬盘读取时间 + 网络时间
全世界任何地方打开都是 < 100ms

### 3. 过期后访问 (`每N分钟只发生一次`)

**后台静默更新，用户零感知**

```
当缓存过期后第一个人访问时：

1.  Next.js 立刻把旧缓存返回给这个用户
2.  同时在后台默默启动一个线程重新渲染新版本
3.  渲染完成后替换缓存
4.  之后所有用户拿到新版本
```

**没有任何人需要等**
即使渲染花了3秒也没有人会看到
全世界只有你知道这件事发生过

## 🎯 项目页面决策矩阵

| 页面     | 最佳配置                    | 理由              |
| -------- | --------------------------- | ----------------- |
| 首页     | `revalidate = 60`           | 新文章1分钟内可见 |
| 分类页   | `revalidate = 300`          | 分类变化频率低    |
| 文章详情 | `revalidate = 3600`         | 文章几乎不会修改  |
| 标签云   | `revalidate = 3600`         | 标签基本不变      |
| 关于页   | `dynamic = 'force-static'`  | 永远不变          |
| 登录页   | `dynamic = 'force-static'`  | 永远不变          |
| 收藏夹   | `dynamic = 'force-dynamic'` | 每个用户都不同    |
| 个人中心 | `dynamic = 'force-dynamic'` | 每个用户都不同    |

## ⚠️ 常见错误模式

### ❌ 错误 1: `force-dynamic` + `revalidate` 矛盾

```typescript
// ❌ 错误
export const dynamic = "force-dynamic";
export const revalidate = 60;
```

只要你写了 `force-dynamic`，Next.js 就会完全忽略 `revalidate`，永远不会在构建时预渲染。

### ❌ 错误 2: 缺少 `generateStaticParams`

动态路由如果没有定义 `generateStaticParams`，Next.js 不会在构建时预渲染任何版本，第一个访问每个参数的用户都会遇到延迟。

### ❌ 错误 3: 全局 `dynamic = 'force-dynamic'`

这会禁用整个应用的所有静态优化，所有页面都变成动态渲染，这是性能最差的配置。

## 零骨架屏架构黄金法则

1.  **所有公共页面必须使用 ISR 或 Static**
2.  **只有用户私有数据页面才能使用 Dynamic**
3.  **动态路由必须定义 `generateStaticParams`**
4.  **永远不要在公共页面使用 `force-dynamic`**
5.  **过期时间设置在内容新鲜度和性能之间找到平衡**
