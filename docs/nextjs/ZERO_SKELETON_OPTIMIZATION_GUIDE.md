## ⚠️ Next.js 反直觉模式

### force-dynamic + revalidate 组合模式

这是 Next.js 15 中最强大也最少被理解的模式：

```typescript
// ✅ 完美的按需 ISR 模式
export const dynamic = "force-dynamic";
export const revalidate = 3600;
```

| 配置                      | 作用                                          |
| ------------------------- | --------------------------------------------- |
| `dynamic = force-dynamic` | 告诉 Next.js: **不要在构建时生成这个页面**    |
| `revalidate = 3600`       | 告诉 Next.js: **在运行时缓存这个页面 1 小时** |

### 实际行为

1.  ❌ 构建时不生成任何静态文件
2.  ✅ 第一个访问者触发实时渲染
3.  ✅ 渲染结果被缓存
4.  ✅ 接下来 3599 个访问者直接获得缓存结果
5.  ✅ 过期后第一个访问者触发后台重新验证

> ❗ 绝大多数开发者误解这两个配置是互斥的。实际上它们是完美的组合，产生纯粹的按需增量静态生成。

### ✅ 三重缓存组合拳

加上 CDN 缓存头，这三个配置在一起产生 1+1+1 > 10 的效果：

```typescript
// ✅ Next.js 15 完美缓存模式
export const dynamic = "force-dynamic";
export const revalidate = 3600;

export async function generateHeaders() {
  return {
    "Cache-Control": "public, s-maxage=3600, stale-while-revalidate=86400",
  };
}
```

| 配置                           | 缓存层级                | 缓存时间 |
| ------------------------------ | ----------------------- | -------- |
| `revalidate = 3600`            | Next.js 服务器缓存      | 1小时    |
| `s-maxage=3600`                | Cloudflare 全球边缘缓存 | 1小时    |
| `stale-while-revalidate=86400` | Cloudflare 后台静默更新 | 24小时   |

### 最终效果

✅ **99% 的请求**：Cloudflare 边缘节点直接返回 <10ms
✅ **0.9% 的请求**：Next.js 缓存返回 <50ms
✅ **0.1% 的请求**：真正到达源站执行 ~200ms

> ✨ `stale-while-revalidate` 魔法：即使缓存过期了，用户仍然立刻得到响应，Cloudflare 在后台静默更新。用户永远不会等待。

## 🏛️ 四层架构设计

### 第零层：平台感知层

```
┌─────────────────────────────────────┐
│         Platform Detector           │
│  ┌─────┐  ┌───────┐  ┌──────┐     │
│  │ SSR │  │ Web   │  │ App  │     │
│  └─────┘  └───────┘  └──────┘     │
└─────────────────────────────────────┘
```

**核心能力**：

- 运行时环境检测（SSR/Web/App/H5）
- 动态选择最佳渲染策略
- 平台适配器配置

---

### 第一层：服务端渲染层

```
┌─────────────────────────────────────┐
│        Server-Side Rendering        │
│  ┌─────────────┐  ┌─────────────┐  │
│  │   ISR 60s   │  │ Edge Cache  │  │
│  └─────────────┘  └─────────────┘  │
└─────────────────────────────────────┘
```

**核心机制**：

- **ISR 60秒缓存**：页面级增量静态再生
- **Edge Cache**：Cloudflare Worker边缘缓存
- **流式SSR**：渐进式渲染，首字节优先

---

### 第二层：混合渲染层

```
┌─────────────────────────────────────┐
│      Hybrid Rendering Pattern       │
│  ┌─────────────┐      ┌───────────┐│
│  │ Server Comp │─────▶│Client Comp││
│  │ (Data Fetch)│      │ (UI/Inter)││
│  └─────────────┘      └───────────┘│
└─────────────────────────────────────┘
```

**核心模式**：

- **服务端组件**：数据获取 + ISR配置
- **客户端组件**：交互逻辑 + 动态更新
- **初始数据传递**：服务端 → 客户端无缝传递

---

### 第三层：客户端体验层

```
┌─────────────────────────────────────┐
│      Client-Side Optimization       │
│  ┌──────┐  ┌───────┐  ┌─────────┐ │
│  │Prefetch││Progress│  │Cache   │ │
│  └──────┘  └───────┘  └─────────┘ │
└─────────────────────────────────────┘
```

**核心优化**：

- **智能预取**：视口内链接自动预取
- **导航过渡**：微进度条代替全屏骨架
- **平台缓存**：Web/App/H5差异化缓存策略

```
┌─────────┐    ┌─────────┐    ┌─────────┐
```

## 🔄 骨架屏优化逻辑

### 显示决策树

```
是否已有初始数据？
    ├── 是：直接显示内容，后台静默更新
    └── 否：是否正在加载？
        ├── 是：显示骨架屏
        └── 否：显示错误/空状态
```

**核心原则**：

- 有缓存数据时**永远不显示骨架**
- 骨架只覆盖真正动态的部分
- 静态内容（导航、布局）永远不骨架

## ⚠️ 关键决策点

### 1. 架构选择

- ✅ **混合渲染**：服务端组件 + 客户端交互
- ❌ **纯服务端**：失去客户端交互能力
- ❌ **纯客户端**：无法利用ISR缓存

### 2. 缓存策略

- ✅ **平台差异化**：Web ISR / App持久化 / H5内存
- ❌ **统一缓存**：无法发挥各平台优势

### 3. 迁移策略

- ✅ **渐进迁移**：首页先行，逐步扩展
- ❌ **一次性迁移**：风险高，回滚困难

## 📁 实施文件结构

### 混合渲染模式文件结构

```
app/[locale]/
├── page.tsx              # 服务端组件（Web/SSR/ISR）
├── page.client.tsx      # 客户端包装组件
├── components/
│   ├── ArticleList.server.tsx  # 服务端数据获取
│   └── ArticleList.client.tsx  # 客户端交互
└── platform/
    └── adapters/
        ├── ssr.adapter.ts      # 服务端渲染适配器
        ├── app.adapter.ts      # App端适配器
        └── web.adapter.ts      # Web端适配器
```

### 平台适配器结构

```
lib/platform/adapters/
├── ssr.adapter.ts      # SSR渲染适配器
├── app.adapter.ts      # App端适配器（SQLite缓存）
└── web.adapter.ts      # Web端适配器（ISR缓存）
```

### 数据服务结构

```
lib/platform/services/
├── data.service.ts     # 平台感知数据服务
└── sqlite.service.ts   # App端SQLite服务
```

### 迁移实施步骤

1. **备份现有组件**：`cp page.tsx page.client.tsx`
2. **创建服务端组件**：新的`page.tsx`（服务端组件）
3. **重构组件逻辑**：分离服务端/客户端职责
4. **集成平台服务**：实现`data.service.ts`
5. **测试验证**：本地测试 + 部署验证

### 关键文件职责

| 文件                | 职责                     | 平台支持  |
| ------------------- | ------------------------ | --------- |
| `page.tsx`          | 服务端数据获取 + ISR配置 | Web/SSR   |
| `page.client.tsx`   | 客户端交互 + 动态更新    | 所有平台  |
| `data.service.ts`   | 平台感知数据获取         | 所有平台  |
