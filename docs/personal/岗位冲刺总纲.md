## 7. 简历

### 7.1 精炼版（粘简历）

> **JoyMini 智能客服 Agent**｜Node.js · TypeScript · LangGraph.js · PostgreSQL/pgvector · Redis · DeepSeek
> 基于 LangGraph StateGraph 构建 9 意图路由 + 8 域 Agent + 35 个业务工具的生产级客服系统，覆盖充值、提现、优惠券、订单、KYC 等真实业务；实现 4 层 RAG 降级检索与写操作确认卡片，SSE 首 token 延迟 < __ s。

### 7.2 展开版

**技术栈：** Node.js / TypeScript / NestJS / LangGraph.js / Prisma / PostgreSQL + pgvector / Meilisearch / Redis / DeepSeek / Jina / SSE + Socket.IO

- 基于 LangGraph `StateGraph` 构建客服 Agent，实现 **9 类意图**路由到 **8 个业务域 Agent**，通过 `ToolRegistry` 注册 **35 个业务工具**，单轮可串联多个工具完成复杂业务（查订单 → 查钱包 → 发起提现）
- 设计 **4 层降级 RAG 检索**：pgvector 语义 → Meilisearch BM25 → Chunk 关键词 → 整档关键词，合并去重后 rerank 重排，任一底层不可用自动降级
- 实现**多供应商 Embedding/Rerank 降级链**（Gemini → Groq → Infinity → Jina → Ollama），单一供应商故障时检索不中断
- 设计**写操作三层防护**：Agent Loop 拦截 5 类资金/资产工具 → 服务端一次性 token（Redis `GETDEL` 原子消费、60s 过期、userId 绑定）→ 资金类叠加 OTP 双验证
- 实现**三级转人工**：关键词情绪检测 → LLM 判断 → 工具结果标记；转人工写入 `handlerId` 状态，10 分钟无响应自动回收给 AI
- 基于 Redis 实现 **5 层限流**（IP / 设备 / 用户 / 全局并发 / 令牌桶）+ 熔断，保护 LLM 调用成本
- 前后端全栈交付：NestJS 后端 + Next.js 管理台 + Flutter 客户端，确认卡片、消息推送、转人工状态全链路打通

### 7.3 亮点四条（每条是决策，不是功能）

**亮点 1：AI 不允许直接动钱——三层写操作防护**
- 拦截层：Agent Loop 里识别 5 类写工具，不执行，转为待确认
- 凭证层：服务端签发一次性 token，`GETDEL` 原子消费 + userId 绑定 + 过期时间
- 验证层：资金类追加 OTP，token 与验证码双闸门
- 判断依据：**权限不能由模型决定**。Prompt 里写"请先确认"是可绕过的，只有服务端凭证是真的

**亮点 2：多供应商降级链**
- 向量检索依赖外部 Embedding API，任何一家都可能限流或宕机
- 按顺序探测 provider，失败自动切换；reranker 不可用时回落到原始分数排序
- 判断依据：RAG 是增强不是命脉，不能因为 embedding 挂了让整个客服不可用

**亮点 3：意图融合而不是单选**
- pgvector 余弦（0.7）+ Meilisearch BM25（0.3）双路召回后融合
- 分数差过小时不强行选一个，交给 LLM 二次判断
- 判断依据：中文短问句上单一路径不稳定，语义与关键词各有盲区

**亮点 4：转人工是状态机，不是一个标记**
- 三级触发 + `handlerId` + 时间戳 + 10 分钟自动回收
- 判断依据：单纯 `isHuman=true` 会让 AI 永久失联

### 7.4 难点四条（每条落到通用模式）

**难点 1：流式输出与消息落库的时序分离**
- 问题：转人工和确认卡片两条分支提前 return，`onDone` 不触发，前端一直转圈
- 方案：统一收口到 `finalizeAfterStream`，三路分支各自保证终态事件
- 模式：**流式系统的终态必须穷举**，任何一条 return 路径不闭环就是"AI 零回复"

**难点 2：State reducer 的覆盖 vs 追加**
- 问题：`pendingConfirm` 用 `b ?? a`，上一轮确认卡片残留到下一轮
- 方案：每轮显式置 `null`，reducer 改为纯覆盖
- 模式：**有状态 Agent 的"轮次"必须有显式边界**

**难点 3：中文检索的 tokenizer 陷阱**
- 问题：英文 tokenizer 把中文整句清空；SQL 占位符错位导致必然报错，再被 catch 静默吞掉
- 方案：中文分词 + 占位符对齐 + 降级路径计数告警
- 模式：**降级路径不可观测 = 没有降级，只有静默失效**

**难点 4：一次性凭证的生命周期**
- 问题：token 60s 与 OTP 300s 错配；先 pop 再验码，输错一次即销毁
- 方案：TTL 对齐 + 校验全部通过后再消费
- 模式：**一次性凭证的消费点必须在所有校验之后**

## 8. 面试题库与答法

> 基于一份真实面试记录的逐题拆解：[真实面试逐题拆解](./真实面试逐题拆解.md)（17 题追问链 + 35 题作答表 + 3 道困难题诚实答法）

### 8.1 履历一致性（最危险的一段）

面试官会用封闭问题链锁事实：离职月份 → 空窗期 → 项目时间 → 是否在职 → AI 经验是否自学。

**准备一张口径卡，背死，全程不改口：**

| 问题 | 你的固定答案 |
|---|---|
| 这份 AI 项目是公司项目还是个人项目？ | ________（三选一，写死） |
| AI 相关经验多久？ | ________ |
| 空窗期在做什么？ | ________ |

**推荐口径：**「个人项目，按生产标准做的」——你有 P0 审计清单、有真实资金业务，这个说法比含糊其辞强得多，而且可验证。

**三条红线：**
1. 不要把"知道"说成"做过"
2. 不要编在职经历
3. 不要抄别人的项目数字（15 步、15 倍成本、60% 降本都不是你的）

### 8.2 Agent 架构（主战场）

**Q：你的 Agent 怎么决定调哪个工具？**
A：两层。第一层意图路由，pgvector + BM25 融合出 top 意图，映射到 8 个域 Agent；第二层才是 LLM 在该域工具集里做 Function Calling。没有让一个 Agent 拿全部 35 个工具——工具太多模型选不准，先按域裁剪到 2-7 个。

**Q：为什么不用一个 Agent 加全部工具？**
A：35 个工具塞一个 prompt，token 成本高，工具描述互相干扰，模型容易选错。按域拆分后决策空间小，准确率和成本都更好。代价是路由错时用户得到域外回答，所以阈值设得谨慎。

**Q：LangGraph 和 LangChain 的区别？**
A：LCEL 是线性管道，适合固定步骤；LangGraph 是有向图，支持循环、条件路由和检查点。客服需要"用户改主意"（先说查订单，中途要提现），这是状态迁移不是管道，所以用图。检查点让中断恢复成为可能。

**Q：你的状态存在哪？**（⚠️ 高风险题）
A：现在是 `MemorySaver`，进程内内存。这是我明确的短板：重启即失忆、多实例不共享、无法恢复中断。生产方案是 `@langchain/langgraph-checkpoint-postgres`，thread_id 用 `userId:conversationId`，业务侧会话归档走 PG，Redis 只放短期缓存和限流计数。
> **按实话说。** 这题答"我在改"比答标准答案强十倍。

**Q：怎么防止 AI 执行危险操作？**
A：三层。Agent Loop 拦截写工具不执行；服务端一次性 token，`GETDEL` 原子消费；资金类再加 OTP。核心是权限由服务端算，不由模型决定。

**Q：ReAct 和 Plan-and-Execute 的区别？**
A：ReAct 边想边做，动态决定下一步；Plan-and-Execute 先拆计划再执行。我的客服场景步骤短、分支多，ReAct 更合适；如果要做"多日行程规划"这类长任务，才需要显式计划。

### 8.3 RAG（你的素材最扎实的一题）

**Q：RAG 的原理和你怎么做的？**
A：不是把所有知识塞进模型，而是提问时实时检索相关片段拼进上下文。我的实现是 4 层降级：pgvector 语义 → Meilisearch BM25 → chunk 关键词 → 整档关键词，合并去重后 rerank 取 topK。多层的原因是不同的查询形态各有盲区——语义能跨语言，关键词能精确匹配货号。

**Q：怎么提高 RAG 准确度？**
A：先定位问题在检索还是生成。没召回就去优化数据、切分、embedding、混合检索和 rerank；召回了但答不准就优化上下文组织、prompt 约束和引用。我实际踩过的坑：英文 tokenizer 处理中文会把句子清空、rerank 没有相关性门槛导致不相关内容也进上下文、向量检索没有分数阈值。

**Q：文档量多大？**（⚠️ 必须精确）
A：27 篇文档（95,374 字符），按 500 字符 / 50 重叠切分，共 **311 个 chunk**。规模不大，重点是把解析、切分、向量化、检索、引用、评测的完整链路跑通，而不是堆文档量。

**Q：RAG 效果怎么评估？**（⚠️ 主动承认）
A：目前是人工抽查加日志看 top 分数，**这是我正在补的**——100 条 golden set，按意图准确率、检索命中率、答案忠实度三项跑回归。

### 8.4 工程化

**Q：AI 生成代码出错怎么办？**
A：测试、运行、日志、缩小范围，要求 AI 给出原因和方案，最后人工验证。我的习惯是小步提交、先计划后执行、看 diff。

**Q：AI Coding 占比多大？**
A：按任务分——CRUD、DTO、测试、文档这类重复性工作 AI 参与度高；业务规则、状态机、资金链路我自己设计和审核。真实比例约 ____%。

**Q：模型怎么选？**
A：按任务和成本分。主生成用能力强的模型，分类和结构化输出用便宜的。我在项目里做了多供应商降级链，单一供应商故障不影响主流程。

**Q：做过微调吗？**
A：没有。我优先做应用层调优——prompt、上下文、RAG、工具约束、评测。微调放在有稳定数据、且应用层手段到顶之后再考虑。
