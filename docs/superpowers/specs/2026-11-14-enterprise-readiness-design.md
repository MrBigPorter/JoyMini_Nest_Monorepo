# 企业级化设计方案（AI 全栈方向）

> 日期：2026-11-14
> 目标时间窗：2027 年换工作，前置准备 6 周
> 相关文档：`docs/system-review/系统重点与难点.md`、`docs/current-task.md`

---

## 1. 为什么做

### 现状

这是一个可运行的 AI 客服系统（NestJS + LangGraph + PostgreSQL + Redis + Meilisearch），已完成：双路意图召回、四层 RAG、工具注册与写操作截停、转人工状态机、两阶段 SSE、结构化日志与 traceId、63 题评测回放、部署与回滚。

### 问题

面向「大模型应用开发 / AI 全栈」岗位，当前有三类缺口会在面试中被拆穿：

1. **可被当场证伪的缺陷**：工具参数里的 `userId` 由 LLM 提供；多实例部署后状态与消息投递都会断；没有任何 token 预算。
2. **没有质量闭环**：只有 63 题意图准确率，不知道「问题有没有被解决」，线上差评不会回流到评测集。
3. **全栈叙事不完整**：前端有真实设计（RSC 预取、缓存 tag 失效），但全仓 0 个 `useMutation`、0 个乐观更新，类型契约三处手工维护。

### 成功的定义

能对着代码回答以下三句话，且每一句都有可演示的证据：

> 「这套系统每周自动跑 150 题，线上差评会自动进评测集。」
> 「AI 的每一个写操作都要过三道闸门，而且 userId 不可能由模型提供。」
> 「单会话 token 超预算会降级，用户断连会中止推理。」

## 2. 目标 / 非目标 / 反目标

### 目标

- **G1 堵致命缺陷**：越权路径、多实例断链、无成本约束。
- **G2 建质量闭环**：评测集扩容 → 任务成功率 → 线上反馈回流。
- **G3 前端收口**：写操作用 `useMutation` + 乐观更新；类型契约单一来源。
- **G4 交付证据**：质量报告、演示脚本、边界文档。

### 非目标

- 不做多租户 / 租户隔离。
- 不做多渠道接入（WhatsApp、Web Widget）。
- 不做 A/B 实验平台与灰度发布系统。
- 不做 DDD 重构，不改意图标签体系（仍为 9 个）。
- 不替换或移除 LangGraph。

### 反目标（做到也算失败）

- 为「看起来企业级」引入 K8s、服务网格、消息中间件全套。
- 为了加能力而改坏资金正确性（条件更新、CAS、单一结算出口）。
- 只做面板没有真实数据支撑（例如仪表盘写死数字）。

---

## 3. 约束

- **人力**：单人，每周约 3 个工作日，总窗口 6 周。
- **环境**：本地 Colima 4GB 内存；AI 全套约 4GB，需分阶段启动。
- **部署**：线上单 VPS。多实例只能在本地用 compose 起两个副本验证。
- **依赖**：不引入付费新服务；embedding / reranker 已有。
- **回归**：现有单测（`yarn workspace @lucky/api test`）必须保持绿；已知的 2 个过期套件不在此列。

---

## 4. 方案对比与选择

| 方案 | 内容 | 做完的样子 | 代价 |
|---|---|---|---|
| A 横向补全 | 按缺口清单逐项清 | 什么都对，但每块都是标准做法 | 4 个月，有广度无纵深 |
| B 纵向做深 | 只做评测与质量闭环到极致 | 一个别人问不倒的专长 | 基础题可能答不上 |
| **C 双线（选中）** | 前 2 周堵缺陷 → 1 周闭环 → 1 周前端 → 2 周交付 | 完成度 + 一条主线 | 4 个月版本压缩为 6 周，两条线都不极致 |

**选 C 的理由**：AI 全栈岗的筛选靠广度（问到多实例、成本、类型答不上就减分），定级靠深度（有没有一块问不倒）。C 两头都能交代；且横向阶段里的「反馈采集」本身就是评测闭环的入口，两段自然衔接。

## 5. 设计

### 5.1 阶段一（第 1-2 周）：堵致命缺陷

#### 5.1.1 `userId` 从工具 schema 收口

**现状**：工具参数由 LLM 生成，若 schema 中允许 `userId`，用户可通过 prompt 指定他人身份。

**做法**：从 9 个领域工具的 schema 中删除 `userId` 字段；工具改为工厂函数 `createXxxTools(ctx: { userId })`，由调用链闭包注入；Agent 执行时不能覆盖。

**验收**：构造一次「把 userId 换成别人」的对话，工具调用里不出现该参数，且数据仍属于当前用户。

#### 5.1.2 工具能力策略（不依赖 RBAC）

**修正**：原设计写"校验当前用户角色"，但客户端用户没有角色体系——客户端 JWT 只签 `{ sub }`，`User` 表无 role 字段，RBAC 只存在于 `AdminUser`。新增角色体系属于过度设计。

**做法**：`ToolRegistry` 注册时声明**能力标记**：`read` / `write` / `requiresOwnership`。执行前校验：
- 工具声明 `requiresOwnership` 时，注入的身份必须与工具要操作的数据主体一致；
- 工具声明 `write` 时，必须处于确认流程中（见 5.1.1/F4），否则拒绝执行。

拒绝返回结构化结果（不是异常），并在结构化日志留下 `tool.denied` 事件。

**验收**：构造一个参数指向他人数据的调用，被拒且日志可查；未走确认流程直接调用写工具，被拒。

#### 5.1.3 PG Checkpointer

**现状**：`MemorySaver`，进程内。

**修正**：原设计写"`thread_id` 取 `conversationId`"，但代码里已有 `Conversation.threadId`（随机 UUID），同时被用作 LangGraph thread_id、Redis 热缓存 key 和回查键。改键会让历史会话状态断裂。

**做法**：
- `thread_id` **沿用现有 `Conversation.threadId`**，零迁移；
- checkpoint 表通过 **Prisma 迁移**创建（不走运行时 `setup()`），保证线上只需 `prisma migrate deploy` 权限，回滚可控；
- 保留 `MemorySaver` 作为无数据库环境的降级，但必须打 `warn`。

**验收**：重启后端后，同一会话的 `previousIntent`、`messages`、`flowState` 仍在（注意：`pendingConfirm` 不在 `AgentState` 中，确认令牌本来就存 Redis，不受重启影响——原验收写错了字段）；两台实例交替处理同一会话，状态一致。

#### 5.1.4 Socket.IO Redis Adapter

**做法**：`main.ts` 使用 `RedisIoAdapter`（`@socket.io/redis-adapter`），复用现有 Redis 连接配置。

**验证方式（原设计未考虑部署约束）**：`compose.yml` 的 backend 固定了 `container_name`，nginx 只指向单个 backend，且 Colima 4GB 放不下两个容器 + 完整 AI 栈。

**做法**：用**两个宿主机 Node 进程（不同端口）**验证，不改 compose/nginx。跨实例推送用「在 A 进程主动 emit 一条测试事件」的方式构造，而不是依赖 Socket 发送路径（Socket 发送天然在连接所在实例处理，无法路由到 B）。

**验收**：A 进程 emit 的消息，能被连在 B 进程的客户端收到。

#### 5.1.5 成本护栏

**口径（原设计不一致，此处定死）**：两级计数，各管一件事。

| 维度 | Key | 目的 | 超限动作 |
|---|---|---|---|
| 用户日累计 | `cost:u:{userId}:{yyyymmdd}` | 防滥用 | 拒绝新会话，提示稍后再试 |
| 单会话累计 | `cost:c:{conversationId}` | 防单轮跑飞 | 强制降级为静态话术并转人工 |

**做法**：数据源为既有 `llm.usage` 事件；两级都超限时以单会话降级优先（用户体验优先于限流）。触发时写 `cost.guard` 事件，携带 `{scope: user|conversation, tokens, limit}`。

**验收**：分别构造"一个用户多会话"和"一个会话多轮"两种场景，两种降级动作都按上表发生且留痕。

#### 5.1.6 断连取消

**做法**：SSE `close` 事件创建 `AbortController`，沿 `ai-customer.service → orchestrator → agent-runner → LLM` 传递；LangGraph 侧通过可中断的调用点退出；已产生的部分输出不回滚。

**验收**：连接建立后立即断开，服务端在超时内停止模型调用（日志无后续 `llm.usage`）。

### 5.2 阶段二（第 3 周）：质量闭环

#### 5.2.1 评测集扩容

**做法**：63 → 150 题，按 9 个意图分层（每层 ≥12），补齐 `rag` 样本；入库前与 `intent_examples` 查重。

**验收**：分层统计每意图都有独立数字；查重命中时回放被拒绝。

#### 5.2.2 任务成功率

**做法**：在回放中增加「任务是否完成」判定，输入为（用户问题、AI 回复、工具调用序列），输出 `solved / partial / unsolved`；人工抽检 10% 校准 judge 准确率。

**Judge 来源（评审提出，已定）**：新增一个与被测模型**不同厂商**的便宜 API（如 Qwen / GLM / Kimi 之一），仅用于周级评测，月成本在几元量级。选它而不是：
- 本地 Ollama —— 4GB 内存放不下，且项目已明确不需要本地 LLM；
- 同厂商另一模型 —— 同语料同偏好未完全避开，违背 D4 初衷。

**评测执行方式（评审提出，已定）**：用**固定 fixture 用户**（预置订单/钱包/券/KYC 数据），只读工具真实执行；写工具不真实执行，只判定「是否正确生成了确认卡片」。这样既不污染真实数据，又能评到任务链路。评测集 schema 需从 `{id,input,expect}` 扩展为带 `fixtures` 与 `expectTask` 的形态。

**验收**：报告中同时出现意图准确率与任务成功率；人工抽检一致率 ≥80%。

#### 5.2.3 反馈采集

**归属修正（用户已定）**：评价入口做在 **admin 端**，不是 Flutter 端。因此评价主体是**客服**，定位为「客服质检标注」，不是终端用户满意度。叙事要相应调整。

**做法**：
1. **显式标注**：admin 会话页对 AI 消息提供「正确 / 有误」标注 + 错误类型枚举（答非所问、信息过时、越权试探、格式错误）；数据落 `ai_feedback` 表。
2. **隐式信号**：用户转人工、同一问题重复追问、会话中途放弃，作为弱反馈写入同一张表（`source` 字段区分）。
3. 两类信号都进入待标注列表，可导出为评测集样本。

**验收**：客服标注一次 → 落库 → 出现在 badcase 导出中；构造一次"重复追问"，隐式信号同样落库且 `source` 可区分。

### 5.3 阶段三（第 4 周）：前端收口

#### 5.3.1 乐观更新

**范围（原设计未定，此处定死）**：全仓约 65 处写调用，1 周内全量迁移不现实。

**做法**：只覆盖 **3 个代表性页面**——用户管理、订单列表、财务审核。其余迁移留作后续。三个页面必须同时处理现有的 Server Action + `revalidateTag` 缓存失效（`src/lib/actions/*-revalidate.ts`），不能只改客户端。

**验收**：断网时在三个页面各点一次写操作，UI 立即变化，失败后回滚并提示；成功时列表与首页统计同步更新。

#### 5.3.2 类型契约

**做法**：从后端生成 OpenAPI（Nest Swagger 已有基础），用 `openapi-typescript` 生成类型，替换 admin 手工维护的 `src/type/types.ts` 中与后端重叠的部分；CI 增加「生成物与提交物一致」检查。

**验收**：后端改一个字段，前端类型检查能报错。

### 5.4 阶段四（第 5-6 周）：交付物

- 一份质量报告（意图准确率 + 任务成功率 + 分意图明细 + 与上次对比）
- 一个演示脚本：一条命令跑通「正常问答 / 转人工 / 模型故障降级 / 成本降级」
- 系统边界文档：已知缺口、为什么不补、补的话怎么补

## 6. 关键决策

| # | 决策 | 替代方案 | 理由 |
|---|---|---|---|
| D1 | Checkpointer 用 PostgreSQL | Redis / 自研表 | 已有 PG；LangGraph 官方包自带建表；与业务数据同库便于排查 |
| D2 | 任务处理幂等键 = `messageId` | `conversationId + seqId` | 消息 ID 天然唯一，且发送方已保证唯一 |
| D3 | 成本计数放 Redis 而非 PG | PG 计数表 | 高频写、可容忍丢失、TTL 自动清理 |
| D4 | Judge 模型与被测模型不同 | 同一模型自评 | 同模型自评有系统性偏好，结论不可信 |
| D5 | 前端类型用 OpenAPI 生成 | 手写 / zod 运行时校验 | 已有 Swagger；生成成本最低，CI 可卡漂移 |

## 7. 验收标准（整体）

- [ ] 重启后端不丢会话状态
- [ ] 两副本部署下消息可跨实例送达
- [ ] 工具参数中不存在 `userId`
- [ ] 单会话 token 超阈值触发降级并留痕
- [ ] 断连后模型调用在 5 秒内停止
- [ ] 评测集 ≥150 题，按意图分层统计
- [ ] 报告含任务成功率与人工校准一致率
- [ ] 差评可落库并进入 badcase 导出
- [ ] admin 写操作有乐观更新与失败回滚
- [ ] 后端改字段前端类型检查报错
- [ ] 全量单测保持绿

## 8. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 取消信号穿透不到 LLM SDK | 断连仍继续烧 token | 先做最小验证（单 Agent 场景），确认可行再全链路改 |
| Checkpointer 序列化失败 | 会话状态写不进 | 先在本地用两条真实会话验证，再切默认 |
| Judge 偏差大 | 任务成功率不可信 | 人工抽检 10%，一致率低于 80% 则调整 prompt 或改人工标注 |
| 6 周做不完 | 半成品 | 阶段一独立可交付；阶段二/三可裁掉不影响"能讲" |
| 改坏资金逻辑 | 生产事故 | 任何涉及资金文件的改动必须跑既有并发测试；不改条件更新语句 |
