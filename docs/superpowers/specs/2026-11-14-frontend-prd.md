# 前端 PRD

> 日期：2026-11-14
> 范围：`apps/admin-next`（主）、`apps/frontend-blog`（次）
> 定位：把前端从「架构上做对了」推到「叙事上站得住」
> 关联：`2026-11-14-enterprise-readiness-design.md`

---

## 1. 目标

admin 的架构底子是好的：Server Component 预取 + HydrationBoundary 注水、URL 作为筛选状态源、Next Data Cache 按 tag 失效、HTTP 层做单飞 refresh 与请求去重。

问题在于**三处「说得到但翻代码就露」**：

```
一：写操作没有统一的变更模型    → 全仓 0 个 useMutation、0 个乐观更新
二：类型契约三份手工维护        → 后端 DTO / 前端 1875 行手写 / shared 只共享枚举
三：服务端预取只管第一屏        → 表格翻页后走另一套手写数据流
```

本 PRD 要求：把这三处补上，让「全栈」两个字经得起看代码。

## 2. 用户与场景

| 用户 | 场景 | 关心什么 |
|---|---|---|
| 运营人员 | 每天处理订单、审核提现、回客服消息 | 点了立刻有反馈，失败要能看出来 |
| 开发者 | 后端加字段、改接口 | 前端类型能自动跟着变 |
| 面试评审者 | 翻代码 | 这个人的前端是不是只会堆组件 |

## 3. 功能需求

### F1 写操作统一用 mutation + 乐观更新

- **范围：3 个代表性页面**（用户管理、订单列表、财务审核），不做全量迁移（全仓约 65 处写调用）。
- 这三个页面的写操作统一走 `useMutation`，并同时处理现有的 Server Action + `revalidateTag` 失效链路。
- 列表与详情在提交时立即更新 UI，失败回滚并提示。
- 成功后就地刷新相关查询，不整页重载。

**验收**：断网状态下点「禁用用户」，列表立即变化，请求失败后回滚并提示。

### F2 缓存一致性

- 写成功后同时失效两层：React Query 的查询缓存、Next Data Cache 的对应 tag。
- 失效范围必须明确到受影响的列表与统计，不得全站刷新。

**验收**：修改一个订单后，列表与首页统计都更新，其他无关页面不重新请求。

### F3 类型契约单一来源

- 与后端重叠的类型由后端生成，不手写。
- 生成物与提交物不一致时，CI 报错。
- `packages/shared` 只保留真正跨端共享的枚举与常量，不重复定义 DTO。

**验收**：后端给某接口加一个必填字段，前端类型检查立即报错。

### F4 AI 会话页体验

- 流式回复逐段渲染，连接状态可见（连接中/流式中/已结束/已断线）。
- 需要用户确认的动作以卡片呈现，明确展示将要执行的内容与影响。
- **客服质检标注**：客服可对 AI 回复标注「正确 / 有误 + 错误类型」，不是终端用户点赞点踩（终端用户在 Flutter 端，本次不动）。
- 提供待标注列表，可按错误类型筛选与导出。

**验收**：断线时 UI 明确提示，不假装还在生成；确认卡片展示的参数与后端实际执行一致。

### F5 服务端与客户端数据流统一

- 首屏预取与后续翻页使用同一套查询模型，不出现「第一屏来自 RSC、后面来自手写 fetch」。
- URL 始终是筛选条件的唯一来源，刷新与前进后退不丢状态。

**验收**：翻页三次后刷新页面，页码与筛选条件完全恢复。

## 4. 非功能需求

| 编号 | 要求 |
|---|---|
| N1 | 首屏 LCP 不因引入 mutation 而退化 |
| N2 | 所有写操作必须有失败态与重试入口 |
| N3 | 不引入新的 UI 库；沿用 `@repo/ui` 与既有 scaffold |
| N4 | 国际化文案必须走 i18n，不硬编码中文 |

## 5. 现有能力盘点

已具备：

- RSC 预取 + HydrationBoundary 注水（约 14 个页面）
- URL 作为筛选状态源
- Next Data Cache tag 失效链路
- HTTP 层：GET 单飞、写请求去重、并发 401 单飞 refresh、指数退避
- ModalManager（module store + useSyncExternalStore + createPortal）
- 两套 i18n 方案（admin 无 locale 前缀、blog 有）

## 6. 已知问题（本 PRD 要求处理）

| 问题 | 处理方式 |
|---|---|
| 表格首屏与翻页数据流不一致 | F5 统一 |
| 类型三份手工维护，生成物零引用 | F3 收敛 |
| 无 optimistic update | F1 补齐 |
| Modal 场景靠额外传 `t` 绕过 Context | 记录为技术债，本次不修 |

## 7. 不做

- 重构 admin 的整体信息架构
- 替换两代并存的表格组件（SmartTable / BaseTable）
- 引入 tRPC
- 重做 blog 的 ISR 与离线缓存

## 8. 验收总表

- [ ] 写操作均为 `useMutation` 且有乐观更新与回滚
- [ ] 写成功后两层缓存同时失效，范围精确
- [ ] 类型由 OpenAPI 生成，CI 卡漂移
- [ ] 会话页可展示连接状态、确认卡片、评价入口
- [ ] 翻页后刷新可恢复页码与筛选
- [ ] 首屏性能无退化
