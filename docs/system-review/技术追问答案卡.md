# 技术追问答案卡

> 用途：每个问题一张卡，五小时内能背完。
> 结构：**一句话答案**（30 秒内说完）→ **展开三点**（被追问时用）→ **诚实缺口**（主动说出来，比被问穿强）

---

## 卡 1 · 你的 hybrid search 为什么融合分数，不融合排名？

**一句话**：因为不同来源的分数不可比，名次可比。

**展开**：
1. 四层的量纲完全不同：余弦相似度 0~1、BM25 位置分、ILIKE 固定 0.5、文档分可能 >1。
2. 直接取最大值合并，会让某一层主导结果，而不是让真正相关的内容胜出。
3. 标准做法是 RRF：`Σ 1/(k + rank)`，只融合名次，天然免疫量纲问题。

**诚实缺口**：我用 reranker 兜住了——四层合并后用 cross-encoder 统一重打分，等于换了一把尺子。但 reranker 不可用时会退回原始分排序，量纲问题重新暴露。更稳的做法是先用 RRF 融合名次、再重排。

## 卡 2 · 你选了 512 的 chunk，为什么不是 256？

**一句话**：没有做过 ablation，就不能说"选的"，只能说"沿用的"。

**展开**：
1. chunk 大小是召回粒度与上下文完整性的权衡：太小语义碎片化，太大稀释相关性。
2. 判断依据不是直觉，是 Hit@k 与 context precision 的对比实验。
3. 正确做法：固定其余变量，跑 256 / 512 / 1024 三组，看指标拐点。

**诚实缺口**：项目里是固定切分策略，没做对比。这是一次半天的实验，我把它列进了待办。

## 卡 3 · reranker 提升了准确率，代价是多少延迟？

**一句话**：一次批量调用，大约 +100~200ms。

**展开**：
1. cross-encoder 是逐对打分，比 bi-encoder 慢，但精度高——这是 recall → precision 的两阶段分工。
2. 关键优化是**批量**：N 个候选一次请求，不是 N 次请求，往返次数才是延迟大头。
3. 必须有降级：reranker 超时或报错时回退到原始排序，宁可慢一点也不能让请求失败。

**诚实缺口**：目前没有实测 p95，只有设计预期。补一个延迟埋点就能出数。

---

## 卡 4 · hybrid search 赢了，那它在哪些 query 上输了？

**一句话**：短查询、纯专有名词、跨语言查询。

**展开**：
1. 极短查询（"退款"两个字）关键词打分会不稳，向量的语义优势也不明显。
2. 纯编号/型号（订单号、错误码）向量不敏感，反而是 BM25 的主场。
3. 跨语言是最大坑：中文 query 要先翻译再进关键词检索，翻译一失败整层失效。

**你的证据**：意图分类里 CJK 输入会先调一次 LLM 翻译成英文再查 BM25，就是为了这个。

## 卡 5 · 你怎么知道评测集没有泄进 prompt？

**一句话**：查重——规范化后精确匹配 + 高相似度近似匹配。

**展开**：
1. 如果评测句子本身就在例句库里，测出来的分数是"背答案"，不是泛化能力。
2. 本项目用 `intent_examples` 做近邻匹配，泄露风险是真实存在的，不是理论问题。
3. 查重应该做成回放前的硬门禁：有重合就拒绝入库并列出待替换项。

**诚实缺口**：目前没有实现查重。已列入方案，优先级不低——因为它会让所有历史数字失去意义。

## 卡 6 · LLM-as-judge 和你一致，它和用户一致吗？

**一句话**：不会自动一致，必须人工抽检校准。

**展开**：
1. judge 有三类系统性偏差：位置偏差（偏爱第一个）、长度偏差（偏爱长答案）、自偏好（偏爱同模型输出）。
2. 缓解手段：用**不同厂商**的模型、随机打乱候选顺序、控制答案长度。
3. 校准方式：抽 10% 人工标注，算 judge 与人的一致率，目标 ≥80%；低于就调 rubric 或改人工。

**诚实缺口**：目前还没有 judge，这一整套是阶段二的目标。

## 卡 7 · 召回率没变，MRR 掉了，没人动过 retriever，为什么？

**一句话**：问题在排序层，不在召回层。

**展开**：
1. MRR 只看"第一条命中排第几"，召回率看"有没有召回"——两者解耦。
2. 常见原因：合并去重的保留规则变了、rerank 权重变了、截断 topK 变了。
3. 排查顺序：对比同一批 query 的 top-k 列表差异 → 定位到具体是哪一步改了顺序。

**加分句**：所以监控要同时看召回率和排序指标，只看一个会漏掉整类回归。

## 卡 8 · Agent 会不会无限循环？

**一句话**：双保险——迭代上限 + 只统计"真的调了工具"的轮次。

**展开**：
1. 上限 `MAX_ITERATIONS = 3`，超过就退出循环。
2. 计数器只在出现 `tool_calls` 时递增，避免模型空转被算成一轮。
3. 超限时必须给出明确的收尾，而不是把最后的原始工具结果直接抛给用户。

**诚实缺口**：当前超限时会把最后一条 `ToolMessage` 的原始 JSON 返回（单 Agent 场景），且 `maxIterationsReached` 字段声明了但从没赋值。正确做法是返回"需要人工协助"并转人工。

---

## 卡 9 · 工具返回非法结构怎么办？

**一句话**：统一包装 + 喂给模型前剥壳，但前提是**真的统一**。

**展开**：
1. 设计约定所有工具返回 `{ ok, data }`，给模型前用 `stripToolResult` 剥掉包装。
2. 剥壳的意义是让模型看到干净数据，不被内部结构干扰。
3. 契约一旦被破坏，模型会看到两种形状的数据，行为不可预测。

**诚实缺口**：项目里 `tool-result.ts` 声称"所有工具都遵守"，实际有 3 个工具直接返回裸 JSON，错误也用了不同形状。已列入修复清单。

## 卡 10 · 模型超时或挂掉，用户不能什么都收不到，怎么办？

**一句话**：静态兜底 + 置位阻断 + 发事件 + 记原因，四件事一起做。

**展开**：
1. 落一条**静态**兜底话术——不能依赖已故障的模型生成道歉。
2. 把会话置为 `awaiting_human`，阻断下一轮继续失败。
3. 发出转人工事件，并记录 `transfer{source: fallback, reason: ai_error}`，让原因可统计。

**证据**：用故障注入（`__CHAOS__` 前缀 + Redis 开关，生产物理隔离）跑了 E2E，9 个场景全过。

## 用法建议

```
考前 10 分钟   只看每张卡的第一句
被追问时       用"展开三点"，每点一句，别展开成段
被问到底       主动说"诚实缺口"——这是加分项，不是减分项
```

**最重要的一条**：这十张卡里有 6 张的答案包含"我还没做"。**面试官要的不是完美，是你知道边界在哪。**
