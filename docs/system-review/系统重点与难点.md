## 1. 一页纸：12 条能背的话

1. **意图分类**是双路召回（pgvector 语义 + Meilisearch 关键词）加权融合，不是纯 LLM。
2. **门禁位置错位**是这套系统最值得讲的 bug：阈值卡在融合之前，导致单路略低的意图被提前淘汰。
3. **多 Agent 调度**不在图里，是 orchestrator 内部一个 for 循环——因为条件边会随意图组合爆炸。
4. **写操作三道闸门**：工具截停 → 一次性 token → 提现再过 OTP。
5. **RAG 四层全跑**，再用 reranker 统一量纲——因为余弦、BM25、ILIKE 的分根本不可比。
6. **转人工检测放在最前面**，因为"转人工"这种短句意图分天然低，放后面会被当闲聊。
7. **资金并发靠条件 UPDATE**，不靠分布式锁；锁只是减少冲突，不是正确性来源。
8. **领券先扣库存、后查限领**，正确性依赖 READ COMMITTED 的语句级快照。
9. **SSE 拆两段**：POST 带 body 换 streamId，GET 用 `?token=` 连流——因为 EventSource 不能设 header。
10. **traceId 用 AsyncLocalStorage** 穿透整条链路，事件总线入口自己生成。
11. **结构化日志绕过 Nest Logger**，因为它加前缀和颜色码会让 Loki 解析失败。
12. **golden set 回放打生产接口**，不复制 prompt——否则是自证测试。

## 2. 五条主线

### 2.1 AI 链路：意图分类 + 编排

**机制**：`intentRouter` → `orchestrator` 两个节点，其余全是普通 TS。

| 问题 | 答案 |
|---|---|
| 为什么只留两个节点？ | 旧架构 10+ 节点、65 行条件边，多意图组合让边数组合爆炸，且无法表达"product 必须先于 coupon"。改成 for 循环后，依赖排序、共享 messages、单 Agent 异常隔离都是普通代码 |
| 代价是什么？ | orchestrator 成了 700 行上帝节点；`streamEvents` 里所有模型调用都叫 `orchestrator`，无法按 Agent 区分 |
| StateGraph 还留着干什么？ | 只剩 checkpointer、streamEvents、未来的 interrupt/resume——**路由价值已经没有了** |

代码：`graph/customer.graph.ts:143-181`、`graph/nodes/orchestrator.node.ts:464-627`

**意图分类的真实结构**：

```
输入 → toLowerCase → (CJK 先 LLM 翻英文给 BM25)
                        ↓
        ┌───────────────┴───────────────┐
        ↓                               ↓
   pgvector TOP-5                 Meilisearch BM25
   逐条筛 >=0.70  ← 【关卡A】       按域取最高分
   按域取最高分                    (不过滤)
        └───────────────┬───────────────┘
                        ↓
              0.7×vector + 0.3×bm25
                        ↓
              rag/general 平局让位(0.02)
                        ↓
                  全部 <0.7 → LLM 兜底
```

**【已验证】三个关键细节**：

1. **关卡 A 在融合之前**（`intent-classifier.ts:317` 先过滤，`:343-364` 才融合）。向量 0.69 + BM25 0.90 的意图，本该融合成 0.753，实际走"单路打折"变成 0.27。
2. **BM25 单路上限 = 0.3**（`:355-362`），永远过不了 0.7 → **BM25 实际上只是"给已过线域加分"**，不能独立召回任何意图。
3. **`intent-router.node.ts:200` 的 `<0.5` 分支几乎不可达**——embedding 路径出来的标签最低也有 0.64。

**【已验证】还有一个串行化浪费**：`translateToEnglish` 在 `Promise.allSettled` **之前**被 await（`intent-classifier.ts:186` vs `:191`），注释却说"并行执行以减少延迟"。CJK 输入时白白多等一次 LLM 往返。

**多意图仲裁**：`MIN_SCORE=0.7` 去噪音 → 按域去重 → 单域直接跑 → 多域且 gap `<0.05` 才调第二次 LLM 判 `single/all/ask`。

> 注意：注释里写的 0.15 和 "close-contenders" 是上一版策略，代码已改成 0.05 + LLM 仲裁。**主动说出这件事，比假装一致强。**

#### 框架选型：LangChain 与 LangGraph 的分工

两者不是竞争关系，**LangGraph 建在 LangChain 之上**。

| | LangChain | LangGraph |
|---|---|---|
| 管什么 | 怎么跟模型、工具、数据源打交道 | 多步骤怎么走、状态存哪 |
| 形态 | 组件 + 组合（`Runnable` / `.pipe()`） | 有状态的图（节点 + 边 + 共享 state） |
| 特点 | 无状态、线性、适合单次调用 | 有状态、可循环、可恢复 |

**本项目实际用到的 LangChain（全仓统计）**：

| API | 次数 | 用途 |
|---|---|---|
| `tool` / `DynamicStructuredTool` | 12 | 把 TS 函数包成模型可调用的工具 |
| `ChatPromptTemplate` | 7 | 提示词模板 |
| `BaseMessage` / `HumanMessage` / `AIMessage` / `ToolMessage` | 14 | 统一的消息类型 |
| `StringOutputParser` | 5 | 输出转字符串 |
| `ChatOpenAI` / `ChatOllama` | 2 | 模型适配器 |
| `MarkdownTextSplitter` | 1 | 文档切分 |

**最值钱的一点**：代码调用的是 DeepSeek，但用的是 `ChatOpenAI` 类——因为 DeepSeek 兼容 OpenAI 协议。这就是抽象层的价值：换任何兼容服务，业务代码一行不改。

**LangGraph 在本项目里剩下的价值**（因为多 Agent 调度已挪进 for 循环）：

| 还在用 | 已经不用 |
|---|---|
| Checkpointer（跨轮状态） | 路由（条件边改成常量路由可退化为 `addEdge`） |
| `streamEvents`（token 流） | 多 Agent 调度（改为 orchestrator 内部循环） |
| 未来 interrupt / resume | — |

**state 的合并语义**（高频追问）：节点只返回增量，合并规则由 `Annotation` 的 reducer 决定。`messages` 用 `messagesStateReducer`（追加），`intent` 用 `(a, b) => b`（覆盖）——如果两者都用覆盖，多轮消息就只剩最后一条。

### 2.2 实时与转人工

**两阶段 SSE**（`ai-customer.controller.ts:105-256`）：

```
POST /chat  ──> 轻量限流 + 消息写 Redis(TTL 120s) ──> 返回 streamId
GET /chat/stream/:streamId?token=JWT
            ──> Lua 原子 consume(只能一次、校验 owner)
            ──> 用户独占 + 全局并发限流
            ──> 才真正跑 LangGraph，token 流式推
```

为什么要拆：
- EventSource / dart:io 的 GET **不能设 Authorization header** → 只能 `?token=`
- 消息体放 POST，避免进 URL 和访问日志
- LangGraph 在 GET 连上后才执行 → 不需要"连接前缓冲事件"

**代价（一定要主动说）**：`?token=` 会进 Nginx access log；断连不中止图执行；没有 resume。

**双通道投递**（`events.gateway.ts:225-250`）：

```
会话房间(conversationId)  ← 依赖客户端主动 join_chat，断线重连会丢
用户私有房间(user_<id>)   ← handleConnection 自动 join，重连必恢复
.except(conversationId)   ← 排除已在会话房间的连接，避免重复
```

成员列表每轮只查一次（`ai-customer.service.ts:241-255`），注释明确"不能每个 token 查库"。

**转人工状态机**：`handlerId` 单字段三态

```
null             → AI 处理中
'awaiting_human' → 排队中
真实 adminId     → 人工已接管
```

认领用 CAS：`updateMany({ where: { id, handlerId: 'awaiting_human', status: NORMAL } })`，改到 1 行=抢到。**0 行之后的 findUnique 只用来区分 404/409，不参与判定**——这个区分是设计的关键。

**三个时钟字段为什么必须拆**：

| 字段 | 语义 | 被谁改 |
|---|---|---|
| `transferredAt` | 本轮排队起点 | 不可变，FIFO 排序用 |
| `handlerAssignedAt` | 认领/活跃时间 | 每条消息刷新 |
| `firstResponseAt` | 首次人工回复 | 条件更新，只写一次 |

混用的后果：`waitingSeconds` 被重置、催得越急排得越后、响应时长算出负数。

### 2.3 资金与并发

**核心信条：并发正确性下沉到数据库，不靠应用层锁。**

| 场景 | 做法 | 为什么不用别的 |
|---|---|---|
| 领券库存 | `updateMany({ where: { issuedQuantity: { lt: totalQuantity } } })` | 唯一索引只能表达"最多 1 次"，表达不了 `perUserLimit=N` |
| 每人限领 | 先扣库存拿行锁 → 再 `count()` | 先 count 再扣，并发全都能通过判断 |
| 钱包扣款 | `where { realBalance: { gte: amt } }` | 先查后改会出现负余额 |
| 提现落终态 | `notIn: [SUCCESS, FAILED]` 原子抢占 | 三条入口（审核/回调/补单）复用同一出口 |
| 支付回调 | 先条件迁状态，抢到才 `creditCash` | 重放不会二次入账 |

**【已验证】最值得讲的一条**：领券"先扣后查"的正确性**只在 READ COMMITTED 下成立**。`updateMany` 加行锁让并发的同券请求排队，排队结束后 `count()` 在 READ COMMITTED 下拿语句级新快照，才能看见前一个事务刚提交的券。

> 全仓没有一个 `isolationLevel`。换 REPEATABLE READ 就是序列化失败或漏计。**这一点是理解锁机制与记住结论的分界线。**

**AI 写操作的三道闸门**：

```
1. runAgentLoop 里命中 CONFIRM_REQUIRED_TOOLS → 不 invoke，只产出 pendingConfirm
2. 60s 一次性 token，getDel 原子消费 + 校验 userId
3. 提现再过 OTP：peek(验码前只读) → verify → pop(验码后原子删)
   最后 plainToInstance + validate({ whitelist, forbidNonWhitelisted }) 过滤 LLM 夹带字段
```

`OrchestratorStateUpdate` 用类型强制每个返回路径都显式给 `pendingConfirm`——防止上一轮卡片跨轮残留。

### 2.4 可观测性与工程化

**traceId 穿透**：`runWithTrace(req.id)` + AsyncLocalStorage。为什么不用参数透传（要改十几层签名，LangGraph 节点容易漏）或全局变量（5 个并发请求会串号）。

事件总线入口没有 `req.id`，**必须自己生成 UUID**，否则 `chat.start`/`intent`/`llm.usage` 全是 `-`，Loki 无法按对话聚合。

**结构化日志为什么绕过 Nest Logger**：Nest 会加 `[Nest] pid - time [Context]` 和 ANSI 颜色码，整行不再是合法 JSON，Loki 的 `| json` 直接失效。所以直接写 stdout。

三个设计细节：
- 固定字段**放业务字段之后**展开 → 调用方无法伪造 `traceId/stage/level`
- 字段**黑名单**而不是白名单 → 白名单会逼着每次加字段都改日志器
- `emitStage` 整体 try/catch → 写日志失败绝不影响业务

**测试不是覆盖率，是"反 mock 失效"的探针**：

mock 会把并发问题抹平——两个请求在 mock 里都成功，超卖永远不出现。所以测试钉的是"我们依赖的数据库语义"：

- `coupon.service.spec.ts:132-146` 用 `invocationCallOrder` 断言 `updateMany` 早于 `count`（顺序调回去立刻变红）
- `support-handler.service.spec.ts:34-69` 断言 CAS 的 `WHERE` 形状
- `structured-logger.spec.ts:68-100` 断言**序列化后的整行**不含原文

**而且记录了反面教材**：`state.spec.ts` 是自证测试（测的是本地复制的 reducer，不是生产代码）。**主动说这个，比藏起来强。**

### 2.5 前端（不是主战场，但要会讲）

**Server Component → Client Wrapper + HydrationBoundary**：`page.tsx` 是 async RSC，用 `serverGet` 直连后端，`prefetchQuery` 进请求级 QueryClient，`dehydrate` 交给 HydrationBoundary。消灭首屏请求瀑布。

**最值得讲的三个故事**：

1. **ModalManager 为什么不用 `ReactDOM.createRoot`**——独立 root 会丢 React Context（i18n、QueryClient、主题），弹窗里的日期组件会报错。改成 module store + `useSyncExternalStore` + `createPortal`。
2. **`http.ts` 的单飞 refresh + 清 cookie**——并发 401 用 `refreshPromise` 只刷一次，`_retry` 防循环；关键细节是**先调 clear-cookie 再跳登录**，否则 middleware 看到旧 cookie 会把 `/login` 重定向回首页，死循环。
3. **monorepo 里 shared 包的 CJS/Turbopack/Edge Runtime 三重坑**——所以存在 `shared-wrapper.ts` 这种绕开包入口的补丁。

**两套 i18n 不是不一致，是场景驱动**：admin 是内部工具，cookie + Accept-Language，不值得为 SEO 付 URL 前缀成本；blog 是公网内容站，必须 `[locale]` 前缀 + hreflang + ISR。

## 3. 常见追问 20 例（按难度）

### 基础级（必须秒答）

1. **为什么用 `updateMany + count` 而不是先查后改？** → 检查与修改必须同一条 SQL；改 0 行就是 CAS 失败信号。
2. **SSE 为什么要拆两段？** → EventSource 不能设 header；消息体不进 URL。
3. **双通道投递解决什么问题？** → 会话房间依赖 join_chat 会丢，用户私有房间由连接时自动 join，重连必恢复。
4. **为什么转人工检测要放最前面？** → "转人工"短句意图分天然低，放后面会被当闲聊 return。
5. **结构化日志为什么不直接用 Nest Logger？** → 前缀和颜色码破坏 JSON，Loki 解析失败。

### 中层级（要能讲取舍）

6. **为什么用 embedding 分类而不是直接 LLM 分类？** → `intent_examples` 是唯一数据源，运营改例句立即生效；每轮只多一次 embedding，比每条消息一次 LLM 便宜稳定；LLM 只处理短回复和全低分。
7. **多意图怎么决定执行哪些？0.7 和 0.05 哪来的？** → 0.7 去掉"低分里的假明确"；0.05 是只在真正模糊时付一次 LLM 调用的窄带。
8. **为什么资金用条件更新而不是分布式锁？** → 锁只是减少冲突，TTL 到期/无 fencing token 都会失效；CAS 是最后防线，不怕进程崩溃。
9. **写操作怎么保证不被 LLM 偷偷执行？** → 三道闸门，且服务端只有一个执行点。
10. **RAG 四层怎么合并？量纲不同怎么办？** → 四层全跑取候选，按 id 合并保最高分，reranker 统一重排。
11. **traceId 为什么用 AsyncLocalStorage？** → 参数透传改十几层，全局变量会串号。
12. **评测工具怎么避免自证测试？** → 打生产接口，复用同一份构造参数，不复制 prompt。

### 高层级（决定能不能讲出深度）

13. **领券"先扣后查"的正确性依赖什么？** → READ COMMITTED 的语句级快照 + UPDATE 行锁。**换隔离级别就破。**
14. **把服务扩到 3 个 Pod 会怎样？** → 见 §4 方向一。
15. **用户能不能通过 prompt injection 查别人余额？** → 见 §4 方向二。
16. **RAG 的 reranker 挂了怎么办？** → 回退原始分排序，此时量纲问题重新暴露（`rag-retrieval.service.ts:549-556`）。
17. **提现为什么冻结毛额、累计记净额？手续费去哪了？** → 冻结必须是账上被扣住的全部；差额只落在 `withdraw_order.fee_amount`，**钱包流水没有手续费分录**——对账时要能解释这个缺口。
18. **为什么"钱已出去但冻结不足"还要强扣成负数？** → 终态必须落定，否则订单卡在 PROCESSING、用户重复提现。资金事实优先于账面约束。
19. **一轮对话最坏要调几次模型？** → CJK 翻译 1 + 意图兜底 1 + 多意图仲裁 1 + 5 Agent × 3 轮 + 合成 1 ≈ **18 次 chat completion**，且整轮没有全局 deadline。
20. **如果现在把 LangGraph 去掉，哪些能力真的会丢？** → 诚实答案：只有跨轮 checkpointer 和 streamEvents，而 checkpointer 现在是进程内 MemorySaver。**想清楚这一点，能说明架构选择不是"为了用而用"。**

### 框架选型（2 例）

21. **LangChain 和 LangGraph 有什么区别？**
    → LangChain 是抽象与适配层：统一模型、消息、工具、输出解析的接口，换服务商不改业务代码（调 DeepSeek 用的是 `ChatOpenAI` 类，因为协议兼容）。LangGraph 是建在它之上的有状态编排层：用图表达循环和分支，用 checkpointer 持久化状态。Agent 本质是「模型 → 工具 → 模型」的循环，链式表达不了，所以用 LangGraph。

22. **什么时候不该用 LangGraph？**
    → 简单线性调用别上，图会变成为了用而用。本项目的教训是反面例子：旧架构 10+ 节点、65 行条件边，多意图组合时边数爆炸，最后收缩成 2 个节点，把调度挪进普通 for 循环。**能说清「不该用」比说清「该用」更能证明判断力。**

   补充：如果调用很简单，直接用官方 SDK（如 `openai` 包）比套 LangChain 更轻；LangChain 的价值集中体现在「模型调工具、结果回灌、再调模型」这套消息流转上。

## 4. 深水区：三个必被追问的方向

### 方向一：多实例部署

**问法**：扩到 3 个 Pod 会怎样？

**现在的事实**（【报告】，多份交叉印证）：

| 状态 | 位置 | 多实例后果 |
|---|---|---|
| `MemorySaver` | `customer.graph.ts:179` | `previousIntent`/`repeatCount`/`pendingConfirm` 全丢，同 threadId 打到不同 Pod 各存一份 |
| `EventEmitter2` | 进程内 | 无 Socket.IO Redis adapter，A 实例写的消息到不了 B 实例上的用户 |
| 熔断器状态 | `sse-rate-limiter.service.ts:41-45` | 各实例独立熔断："这台拒绝、那台放行" |
| 提现幂等 `Set` | `wallet-tools.ts:70-80` | 不共享 |
| 分布式锁 | `redis-lock.service.ts` | 无续租、无 fencing token；装饰器找不到锁还 fail-open |

**改进方向**：Redis/PG checkpointer + `@socket.io/redis-adapter` + 熔断状态外置 + in-flight 流做粘性会话。最后补一句：**无论如何，CAS 和唯一索引是最后防线，Redis 只是优化。**

### 方向二：信任边界

**问法**：用户能不能通过 prompt injection 让 AI 查别人余额？

**要检查的点**：
- 工具的 `userId` 从哪来？**如果 tool schema 里有 userId 字段，就应该删掉**——它不该由 LLM 提供，应该在每轮按请求上下文闭包绑定
- system prompt 里写"禁止询问 userId"**不是安全边界**，只是意图引导
- 工具返回的商品名/兑换码会被再次喂给 LLM → 应视为不可信数据
- 确认卡片里**除提现外**的 params 没有 DTO 校验（【已验证】：只有提现路径做了 `plainToInstance + validate`）

### 方向三：成本与延迟预算

**问法**：一轮对话最贵能到多少？

**要能给出预算表**：各步调用次数 × 单次超时（`timeout 15s`、`maxRetries 1`）× 最坏路径。然后指出：**没有全局 deadline、没有 AbortSignal、没有队列背压**（只有 200 个 SSE 并发上限）。断连只释放限流，图继续跑继续烧 token。

### 最可能被追问的一条（直接命中本项目）

> **"你的 hybrid search 为什么融合分数，而不是融合排名？"**

这是 RAG 面试的经典深水题，而本项目的做法正好是**按分数取最大值合并四层结果**——余弦相似度、BM25 位置分、ILIKE 固定 0.5、文档分，四者量纲完全不同。

**标准答案是 RRF（Reciprocal Rank Fusion）**：只融合名次不融合分数，公式 `Σ 1/(k + rank)`，天然免疫量纲问题。

**本项目的诚实回答**：

> 我用 reranker 兜住了这个问题——四层合并后统一用 cross-encoder 重排，等于用一把尺子重打分。但 reranker 不可用时会退回原始分排序，那时量纲问题会重新暴露，这是已知缺口。更稳的做法是先用 RRF 融合名次、再重排。

**主动说出这个缺口，比被问出来强得多。**

### 十个"追问杀手"

搜到的题库都强调同一件事：**基础题人人会答，分差在追问**。以下十句是高频追问，每句都要能接住：

1. 你选了 512 的 chunk，为什么不是 256？→ 要有 ablation 数据，没有就说"我用的是固定策略，没做对比"
2. reranker 提升了准确率，代价是多少延迟？→ p50 +100~200ms 量级
3. hybrid search 赢了，那在哪些 query 上输了？→ 短 query / 纯专有名词
4. 你怎么知道评测集没有泄进 prompt？→ 本项目的答案是"查重"，但实际没做（N/A）
5. LLM-as-judge 和你一致，它和用户一致吗？→ 所以需要人工抽检校准
6. 召回率没变，MRR 掉了，没人动过 retriever → 排序或去重逻辑变了
7. faithfulness 很高，但评审发现了编造 → judge 与人的口径不同
8. Agent 会不会无限循环？→ `MAX_ITERATIONS=3` + 只统计带 tool_calls 的轮次
9. 工具返回非法结构怎么办？→ 本项目的 `tool-result.ts` 声称统一包装，实际有 3 个工具没遵守
10. 模型挂了怎么办？→ `degradeToHuman` 四步，静态话术 + 置 awaiting_human + 发事件 + 记原因

### 三个目前答不了的

| 问题 | 现状 | 建议 |
|---|---|---|
| chunk size 为什么是这个值 | 没有 ablation | 补一次对比实验，出 3 组数据 |
| judge 和用户的一致率是多少 | 没有 judge | 阶段二建起来后补 |
| 你的评测集覆盖多少真实线上分布 | 人工构造 | 用隐式信号（转人工/重复追问）做分布校准 |

## 7. 系统讲解建议（60 秒版）

> 我做的是一个 AI 客服系统，核心难点不在"接大模型"，而在**让 AI 的写操作和资金系统一样可控**。
>
> 三个设计我自己比较满意：
> 第一，**多 Agent 调度没放进图里**。原本每个意图一个节点、条件边随组合爆炸，我改成 orchestrator 内部按依赖排序的循环，代价是节点变胖，但依赖表达、异常隔离、上下文共享都变成了普通代码。
> 第二，**意图分类保留了两路召回**，因为运营改例句要立即生效，不能每次都改 prompt。这套东西我后来发现一个门禁位置错的 bug——阈值卡在融合之前，单路略低的意图会被提前淘汰。
> 第三，**写操作有三道闸门**：工具在 LLM 调用前被截停、一次性 token、提现再过 OTP。原则是"服务端绝不先执行写操作，且只有一个执行点"。
>
> 我也清楚它的短板：状态还在进程内，多实例部署会断；评测集只有 63 题，任何小于 10 个点的改进都证明不了。这些是我下一步要补的。

**这版叙事的关键**：主动说出短板。被问"有什么问题"时，答"没有"是最减分的。
