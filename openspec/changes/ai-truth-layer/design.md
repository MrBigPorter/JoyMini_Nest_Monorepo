# Design

## Context

- 事实的现状载体：`payment_channels` 表（`code / name / type / currency / min_amount / max_amount / fee_rate / fee_fixed / status`，`type` 1=入金 2=提现）。生产值：入金只有 `PH_GCASH`、`PH_PAYMAYA`、`PH_BDO`（`PH_BDO` 费率 1%，最低 ₱100，最高 ₱80,000）；提现只有 `PH_GCASH_WITHDRAW`（0.8% + ₱5，最低 ₱100）与 `PH_BANK_WITHDRAW`（1% + ₱10，最低 ₱200）。
- 文档的现状载体：`knowledge_documents.content`，markdown，渠道信息写成**人类可读的表格**（Method / Processing Time / Min / Max / Fee），数值直接写在单元格里。
- 读取通道：`GET /admin/payment/channels/list?type=1|2`（`payment-channel.controller.ts:55`）返回 `PaymentChannelDto`，含 `minAmount / maxAmount / feeFixed / feeRate`；`GET /admin/rag/documents/:id`（`rag.controller.ts:171`）可取文档正文。两者都在管理员鉴权后。
- CI 已有管理员鉴权路径：`eval-regression.yml:117-122` 用 `E2E_ADMIN_TOKEN` 或测试账号 + `E2E_OTP_CODE` 调部署环境的 API。真值校验可复用同一套。
- 仓库内目前没有任何「事实 → 来源」的登记，也没有比对的脚本。
- 外部对照：同课程准生产仓库 `omnisupport-copilot`（`/Volumes/MySSD/work/study/omnisupport-copilot`）用 34 个 JSON Schema 管数据形状，同样没有「事实 → 来源」的登记，也没有文档与配置的比对。可借的是它**把契约作为仓库内文件、走 PR 评审**的组织方式，而不是它的 schema 内容。

约束：本批只做登记与比对，不改对话链路、不改入库管线、不改管理端 UI。

## Goals / Non-Goals

**Goals:**

- 一份可评审、随代码版本走的登记文件，声明每类事实的来源定位与取值方式。
- 确定性的比对程序：不调用任何模型，同一输入永远同一结果。
- 比对对象是**线上正在服务的那几份**（线上文档 × 生效提示词 × 线上配置），而不是仓库里的某份快照。
- 不一致、来源不可达、登记无法解析、文档声明无法解析——四种情况一律失败，且各自给得出可读原因。

**Non-Goals:**

- 不在对话运行期拦截（P5）。
- 不做语义推断式的「自动发现未登记的事实」；只认显式标记。
- 不把文档搬进仓库（迁移时机未定，见 Open Questions）。
- 不复用评测 harness：它依赖判官模型，而这里必须完全确定性。

## Decisions

### D1 — 登记以仓库内 JSON 文件承载，不建表

`tools/truth/registry.json`，与代码同版本、同评审。登记的是**指针**，不是数值。

理由：登记变更需要走 PR 评审；CI 读取不需要连库；不引入迁移与管理端权限。数值永远只有一份，在业务表里。同一门课程里的 `omnisupport-copilot` 也把全部契约放在仓库内由 PR 与契约测试把关，说明这条路在本项目语境下可维护。

替代方案：
- 新建 DB 表 + 管理端页面 —— 需要迁移、权限、UI，且让人能在不评审的情况下改登记；否决。
- 写成 TS 模块 —— 运营改不了，diff 噪声大；否决。

### D2 — 文档用行内标记绑定事实，数值仍写在可见表格里

表格数据行末尾加 HTML 注释标记：`<!-- truth: withdraw.gcash.fee -->`。表格照常给人看、给模型检索，标记不渲染、不影响阅读。

理由：显示值只存在一份，避免「文档里两处数字互相漂移」；不改入库管线与编辑体验。

替代方案：
- 占位符 `{{withdraw.gcash.fee}}` 在入库时渲染 —— 保证文档里根本没有数字，但要求改入库管线并改变编辑体验；本批不做。
- 文档里再写一段结构化 claims 块 —— 同一文档内两份数字，正是要消除的问题；否决。

代价：标记与行必须在一起，表格结构一旦改版解析会失败。缓解见 D4：解析失败按失败处理，不按跳过。

### D3 — 校验是独立的确定性脚本，放在 `tools/truth/`

`node tools/truth/check.mjs`，与 `tools/eval/e2e/*.mjs` 同样的风格（纯 ESM、无框架）。退出码 1 表示失败，逐条输出 `声明 → 文档值 / 真值 / 结论`。

输入三样：登记文件、被扫描的文档集合（登记中 `documents[]` 声明）、管理员鉴权的 API 地址与令牌。

理由：确定性、可本地跑、可被 CI 直接调用，且与模型评测解耦——评测挂了不影响它，它挂了不影响评测。

### D4 — 四种失败一律失败，不做缓存

- 来源 HTTP 非 2xx / 超时 / JSON 结构不符 → 失败，写明来源与原因。
- 登记项缺字段或指向不存在的来源 → 失败。
- 文档表格行缺标记，或标记指向未登记的键 → 失败。
- 行内数值无法按登记的解析格式提取 → 失败。

不缓存真值、不缓存文档。每次运行都重新取，否则「不可达」会被上一次的旧值掩盖。

### D5 — 校验对象是线上那一对，触发点是定时 + 手动 + 相关 PR

文档在 DB 里改，PR 里看不到，所以这套校验本质是**线上一致性的定时体检**，而不是「PR 改了文档就拦住」。

- `schedule`：每日一次。
- `workflow_dispatch`：手动，验收用这条。
- `pull_request`（path 过滤）：改动 `payment-channel` 模块、`prisma/migrations`、`tools/truth/**` 时跑——这类改动会让真值变，而文档不会跟着变。

后果必须写清：**在管理端改文档，不会被任何 PR 拦住**；最迟次日由定时任务发现。要缩短这个窗口，得把文档搬进仓库（Open Questions）。

### D6 — 真值以业务表为准，冲突时不以文档为准

校验永远只问「文档是否等于表」。若业务认为表错了，先改表（走它自己的评审），表变了校验自然再次失败，直到文档同步。这样「哪一边对」只有一个答案，不需要校验器去猜。

### D7 — 本批覆盖的事实类型：渠道是否支持、费率、最低额、最高额

这四类的真值都能在 `payment_channels` 落到字段。**时效（Processing Time）没有真值源**——全库没有承载处理时长的字段（已核对 information_schema）。

因此迁移时必须处理文档里的时效声明：要么删掉精确时长，改成不构成事实声明的表述（如「到账时间因渠道而异」），要么等有了真值源再写回。登记文件里用一个显式的 `unsourced` 条目记录"这一类暂无来源、已从文档移除"，让这条决定在评审里可见，而不是悄悄消失。

### D8 — 声明形式必须与登记一致，不能只比数值

登记项声明该事实的取值形式：`flat`（固定金额）、`rate_plus_fixed`（比例 + 固定值）、`amount`（金额上下限）。文档单元格必须按同一形式书写，形式不符即失败。

理由：`₱15` 与 `0.8% + ₱5` 不能直接比较大小；若只比数值，比较器就得猜"哪个更大算对"。形式本身是可观察的错误（用户实际会被扣 ₱85 而非 ₱15），应当单独判失败。现有冲突里这条正好命中。

实现时补一条窄例外：登记为 `rate_plus_fixed`、文档只写比例（如 `1%`）时，仅当真值的 `fee_fixed` 为 0 才通过；真值有固定费仍判形式不符。否则 `PH_BDO`（1% + ₱0）会被迫写成 `1% + ₱0`。

### D9 — 文档按 docId 定位走列表翻页，而不是详情接口

`GET /admin/rag/documents/:id` 的 `:id` 只接受数据库 UUID（`rag.service.ts:181` `findUnique({ where: { id } })`），而登记与文档表格用的是业务键 `docId`。校验器改为 `GET /admin/rag/documents?isActive=true&page=N&pageSize=100` 逐页匹配 `docId`，翻到 `total` 为止。

理由：不改 api（提案已声明），且只发 GET；文档总数在百级，翻页成本可忽略。代价是依赖列表接口的 `total` 与实际页大小一致，结构不符时按失败处理。列表条目里同时带 `version` 与 `activeVersion`，D12 的版本绑定判定就建立在它们之上。

### D10 — 管理端接口带 URI 版本前缀，写回走独立运维脚本

`main.ts:61` 开了 `enableVersioning({ type: URI, defaultVersion: '1' })`，所以所有路由实际是 `/api/v1/...`：`GET /api/v1/admin/payment/channels/list`、`GET /api/v1/admin/rag/documents`。`--base-url` 一律给到 `/api/v1`，本地是 `http://127.0.0.1:3000/api/v1`。

文档迁移的写回落在一个**独立的运维脚本** `tools/truth/apply-docs.mjs`，而不是校验器里：校验器保持只发 GET，「只读」这条性质才守得住。脚本做三件事——按 docId 取当前正文、与 `fixtures/docs/<docId>.md` 定稿逐字节比较、不同才 `PATCH /admin/rag/documents/:id/content`，然后轮询详情接口直到 `activeVersion` 切到新 `version`，超时即失败并提示索引未生效。

理由：`updateContent()`（`rag.service.ts:791`）才是重新切片、重算哈希与质量分、排队向量化并触发 `KbVersionService` 切换的入口；直接改库会留下「正文是新的、索引还停在旧内容」的隐性不一致。定稿文件放仓库里是为了让改名、删渠道这类**内容决定**能在 PR 里被看见，而不只是留在某人本地。

### D11 — 真值读取必须无损：费率精度是 4 位，不是 2 位

`payment_channels.fee_rate` 是 `Decimal(5,4)`，`0.0080`（0.8%）是合法值。但 `PaymentChannelDto` 的 `@DecimalToString()` 默认只保留 **2** 位小数，接口把 `0.0080` 输出成 `"0.01"`：后台显示成 1%，校验器也读到 1%，于是文档写「1% + ₱5」会被**误判通过**——比文档写错更糟，因为校验器给了假绿。

改动：该字段改为 `@DecimalToString(4)`（`payment-channel.dto.ts`），金额类字段（`minAmount` / `maxAmount` / `feeFixed`）保持 2 位。单测锁三档：`0.0080` → `"0.0080"`、`0.01` → `"0.0100"`、`0` → `"0.0000"`。

这条超出「不改 api」的初版范围，但没有它，本变更的核心比对建立在被四舍五入过的读数上，Requirement 无法成立。

### D12 — 校验绑定在「正在服务的那一版」，而不只是正文列

`KbVersionService.switchTo()`（`kb-version.service.ts:145`）只翻分块与 Meili 的版本标记，**不还原** `knowledge_documents.content`。所以回滚之后：检索服务的是旧版分块，而列表接口返回的仍是当前（新版）正文。只比正文会得到假绿——校验器看不到「线上正在服务的那一份」。

校验器因此要求 `activeVersion === version`，不等即失败，阻断信息写明两个版本号。这是「校验对象是线上正在服务的那一对」在版本维度上的落实。

代价与取向：正文改完、向量化尚未完成时，校验为红。这是有意的失败方向——那段时间检索服务的确实是旧内容；`apply-docs.mjs` 会在写完后等到切换完成，所以正常迁移路径不会撞上。

### D13 — 运行期可改的载体也要扫：提示词守字面量，意图示例不扫

事实有四类载体，能改的人不同，防线也不同：

| 载体 | 谁能改 | 本批防线 |
|---|---|---|
| 知识文档 `knowledge_documents` | 管理端编辑正文并激活版本 | 本校验：标记 + 逐条比对 + `activeVersion` 绑定（D2 / D12） |
| 提示词 `knowledge_prompt_versions` | 管理端创建并激活版本，`status='active'` 即被 `PromptResolverService.mergeConfig` 覆盖到 TS 默认上 | 新增字面量守卫：扫每个生效版本的全部字符串，出现费用/金额字面量即失败 |
| 意图示例 `intent_examples` | SEED / KB_CANDIDATE / 管理端 | 不扫（理由见下） |
| 代码（`graph/agents/prompts/*.ts` 等） | 只能走 PR | 代码评审；本批不动 |

提示词为什么必须扫：它在回答正文里，改的人是运营，激活即生效，没有任何 PR 能拦住——和知识文档同一个风险面。守卫只认三类字面量：百分比（`0.8%`）、带货币符号或 `PHP` 前缀的金额（`₱100`、`PHP 80,000`）、数字加 `peso(s)` 字样（`15 pesos`）。指向工具结果的占位写法（`₱[amount from tool result]`、`[progress from result]%`）不带数字，不会命中。裸数字不判（`1-3 business days` 是流程描述，不是费率），避免把正常流程文本误报成事实声明。百分比一律判违规，包括 `100%`：真有修辞需要就改写成「完全」。当前 dev 的 7 个生效版本实测 0 处字面量。

意图示例为什么不扫：一是实测 783 行里只有 2 行带金额，且都不是事实声明（问句与示例措辞）；二是它在链路里只做路由分类，不进入回答正文，写错数字不会变成用户看到的承诺；三是它本就是用户语言的样本，扫它会把「提现手续费多少」这类自然问句误报成违规。如果将来意图示例被用作 few-shot 拼进回答提示词，这条理由失效，届时随 P2 一起处理。

防线的边界必须说清：守卫只保证「当前生效的每个提示词版本都被看过」，不保证「提示词、知识库、代码是同一版」。把 `codeSha + indexVer + promptVer + kbVer` 打包成 release 并在报告里并列展示，属 P2 `ai-release-versioning`，本批不做。

读取失败与零条生效版本都判失败（对应「校验不可静默跳过」新增的场景）：接口异常时如果当作「没有提示词」放过，守卫就会在真出问题时静默消失。

## Risks / Trade-offs

- **表格解析脆弱** → 解析失败按失败处理并打印原始行；登记里为每种表声明解析格式（本批只有一种：五列渠道表）。
- **定时任务一天一次，DB 改文档最多滞后一天被发现** → 手动 dispatch 兜底；后续把文档纳入仓库可根治（见 Open Questions）。
- **CI 打的是部署环境，需要管理员凭据** → 复用 `E2E_ADMIN_TOKEN` / `E2E_OTP_CODE`，只读权限最理想；若只有高权令牌，至少保证脚本只发 GET。
- **首次运行一定大面积红**（逐行核对：两篇文档共 10 处与 `payment_channels` 冲突，另有整列时效无真值源） → 这是预期结果，不是回归；迁移计划把"让首次运行为绿"作为明确任务，而不是把校验放宽成绿色。
- **删掉时效声明会让回答变"没用"** → 只删精确数字，保留定性描述；RAG 仍然能回答"多久到账"这类问题的方向性内容。

## Migration Plan

1. 建登记文件，登记 `payment_channels` 的两类渠道 × 四个字段 + 时效的 `unsourced` 条目。
2. 在两篇文档的渠道表格行上补标记；把没有真值源的时效声明改成定性表述。
3. 本地对 dev 库跑一次，逐条消掉冲突；再对部署环境跑，确认绿。
4. 接入 workflow：定时 + 手动 + path 过滤的 PR。
5. 回滚：校验是只读的，移除 workflow 即回到现状；文档改动走 `knowledge_documents` 版本切换（`KbVersionService`），可单篇回滚。

## Open Questions

- 时效是否要为它建一个真值字段（例如渠道配置上加 `expected_arrival`），还是长期保持定性描述。答案不影响本批的登记结构与脚本。
- 文档是否长期留在 DB，还是迁进仓库以获得 PR 级别的门禁。这是入库管线层面的决定，本批不改。
