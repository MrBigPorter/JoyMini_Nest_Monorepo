# Design

## Context

- 数据获取：约 30 个 dashboard 路由，其中 14 个用 RSC 预取 + HydrationBoundary；读用 React Query，写用 `ahooks useRequest({ manual: true })`。
- 缓存：写成功后调用 Server Action 执行 `revalidateTag`，同时本地 `refetch`。
- 类型：`src/type/types.ts` 1875 行手写；`packages/shared` 只共享枚举；`gen-types` 产物零引用。
- 写调用：全仓约 65 处，0 个 `useMutation`。
- 表格：`SmartTable`（自研）与 `BaseTable`（tanstack）两代并存；`SmartTable` 只有首屏用 hydration，翻页走自己的 `fetchData`。
- OpenAPI：`apps/swagger-docs/swagger-spec.json` 已提交仓库，由 `yarn workspace @lucky/api export:swagger:full` 生成（该脚本启动 AppModule，属人工/发布前步骤）；`apps/admin-next` 尚未安装 `openapi-typescript`。
- 既有 `gen-types` 只把 `x-field-meta` 生成为 `packages/shared/src/types/gen/` 的字段元数据，**不产出接口请求/响应类型**，不能替代本次类型生成。
- React Query Provider 已全局挂载（`app/layout.tsx` → `Providers.tsx`）。
- 三个目标页现状：用户/订单页是「URL 参数 + 本地 state + 手写 API 调用」；财务页是 `SmartTable request` + hydration；三者当前都**没有轮询**。客服工作台有 ahooks 轮询，不在本次范围。

## Goals / Non-Goals

**Goals:** 三个页面的写操作可感知、缓存一致、类型随契约变化、首屏与翻页统一。

**Non-Goals:** 全量迁移 65 处写调用；统一两代表格组件；引入 tRPC；改 blog。

## Decisions

### D1. 只在三个代表性页面迁移

全量迁移 1 周不现实。选用户管理、订单列表、财务审核：覆盖「列表 + 详情 + 审核」三种典型形态，足以证明模式可复制。

### D2. 乐观更新采用「先改后校」，不做本地状态镜像

`onMutate` 里直接操作 query cache（`setQueryData`），`onError` 回滚快照，`onSettled` 触发失效。不引入独立的本地 store——那会造出第二个真相来源。

### D3. 双层缓存失效沿用现有 Server Action，不重写

现有 `lib/actions/*-revalidate.ts` 已是可用的 tag 失效链路。mutation 的 `onSuccess` 调用它即可，不新建机制。

**为什么**：多实例下进程内缓存不可靠，把一致性交给 Next Data Cache + 显式 tag 是当前架构的正确选择。

### D4. 类型生成用 OpenAPI，不用 zod 运行时校验

- **类型源**：已提交的 `apps/swagger-docs/swagger-spec.json`。生成脚本不联网、不启动后端，保证 CI 可重复。
- **工具**：`apps/admin-next` 新增 devDependency `openapi-typescript`（实施时 pin 精确版本）。
- **产物**：`apps/admin-next/src/type/generated-api.d.ts`，文件头写 “generated by scripts/generate-api-types.mjs, do not edit”，并提交仓库（CI diff 需要基线）。
- **脚本**：`apps/admin-next/scripts/generate-api-types.mjs`，只读 spec、只写产物。
- **CI**：在 `ci.yml` 的 check job 里跑生成 + `git diff --exit-code -- src/type/generated-api.d.ts`，卡住「spec 更新但类型没重生成」。
- **边界（不假装自动化）**：单测 CI 不启动后端，因此**不验证 spec 本身是否最新**；spec 刷新仍是 `yarn workspace @lucky/api export:swagger:full` 的人工/发布前步骤，写进文档。想自动验证 spec 新鲜度，需要另建带 db/redis 的 job，不在本次范围。
- **替换范围**：只替换**结构与可选性完全一致**的类型。已核实 181 个手写导出与 196 个 schema **零同名**，且存在字段差异（如后端 `relateType` vs 前端 `relatedType`、生成 DTO 缺 `updatedAt`），因此不能全局重命名或批量替换。当前唯一可直接替换的是 `Tokens` → `AdminTokenPairDto`。
- **其余重叠**：在 2.x–5.x 各页面迁移时做显式「生成 DTO → 视图模型」映射；禁止为了对齐生成类型而把后端拼写（`relateType`）带进 UI，或删除 UI 依赖的字段。

**替代方案**：zod schema 双端共享——需要先定义一套 schema 再生成，改动面大，否决。

### D5. 首屏与翻页统一，采用「把 SmartTable 的数据来源换成 query」

不动表格的渲染层，只把它的取数从 `fetchData` 换成 `useQuery`（`enabled` 控制首屏是否用注水数据）。这样既保留组件 API，又消除两套数据流。

**实现方式**：SmartTable 增加可选 `query: { queryKey(state), queryFn(state), enabled? }` prop；传了 `query` 时内部 `fetchData` 完全不执行，首屏与翻页共用同一套 queryKey。未传 `query` 的页面继续走 `request`，行为不变。财务审核页是本次唯一切换的实例；用户/订单页本来就是 `useQuery`，不需要改。

### D6. 三个页面的数据层现状与迁移顺序

按「用户 → 订单 → 财务」推进，每个页面独立提交、可单独 revert：

1. **用户管理**：`UsersClient` 已把筛选写进 URL，`UserListClient` 用本地 state + `clientUserApi` 取数。改为 `useQuery`，queryKey 由 URL 参数派生；写操作 `useMutation`。
2. **订单列表**：`OrderListClient` 用本地 state 管分页/筛选。同样把筛选收敛到 URL，查询走 `useQuery`；状态变更类写操作 `useMutation`。
3. **财务审核**：`WithdrawalList` 等通过 `SmartTable` 的 `request` + `enableHydration` 取数。保留 SmartTable API，把 `request` 换成 `useQuery({ enabled: !hydrated })`；审核类写操作**不做乐观更新**（见 D2 与 spec 的资金类例外）。

### D7. ahooks → React Query 的映射

目标页面当前没有轮询，迁移只处理已知形态；后续遇到同类写法按这张表处理：

| ahooks | React Query |
|---|---|
| `useRequest(fn)`（自动） | `useQuery({ queryKey, queryFn })` |
| `useRequest(fn, { manual: true })` 写操作 | `useMutation` |
| `useRequest(fn, { manual: true })` 读操作 | `useQuery({ enabled })` |
| `pollingInterval: N` | `refetchInterval: N` |
| `refreshDeps: [...]` | 并入 `queryKey` |

范围外页面（客服工作台等仍依赖 ahooks 轮询的页面）不迁移。

## Risks / Trade-offs

- **[乐观更新与真实状态不一致]** → 只在低冲突操作上启用；审核类操作（财务）保留"等待确认"再更新，避免误导。
- **[类型生成覆盖不全]** → 先替换与后端重叠的部分，`packages/shared` 的枚举保持不动。
- **[spec 新鲜度不自动保证]** → CI 只校验「类型与已提交 spec 同步」；spec 自身刷新依赖 `export:swagger:full` 人工步骤，文档必须写明，不能让读者误以为全链路自动。
- **[CI 检查增加构建时间]** → 生成器不启动后端、只读 JSON，成本在秒级，因此放在 check job 里始终执行，不做路径过滤。
- **[表格改造成本]** → 只给 SmartTable 增加可选 `query` 取数入口（渲染层不动），只切换财务审核页；其他页面继续走 `request`，行为不变。

## Migration Plan

1. 类型生成脚本 + CI 检查（无行为变化）
2. 用户管理页 mutation 化
3. 订单列表页 mutation 化
4. 财务审核页 mutation 化（保守策略）
5. 三个页面的表格取数统一

回滚：每个页面独立提交，可单独 revert。

## Open Questions

- spec 新鲜度的自动校验是否单开一个带 db/redis 的 CI job？—— 本期不做；先用文档 + 人工 `export:swagger:full`，后续有需要再立项。
