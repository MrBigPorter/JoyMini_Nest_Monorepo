# Design — 修复 AI 领券的有效期与序号绑定

## Context

券模板有 `validType` 两种有效期语义：

- `validType=1`：固定窗口，`validStartTime` / `validEndTime`
- `validType=2`：领取后 N 天，`validDays`

`getClaimableCoupons` 目前只按 `issueType=2 + status=1` 过滤，没有有效期条件；`claimCoupon` 执行时会拒绝过期券，所以不会真的发出过期券，但会出现「先给卡、再报错」。

AI 侧同时存在两张列表：

- `getUserCoupons`：我持有的券（可能已过期/已达限领）
- `getClaimableCoupons`：可领取的券

模型会在两张列表之间切换，而用户的序号只对「刚刚看到的那张列表」有意义。

## Goals

- 过期/未开始/无有效期的券不再出现在可领取列表，也不再生成领券卡。
- 用户用序号指代券时，解析到正确的券；不可领时解释原因，不替换成另一张。
- 执行错误对用户可读且中文；执行层仍保留独立校验。
- 不改变库存、并发、限领的既有不变量。

## Non-Goals

- 不改库存并发与限领顺序（T1-5 / T1-6）。
- 不新增数据库迁移或索引。
- 不做服务端确定性序号门禁（见 D4 的残余风险与备选）。
- 不改 App 领券中心的视觉设计。

## Decisions

### D1. 有效期过滤放在 `getClaimableCoupons`（服务层）

查询条件追加：

```
OR:
  - validType=1 AND validEndTime >= now
    AND (validStartTime IS NULL OR validStartTime <= now)
  - validType=2 AND validDays > 0
```

保持 `issueType=2`、`status=1` 不变。

理由：可领取列表的语义就是「现在能领」；App 领券中心与 AI 工具共用同一份结果，口径必须一致。已抢光/已达限领仍返回，由 `canClaim` 等字段表达，避免改变调用方对「为什么不能领」的解释能力。

### D2. `claimCoupon` 补 validType=2 兜底

`validType=1` 已有 `now > validEndAt` 校验。`validType=2` 若 `validDays` 为空或 `<= 0`，当前会发出立即过期的券；补一条拒绝。库存扣减与限领检查的顺序**不动**。

### D3. 守卫话术与错误本地化放在 AI 动作层

- `issueConfirmCard` 的领券守卫继续用可领取结果做精确匹配；过滤修好后过期券自然匹配不到。
- 守卫拒绝话术改为真实原因（已过期/已下架/已抢光/已达限领），不再说「没有找到」。
- 已知执行错误在 AI 动作结果发布前映射为中文；不改 `ClientCouponService` 的英文错误（App 接口契约不变）。

### D4. A-13 采用「单一编号列表 + prompt 规则」（方案 A）

- 默认展示顺序：先可领取（带编号），再已持有（不带编号，标注状态）。
- Prompt 硬规则：
  1. 用户序号只指向最近展示的列表。
  2. 弹卡前复述券名与序号。
  3. 不可领时解释原因，不换券。
  4. 切换列表必须先重新展示并请用户重选。
- 不做服务端序号门禁（方案 B）：它需要短消息正则、列表时效、graph 状态读取，新增状态与边界，风险大于收益。

**残余风险**：模型可能违反 prompt。验收场景以真实数据覆盖；若仍失败，再单独提案方案 B。

### D5. `getMyCoupons` 不改代码

现有实现已在读取前把「未使用且已过 `validEndAt`」的券标为 `status=2`。本次只验证该行为，不重复实现。

## Constraints

- 有效期判断统一用服务端时间；数据库时间为 UTC。
- 不改变 `claimCoupon` 的「先原子扣库存、后查限领」顺序。
- 不改变 `issueConfirmCard` / 确认令牌 / 执行 CAS 的权威模型。
- AI 领券仍然只能通过确认卡执行，不得直接调用业务接口。
- Prompt 规则不得影响兑码、持有列表、其他意图的正常回答。

## Edge Cases

- `validType=1`：`validStartTime` 为空按「已开始」处理；`validEndTime` 为空视为不可领取。
- `validType=2`：`validDays=0` 或为空视为不可领取。
- 列表展示后、确认前券过期：执行层拒绝；用户收到中文提示；库存/用户券不变。
- 有效但已抢光/已达限领：仍返回列表项，`canClaim=false`；AI 工具默认过滤，用户追问时再解释。
- 序号越界或最近没有展示列表：请用户重新选择，不猜。
- 中英文序号（「领取1」「领第 1 张」「claim 1」）都按同一规则处理。
- 同一会话多次展示不同列表：以最近一次为准。

## Risks / Trade-offs

- **Prompt 可靠性**：A-13 依赖模型遵守规则；用验收场景兜底，失败再上方案 B。
- **App 领券中心行为变化**：过期模板不再返回；属于修正，但需要确认空列表 UI 不异常。
- **查询性能**：新增 OR 条件，当前券表规模小；暂不新增索引。
- **错误映射遗漏**：只映射已知消息，未知错误仍原样透出；后续按出现频率补充。

## Testing Strategy

- 服务层单测：过期、未开始、无结束时间、validType=2 有/无天数、抢光/限领仍返回。
- 领取单测：过期、validDays<=0、并发/限领顺序不回归。
- AI 守卫单测：过期券不建卡、不发动作记录；有效券正常建卡。
- 错误映射单测：四条已知错误 → 中文。
- Prompt 内容测试：序号规则、单一编号列表规则存在。
- 验收：使用真实数据（Fixture 已达限领、Big Spender 已过期）复现 A-13 场景。
