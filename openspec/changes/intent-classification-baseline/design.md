# Design

## Context

评测与可观测的基础设施**已经存在**，本变更主要是把它们接到意图分类这条路上：

| 已有 | 位置 | 现状 |
|---|---|---|
| 回放脚本 | `tools/eval/replay.py`（458 行）、`run-replay.sh` | 打在生产分类路径 `POST /admin/intent-examples/test` |
| 评测集 | `tools/eval/golden/intent.jsonl` | 63 条，单 JSONL，字段 `id/input/expect/tags/note` |
| 基线 | `tools/eval/baseline.json` | 一份，无不确定度 |
| 结构化日志 | `common/logger/structured-logger.ts`（`emitStage`）、`trace-context.ts`（`runWithTrace`） | T0-2 已落地，意图分类只在 orchestrator 用了两处 |
| 重排能力 | `AiService.rerank(query, documents)`，模型 `bge-reranker-v2-m3` | 只被 `rag-retrieval.service.ts` 使用 |
| LLM 工厂 | `graph/llm-factory.ts` 的 `createLLM` | 在线 DeepSeek |

约束：不改意图标签体系（仍是 9 个），不改数据库结构，不改对外接口。

## Goals / Non-Goals

**Goals:**

- 让「改了有没有用」这个问题的答案可被统计检验，而不是靠肉眼看小数点
- 让一次误判能在一条日志里看完全部关卡，不需要读代码
- 用同一批样本、同一套脚本，把三条候选路径放在一张表上比较

**Non-Goals:**

- 本变更**不预先选定架构**。选型是产出的结论，不是输入。
- 不优化各意图的 prompt 质量，不调整 `intent_examples` 的例句内容
- 不做线上灰度与 A/B（属于部署层，另行处理）

## Decisions

### D1. 评测集扩到 150 题，并用配对检验而不是比较两个置信区间

单看两个独立置信区间是低效的：150 题时 95% CI 约 ±7.4 个百分点，要看出 5 个点的提升几乎不可能。但两个方案跑的是**同一批题**，因此应当用**配对检验（McNemar）**——只看两者判定不一致的题，灵敏度高得多：约 20 道不一致题里若 15:5 偏向某一方，即可在 0.05 水平显著。

因此：150 题是**下限**，配合配对检验使用；报告里同时给出总体准确率和配对检验的 p 值。**不用 150 题去支撑「涨了 3 个点」这种结论。**

**替代方案**：扩到 900 题把 CI 压到 ±3 个点。否决——人工标注成本远超收益，配对检验已能解决大部分问题。

### D2. 分层日志复用已有的 `emitStage`，不新建日志体系

`common/logger` 已经提供 `runWithTrace` + `emitStage`，且 T0-2 已在 orchestrator 埋点。本变更只需要：

- 在 `intent-classifier.ts` 增加两类事件：`intent.recall`（两路原始分）、`intent.fuse`（融合分）
- 在每道关卡增加 `intent.gate` 事件，字段固定为 `{gate, threshold, in: [...], passed: [...], dropped: [{label, score, reason}]}`

**为什么不新建一个 metrics 模块**：现有的 `traceId` 已经能把同一次请求串起来，再建一套会有两个关联标识，违背可归因的初衷。

**约束**：`emitStage` 的 payload 不得包含用户原文（既有规范 N-8 已因泄露原文修过一次），只放标签与分数。

### D3. reranker 方案复用 `AiService.rerank`，一次请求批量打分

做法：召回阶段拿到候选域后，把「用户输入 + 每个候选域的代表例句」组成 `documents` 数组，**一次调用** `rerank()` 拿到每个域的相关性分，用这个分做决策。

- 9 个候选域 → 一次 `rerank` 调用，9 篇文档，不是 9 次调用
- 阈值不再是拍脑袋的 0.7，而是从评测集上扫出来的（扫 0.3–0.9，取 F1 最高点）
- 降级：`rerank` 返回空或抛错时回落到现有融合分（`rag-retrieval.service.ts` 已有同样的降级写法，照抄）

### D4. LLM 分类方案用 `createLLM` + 枚举约束，不做 function calling

9 个意图规模下，直接把意图清单与判定标准写进 system prompt，要求输出 `{"intent": "<枚举值>", "confidence": 0-1}`，temperature=0。

**为什么不用工具调用/function calling**：单一枚举输出比工具调用更稳、更省 token，且便于在回放里做严格校验（输出不属于枚举即判错）。

**预期代价**：单次约 800–1500ms、成本按 token 计。是否可接受由对比表决定，不在设计阶段预判。

### D5. 三条路径共用同一回放入口，结果并列成一张表

`tools/eval/replay.py` 增加 `--method {current,rerank,llm}` 参数，三条路径走同一套打分与汇总逻辑，输出同一格式的报告。**禁止**为某一个方案单独写一份评测脚本——否则「比对了什么」本身就不一致。

### D6. 判定标准事先写死

| 结论 | 条件 |
|---|---|
| 切换到某方案 | 配对检验 p < 0.05 且该方案胜出，且 p50 延迟在可接受范围内 |
| 保留现有 | 无方案显著胜出，或胜出方案延迟/成本不可接受 |
| 结论不完整 | 任一必报维度缺失（准确率/各意图精确率/延迟/成本） |

延迟可接受阈值见 Open Questions。

### D7. 评测集与示例库必须查重

现有分类依赖 `intent_examples` 表里的例句做近邻匹配。如果评测集句子与例句库重合，测出来的是「背答案」的虚高分数。因此评测入库前必须做一次查重（规范化后精确匹配 + 高相似度近似匹配），重合项要么替换要么标注。

**这是本设计里最容易被忽略、但会直接让整个对比失效的一条。**

## Risks / Trade-offs

- **[人工标注带主观性]** → 边界样本双人标注，分歧记为「待裁决」，不计入准确率分母并在报告中单列。
- **[reranker 方案延迟上升]** → 一次调用批量打分；若仍超阈值，退化为只对 top-3 候选重排。
- **[LLM 方案成本不可控]** → 报告单列每次判定成本；可用缓存（相同输入直接命中）降低，但缓存命中率需单独报告，否则会虚高速度指标。
- **[150 题仍不足]** → 用配对检验补偿；若某次改进只有 3–5 题量级，结论直接写「不显著」。
- **[评测集泄露进例句库]** → D7 的查重是硬门禁；回放前自动执行一次并拒绝有重合的评测文件。
- **[三条路径口径不一]** → D5 强制共用入口；任何方案专属逻辑必须写在被测实现里，不能写在评测脚本里。

## Migration Plan

1. 阶段 A：扩充与查重评测集，登记新基线（仅现有链路）
2. 阶段 B：补分层日志，确认一次请求可被完整还原
3. 阶段 C：接入 reranker 与 LLM 两条候选路径（默认关闭，仅评测可达）
4. 阶段 D：三方对比，出报告与结论
5. 回滚：候选路径始终通过开关隔离，默认走现有链路；任何阶段失败不影响线上行为

## Open Questions

- **可接受的 p50 延迟上限是多少？** 当前 415ms。若要求 <600ms，reranker 方案的天花板就定了；若允许 <1500ms，LLM 方案进入候选。这是产品决策，需在阶段 D 之前确认，不影响 A–C 的实施。
