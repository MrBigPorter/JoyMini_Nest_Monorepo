# Proposal

## Why

意图分类当前基线是 63 题跑出 Top-1 68.2%。按二项分布计算，63 个样本下 95% 置信区间约为 **±11.5 个百分点**（56.7%–79.7%）——这意味着任何小于 10 个点的改进都落在噪音里，**现在没有任何改动可以被证明有效**。

同时，一次分类请求要穿过四道独立的分数关卡（召回及格线 0.70、路由回落线 0.50、执行门禁 0.70、边际 0.05），但日志只记录最终分。出了误判无法判断是「模型分低」「门禁提前淘汰」还是「融合权重错」，只能靠猜。这是这套逻辑「几个月不写就看不懂」的直接原因——缺的不是记性，是归因链。

`unify-intent-thresholds` 已经处理了其中两件（常量收口、删除融合前门禁）。本变更补的是它没覆盖的部分：**先让度量可信、让每层可见，再用数据决定架构走向**。

## What Changes

- 把 golden set 从 63 题扩到 **150 题**，按 9 个意图分层（每层 ≥12 题），补齐 `rag` 这个当前最弱意图（精确率 38.9%）的样本，使改动前后差异可被统计区分。
- 在分类链路的关键节点补**分层记分日志**：两路召回原始分、融合分、每道关卡的入/出分与淘汰原因。目标是一次误判能直接追溯到具体关卡。
- 基于扩充后的评测集做**三方案横向对比**：现有链路（修完门禁后）、召回后接 reranker 重排、9 个意图直接 LLM 分类。产出一张含准确率、各意图精确率、延迟、成本的对比表。
- 按对比结果给出架构结论：保留现有、升级为标准两阶段、或改用 LLM 分类。**本变更不预先承诺结论**，只承诺用数据得出结论。
- 依赖 `unify-intent-thresholds` 提供的常量模块与门禁修正；本变更不重复声明该能力的规格。

## Capabilities

### New Capabilities

- `ai-customer/intent-evaluation`: 意图分类的评测口径与基线管理——评测集规模与分层、回放执行、指标定义、基线可比性要求，以及方案对比的判定标准。
- `ai-customer/intent-observability`: 分类链路的分数可归因性——每一层必须记录进入值、离开值与淘汰原因，使任意一次判定都能定位到具体关卡。

### Modified Capabilities

（无。项目尚无已归档的 OpenSpec 规格；与 `unify-intent-thresholds` 的能力重叠已在 Impact 中说明处理方式。）

## Impact

**评测工具**

- `tools/eval/golden/intent.jsonl` — 63 → 150 题
- `tools/eval/replay.py`、`run-replay.sh` — 支持按意图分层统计、支持指定待测方案
- `tools/eval/baseline.json` — 新基线（旧基线保留为对照）

**分类链路**

- `apps/api/src/client/ai-customer/graph/utils/intent-classifier.ts` — 分层记分日志；可选的重排分支
- `apps/api/src/client/ai-customer/graph/nodes/intent-router.node.ts`、`orchestrator.node.ts` — 关卡日志
- 复用已有的 `AiService.rerank()`（bge-reranker-v2-m3），不新增外部依赖

**与 `unify-intent-thresholds` 的关系**

- 该变更负责：常量单一来源、删除融合前门禁、修正过期注释
- 本变更负责：评测集、分层日志、三方案对比
- **两份变更的 `specs/` delta 不重叠**。实施顺序上本变更的对比实验依赖前者先落地（否则对比的是有 bug 的基线）。

**不涉及**：数据库结构变更、对外 HTTP 接口、前端、SSE 事件格式、意图标签体系本身（不增删 9 个意图）。

**已知约束**：扩标注集需要人工判断，无法由 AI 全自动完成；150 题是目标下限，若某意图难以凑齐 12 题，需在提案后续修订中说明。
